# 多路关系的四种形态

要表达的东西：一条关系同时绑定三个以上参与者（比如 `{alice, acme, invoice-7}` 共同参与一次审计事件），而成员在这个关系里可能各有角色、权重、有效期，成员之间还可能有序。

逻辑上有四个候选形态。它们表达的事实集合基本相同——任何一条超边都能展开成人造节点加二元边，任何二元边也都是一条二元超边——差别不在"能说什么"，而在**关系是否是一个个体、属性住在哪一层、成员是否有位置**。下面逐个说明，最后给判据。

## 一、关系表

一张普通集合，键就是那几个身份：`MembershipKey { channel_id, member_id }`，一行一个成员。关系自己的属性（`nickname`、`since_ms`）是行上的普通列；反向方向声明成 lead face（`#[ok_lead]`）——它的条目段是从**键自己的字节**里切出来的，不复制负载，所以不可能与键不一致，也不需要维护。写路径把行与它所有的面放在同一批里。

- 能表达：成员各自的属性（行里的列）；成员有序（键里加一列排序维度，再用另一个 lead face 读）；同一成员多角色（多行）；反向索引不会漂移。
- 不能表达：关系作为独立个体存在——没有成员时它就不存在；关系级属性要么在每个成员行上复制 N 份，要么另开一张表多一跳回表。

## 二、集合顶点

不新增载体，而是给图加一种顶点：一个声明了成员类型的**集合节点**，成员边带谓词（`approver`、`receiver`、`evidence`），边的载荷带该成员在这个关系里的角色与权重。

- 能表达：关系个体（有 id、有属性、可在没有成员时存在）；关系级属性只存一份；成员各自的角色（在边上）；同一成员多角色（**平行边**——图本来就允许两条边连接同一对顶点，各自带谓词与载荷）；成员次序（边的键里放排序维度）。
- 代价：集合节点需要一个 id，而引用一条关系本来也需要 id；成员类型必须声明，遍历要能区分"这是实体顶点还是集合顶点"；不支持嵌套。

## 三、子图边界

把一组节点与边作为一个有 id、有生命周期的整体，可嵌套，可整体删除或换版本。

- 增加的表达力落在**包含、嵌套、作用域**上：这些属于所有权语义，不属于关系语义。RDF 的 named graph 是同一件事的先例——图作为一等值，用来标记来源、版本、访问边界。
- 强制边界只有两条实现路径：每个节点与边带 `scope_id`（靠纪律，越界不拦），或容器的 body 列出成员引用（强约束，但成员异构）。两条都落在既有原语上，没有第三种。
- 真正的坑是身份：一个节点在边界内、同时作为实体在别处存在时，要么共享（"在边界内"就只是一个标签），要么拷贝（身份重复，改一处不同步）。

## 四、超边

一条关系被物理具体化为一个载荷行加 N 条成员面：载荷行带关系自己的属性，成员面以"成员引用 + 边 id"为键，于是"哪些关系包含某成员"是一次前缀扫描，求交即集合运算。

- 能表达：关系个体；属性一份；成员集合一次读完（一次载荷行读）；删除干净（读载荷即知该删哪些面）；索引条目减半——没有方向，出去与进入两份面塌成一份。
- 不能表达：成员各自的属性——集合没有位置；放进载荷就只能整读、无法反查，放进面键就得加宽每条面并锁死扫描次序。成员次序同理。方向也丢了——集合本身无序。

## 对照

| 需要 | 关系表 | 集合顶点 | 子图边界 | 超边 |
|---|---|---|---|---|
| 关系是个独立个体 | 否 | 是 | 是 | 是 |
| 关系级属性只存一份 | 否（复制或另开表） | 是 | 是 | 是 |
| 成员各自的角色/权重 | 是 | 是 | 是 | 否 |
| 同一成员两种角色 | 是（两行） | 是（平行边） | 是 | 否 |
| 成员有序 | 是（键里加列） | 是（边的键） | 是 | 否 |
| 关系可以没有成员 | 否 | 是 | 是 | 是 |
| 按成员反查关系 | 是（lead face） | 是（成员边） | 是 | 是（成员面） |
| 方向 | 靠列名 | 是（边的方向） | 是 | 否 |
| 包含 / 嵌套 / 作用域 | 否 | 否 | 是 | 否 |

## 判据

三个容易被混起来的概念要分开：

- **聚合**——"这些东西属于同一个东西"：关系表够用，要"关系是个体"就升级成集合顶点。
- **包含**——"这些东西只在这个东西内有效，删容器即删内容"：子图边界。
- **嵌套**——"子图里还有子图"：子图边界加层级。

另一根更锋利的轴是**属性住在哪一层**：属性属于关系本身（事件类型、风险等级、置信度）→ 关系是个体更省；属性属于成员在这个关系里的位置（角色、权重、有效期）→ 成员必须有位置，集合模型就表达不了；属性属于两者都有 → 集合顶点（属性在点上，位置在边上）。

## 结论

默认用关系表：它已经是这个模型里的普通集合，不消耗新的面号码，反向方向靠 lead face 免费且不漂移。

需要"关系是个体、属性只存一份"时，升成**集合顶点**——它是图的一种顶点形态，复用边 id、平行边、批量写、顶点引用，不需要新载体。

需要所有权、版本、作用域时才用**子图边界**，并且实现成 `scope_id` 纪律加级联助手，而不是把节点真的嵌套起来。

超边不单独建载体：它唯一的净收益（关系是个体、属性一份）集合顶点已经覆盖，而它丢掉的位置能力（角色、次序、方向）恰好是复杂关系最常需要的。
