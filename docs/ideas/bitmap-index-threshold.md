# 位图索引在键寻址模型上的门槛

命题：把"某个值命中哪些行"存成一张位图（值 → 行的位集合），于是成员关系的求交变成机器字的按位与，而不是两路有序键流的归并。

这个想法在列存与 OLAP 里是既有做法。放到一个用键寻址每一行的模型里，它撞上的不是空间，而是两个结构性的东西。下面把编码、发号、写入契约分开说清，最后给判据。

## 编码不是难点：分组

现代位图编码（Roaring）把 32 位值域一分为二：高 16 位是升序数组里的桶号（最多 65,536 个桶，二分定位），低 16 位落进该桶的容器；容器按当时基数在三种形态之间切换——数组（≤4096 个值，稀疏时占用随元素数走）、位图（固定 65,536 位 = 8 KiB，稠密时占用与元素数无关）、游程（长连续区段，几十字节装下上万个连续值）。

于是"按 64K 分组"不是需要新设计的部分，它就是这套编码的骨架。尺寸要说准：64K 指**值域**，对应固定位图 8 KiB，刚好落进 L1 数据缓存；**缓存行是 64 B**（512 bit）。容器同时是存储单位和计算单位——两张位图按容器成对合并，任何一对容器都不会先展开成整张位图。

稀疏也不是问题：数组容器就是为稀疏准备的。

## 难点一：发号

位图要求每个成员有一个 `[0, N)` 的稠密序号——第 i 位代表第 i 行。而键寻址的模型里，一行的地址就是它的键：自描述、跨集合、删除即消失，没有序号。

要序号就得额外做三件事：

1. 分配一个稠密的行 id 列（代理 id）；
2. 维护"序号 → 键"的翻译表，否则位图给出的位号无法回到行；
3. 回答删除之后序号是否复用——不复用则号空间单调增长，复用则要墓碑或压缩，两者都会让位图与实际行集合短暂不一致。

这就是"存连续 ID"为什么不是实现细节：它是换了寻址模型。位图与"键即地址"不兼容，不是性能取舍。

## 难点二：写入契约

索引条目有两种物理身份，选哪一种决定了写侧的形状：

- **一行一条**（每对 `(值, 行)` 一条条目）：写一行只碰它自己那一条，没有跨行读-改-写。这是今天倒排索引的形状，但它装不下一个"集合"。
- **一值一条**（键是值，值里是该值名下所有行的位图）：写一行要读出整个集合、置一位、写回。一条条目被多行写入，这就是跨行读-改-写。

位图索引必然选第二种，而第二种与"每次写入只碰自己那条"的纯度契约冲突。编码再紧凑也不改变这件事：每次 `put`、每次 `purge` 仍要由该值组的每一行重新编码整个集合。

## 基数决定形态

"每个值一张位图"只在一部分情形下正确：

- **低基数**（状态、年份、租户）：一值一图，过滤即几张图求交。这是位图索引的正当用法，也就是 OLAP 里 `groupBitmap` 那类场景。
- **高基数**（`user_id`、时间戳、主键尾段）：一值一图是灾难——绝大多数值只有一两个成员，一个 8 KiB 位图或两元素的数组容器都是浪费。此时要么用 bit-sliced（一个位图对值的一个二进制位，用 log 个与运算算出一个值，适合范围判断），要么根本不该用位图。
- **集合自身**（一条关系的成员、一个分组的成员）：那是一关系一图，属于被存储的**值**，不是索引条目，与过滤无关。

三种形态不能混着谈。

## 唯一说得通的落点

若一定要在键寻址模型里做，位图只能是**派生的、可重建的**结构：从行能重建、坏了可丢弃，与其它派生面（`rebuild_faces` 那类）同一类别。

这样写侧那条最硬的反对意见降级为"跨行读-改-写发生在一个派生结构上，代价是新鲜度窗口和一次重建"。但**寻址问题不会因此消失**：派生层同样要发号，同样需要 id 与翻译表。

## 判据

三条同时成立才值得做：

1. 列基数低（每个值的平均成员数远大于一）；
2. 谓词组合固定、且跨查询反复求交——位图是一个值，可以反复用，固定成本才被摊掉（有序键流用过就没了）；
3. 能接受一个可重建的派生层，不进纯度契约。

任何一条不成立，位图的正确用途就只剩查询侧：把扫出来的键集合用这种编码持有并反复求交，不发号、不动写入契约。它在那里赢的地方是"复用、输入本来无序、需要跨批次持有"，而不是存储形态。
