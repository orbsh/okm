# 超边即成员表：给"一组边/一组节点"一个不污染底图的形状

状态：设计方案（2026-11-12），待定编号的 ADR 草稿。接受后转 `docs/adr/0066-…`（中英孪生）。它只回答一件事：**图里怎么表达"分组"**——社区、事件涉及的事实集合、子图、权限边界这些。

## 结论

分组有两种，判据是**这个分组本身是不是一个实体**：

```
是实体   域、文档、主张、经验体           → 节点 + 成员边
         你要引用它、给它属性、让它出现在导航里
是标注   社区、子图、事件的事实集合、权限边界 → 成员表：(组, 成员) 一行
         它是对一组断言的陈述，不是断言本身；成员默认是**边**，不是节点
```

  用错形状的代价是结构性的，下面两条是本文的全部论据：**底图不因分组而改变**、**标注用行而不是节点**。

## 为什么标注不能做成节点

把一组边"伪装"成节点（星形结构），四处丢信息，且补不回来：

- 顶点集相同而边集不同的两组无法区分（`{ab,bc}` 与 `{bc,ca}`）；
- 一条边被多组共享这件事，在星形下不可见；
- 边自己的角色与属性没有位置，只能再套一层；
- 算法被污染：伪节点成为高连接度的假枢纽，社区发现会把它们识别成核心组件。

而底图本来就是一整张普通图。分组只是它上面的组织层，算法不需要知道：

```
底图    a—b—c—a                 ← 最短路径、PageRank、连通分量、社区发现都在这里跑，完整无损
组织层  {ab,bc}→h1, {bc,ca}→h2   ← 只在查"这一组包含哪些事实"时才用到
```

  由此顺带得到一个便宜能力：**子图代数**。交、并、差、版本 diff 都是对成员表的集合运算——"这个社区和上一版重叠了哪些事实"在节点属性里根本问不出来。

## 行型：一条固定面，组号进键尾

```
行键   [ns][0x0C][kind u8][group_id BE][member_ref]
       kind      分组类型（社区 / 事件 / 子图 / 权限域），一字节，闭合词表
       group_id  运行时分派，不是声明序
值     空，或少量组内元信息（角色、权重）
一级   组 → 成员：前缀扫描 (kind, group_id)
二级   成员 → 组：另一份前缀（成员在前），写路径同批维护
```

  **不要为每个组分配计数族槽位。** 计数族（`0x3nnn`/`0x5nnn`）里的计数器是声明序、上限 4095，适配"一个集合声明了第几条索引"这类静态小集合；组是运行时创建、数量无界，用计数族表达会在第一次重算社区时撞墙。组号放键尾，一种行型就够，组数无上限。

## 边成员是权威，节点成员是派生索引

  要"排序 + 流式"地取参与者，节点顺序必须是某处的**键序**——这是一条硬约束。按边 id 扫出来的端点是乱序的，分块排序再合并也不行（跨块的交错无法只靠"记住上一个"去重）。所以形状定成两份成员行，一份权威、一份派生：

```
0x01  边成员（权威）   [ns][0x0C][0x01][group_id][edge_id]
       组里有哪些边；按边号有序，前缀扫描即得

0x02  节点成员（派生） [ns][0x0C][0x02][group_id][node_id][edge_id]
       按节点号有序，同一个节点的多行相邻；流式去重只需记住上一个节点
```

  `0x02` 完全从 `0x01` 与边行导出（边行本来就带两端），写路径在**同一批**里维护，任何时候都可以重建——所以它不是第二份真相，是一个索引。它存在的理由只有两条，但足够：

- **流式**：按 `(node_id, edge_id)` 有序出，同节点的行连续，去重是"与上一个比较"，不需要内存集合；
- **计数顺带给出**：某个节点在这个组里出现了几行，就是它被几条成员边覆盖。

### 完备性靠一条写入前提，而不靠补行

  导出法是完备的，前提是**没有孤立节点、没有单例组**：

```
节点只在成为某条边的端点时存在 —— 单独建节点这条路径不存在
组只在有两个以上成员时被创建 —— 单成员的分组不落地
```

  在这两条成立的前提下，任意组的成员都能从成员边完整导出，`0x02` 只是它的有序投影；不需要为"某些成员没有边"预留形状，也就不需要节点成员作为并列的第二种模式。这两条落在写入路径上（建边时按需创建端点，不单独创建节点），是模型的一条规定，而不是查询时的容错。

  代价明确：每个成员边两行派生（两端各一），加孤立节点若干行。成员行总数约为边数的 3 倍；换来的是参与者视图有序流式，以及"一个组有多少节点"可以一次前缀扫描数完。

  读取时两条路径各自成立，不需要并集：

```
组的边     扫 0x01 → 边号有序，逐个取行
组的节点   扫 0x02 → 节点有序，跳相邻重复即得去重结果（可流式、可 take(n)、可提前终止）
```

  写入契约只有一条：一条边加入某组时，`0x01` 一行 + 两端各一条 `0x02` 行，同一批；删边时同批删这三行。漏了不影响正确性（`0x02` 可以整体重建），影响的是新鲜度。

## slot 预算

固定面（1 字节，`0x00`–`0x0F`，全模型共享）：

```
0x00 主记录   0x01 动态段   0x02/0x03 字段名词表   0x04/0x05 谓词词表
0x06/0x07 图出/入边   0x08/0x09 图谓词+出/入边
0x0A 向量快照   0x0B 已退役（保留，旧库仍在用）
0x0C 0x0D 0x0E 空闲      0x0F 表元信息（也是 1/2 字节分隔的门槛）
```

  16 个里 12 个有主，**可用只有 3 个**，且是全局的：不是"每个集合三个"，是整个模型还剩三种新行型。建议：`0x0C` 成员行，`0x0D` 预留给投影元信息（构建戳、重建状态），`0x0E` 不预分配。能塞进既有行型键尾的（kind / group / 版本 / 角色）绝不新开固定面。

计数族（2 字节，高半字节 ≥ 1）：

```
0x1nnn 词表名→id   0x2nnn 词表 id→名   0x3nnn 声明索引   0x4nnn reduce   0x5nnn lead face
0x6–0xF 空闲 —— 10 个族，每族 4095 个计数器
```

  实例侧极宽裕（仓库现在全部声明面只有个位数），但如上所述，它服务的是声明序，不服务无界的组。

键长：成员行比普通行多出固定面 1 + kind 1 + 组号 8 + 成员引用约 16 ≈ 26 字节，与今天图边 `[ns][0x06][src][dst][edge_id]` 同量级；同组内 `(kind, group)` 前缀重复，LSM 前缀压缩吃掉大半。真正要盯的指标是**成员行 / 边的比值**（一条边平均属于几组），它决定存储与写放大。

## 版本与删除

  标注会被反复重算，所以组成员带版本：

```
一次重算   → 新的 group 版本；旧版本保留，可 diff、可回滚、可对比
删除一条边 → 它的归并行由写路径同批删除
漏删兜底   → 以边表为准可重建，垃圾可清，正确性不留洞
```

  第二条不能假定数据库级联：okm 没有外键级联，删除要么扫（按 (kind, group) 前缀取成员）要么墓碑。所以"谁清归并行"必须写成契约，而"以边表为准可重建"是它的兜底。

## 多分辨率：分组顺带给了收缩

  组与组的层级（`parent_id`）让"先子图内算、再组间算"变成两次查询：子图内精细计算，组间把跨组边收缩成组与组之间的边。这正是 Louvain 的原理（节点合并为超节点、迭代向上），也是多重网格在图上形态；而在本模型里，**收缩与展开只是对成员表做一次 group by / join，不需要任何图重构**。

  精度要诚实标注：忽略跨组边对度类指标（中心性、PageRank）失真小，对路径类指标（连通性、最短路）失真大；被忽略的边应当是可查询的**残差边**，而不是静默丢弃。

## 写入 API：一次调用，声明、分组与合并一起

  不新增"超表"这种声明。用既有的图，加一个把"边/节点声明"与"超边"放进同一次调用的写入口，合并走 builder：

```rust
Vec::<Decl<G>>::new()
    .decls([ Decl::Node(G::Nodes::User, key), Decl::Edge(head), … ])   // 端点按需创建
    .hyper_edge(HyperEdge { kind, id, payload })                       // id None = 新建
    .reduce_node::<User>(|u: &mut User| u.seen += 1)                   // 每类节点注册一次
    .reduce_edge(|e: &mut E| e.weight += 1)                            // 边载荷每图一种，闭包一个
    .reduce_hyper_edge(|h: &mut Dict| h.insert("w", …))                // 超边属性是动态载荷
```

  四个类型问题必须分清，它们是这套 API 的全部内容：

**1 `Decl` 只有两个变体，节点种类在生成枚举里。** `Decl<G>` 永远是 `Node | Edge`；"多种节点"由 `#[derive(GraphEncode)]` 为 `#[ok_nodes(…)]` 生成的枚举表达——`G::Nodes::User`、`G::Nodes::Org`……一个变体一个集合，ns 取自各表自己的 `#[ok_ns]`（`okm-derive/src/graph_encode.rs:150-165`）。所以声明多长都不影响 `Decl` 的变体数。

**2 节点 reduce 按集合注册，边 reduce 只有一个。** 节点是异质的（User / Org / Asset 各有自己的字段），一个闭包收不下；所以 `reduce_node::<T, _>` 用 turbofish 指明集合，builder 内部按类型存，只作用于该类的 decl。边相反：一张图的边载荷就是它的声明类型 `E`，只有一种，所以单个 `reduce_edge` 就够。

**3 超边也有属性，而且是动态的。** 它不能是纯集合：组的成员数、权重、最近写入时间都要有地方放，而 `kind` 是运行时词表（社区/事件/子图/…），不可能为每种 kind 生成一个 Rust 类型。所以超边载荷 = 动态段那一套（`Dict`），`reduce_hyper_edge` 收到的是 `&mut Dict`，写入与合并都在同一批里完成。

**4 创建与合并同一条路径。** `id: None` 新建并返回组号，`id: Some` 合并进已有；成员取并集，重复加入幂等（同一 `(kind, 组, 成员)` 一行，写路径 upsert）；三个 reduce 都在这一批里求值，不产生二次读-改-写——ADR-0028 那套计数器（读/写/工具三通道）就落在这里。

  其余操作落在同一行型上，不需要新声明：`remove`（删成员并清归并行）、`merge(groups, into)`、`split(group, members)`、`reassign(edge, from, to)`、`lookup(kind, id)`、`members(kind, id)`（边序前缀）、`nodes(kind, id)`（节点序前缀，流式去重）、`diff(a, b)`（两条超边或两个版本的成员差集）。

## 与本仓既有提案的关系

`docs/ideas/hypergraph.md`（2026-10-24 记录的外部提案）里已经出现过同一行形状：

```text
payload      [ns][slot 0x00][edge_id BE]              → 超边的载荷
member face  [ns][face slot][member NodeRef][edge_id]  → 成员面，一个成员一行
```

  它与本文的 `[ns][0x0C][kind][group_id][member_ref]` 是同一种东西——**一个成员一行**——差别有三处，都是本文相对它的推进：

1. **成员是谁。** 原提案的成员是节点（`NodeRef`）；本文允许成员是**边**。这一点是分水岭：成员是边时，分组落在底图的边上，算法完全不受影响；成员是节点时，分组必须借一个伪节点才能进图。
2. **组有没有载荷。** 原提案要求每个超边有一行载荷（组是实体）。本文把这一半留成可选的：组可以什么都没有，只是"一组边的名字"——那正是社区、子图、权限边界的形态。
3. **键的方向。** 原提案的成员面是**成员在前**（`[member][edge_id]`，答"哪些组包含 M"）。本文需要两个前缀：组在前（答"这个组有哪些成员"）与成员在前（答反查），两者写路径同批维护。

  所以不是另起一套，而是把原提案的成员面**推广成两件事的组合**：`(组类型, 组号)` 决定它是实体还是标注，成员可以是节点也可以是边。原提案仍然是"组是实体、成员是节点"那个特例的正确记录。

## 与既有决定的衔接

- ADR-0030：固定面与计数族的分工、`slot ≤ 0x0F` 的一字节分隔——本方案不新增计数族，只占一个空闲固定面。
- ADR-0017：图边的 ns 纪律与面编号；成员行住哪个 ns 由调用方决定，不与边的面冲突。
- ADR-0054：lead face 从键自己的字节切片；成员表的二级前缀是同一思路（不在负载里复制身份）。
- 纯度契约：成员行是"一行一对"，不是一个值里装一个集合——不触发跨行读-改-写。

## 未决

1. **组号宽度。** 8 字节够不够（社区每轮新版本会不会耗尽），还是 `(kind, group, version)` 三段。
2. **kind 词表。** 闭合的几种，谁有权新增（写路径校验还是声明）。
3. **残差边的行型。** 单独行型还是成员表里的一种特殊 kind。
4. **一致性校验的成本。** "以边表为准重建"是一次全扫还是按组版本增量；全扫的触发条件。
5. **派生行的重建粒度。** 全量重建（一次全扫边表）与按组版本增量重建的触发条件；以及 3 倍行数在多大规模上需要压缩。
6. **"不单独创建节点"的强制点。** 写在图 API 里（拒绝建孤立节点）还是仅作约定；外部导入的历史数据没有这条保证时，导出法会漏掉那部分节点。
6. **双向前缀的权威方向。** 组→成员为准、成员→组可重导出的前提是写入同批；跨批写入时如何兜底。
