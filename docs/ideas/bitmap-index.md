# 集合成员关系的位图索引：Roaring，以及它要的那个序号

外部提案的第三份（2026-11-12），与 `schema-aware-index.md` 里那两种索引形态并列记录。只记录，不设计、不排期；`okm-query` 里没有任何东西依赖它。它与那两份的区别在改动对象：不是一条索引条目如何被找到，而是一行集合用什么表示。

## 提案

`MODELING.md` 的「集合成员关系：按基数选倒排索引或 bloom」一节否掉了位图索引：每个值一条 entry、值里装着携带它的那些行的位图，于是成员关系的求交变成机器字 AND。两条性质把它挡在外面——一条被多行写入的 entry 就是跨行读-改-写；比特要靠行序号寻址，也就是一个稠密 id 空间加一条回到键的翻译，而那正是代理 id 带走的东西。提案是同一个形态配上真实编码：**Roaring 位图**，Lucene、ClickHouse、Spark、StarRocks 实际在发的结构，Rust 里是 `roaring`。它点出两个座位，是两个不同的问题——存储侧的 entry 形态，和查询侧的集合表示，后者只是 `OrderedSets` 已经给出的那些集合的一种表示。

## 组件

论域是 32 位无符号整数，一分为二。高 16 位是升序数组里的桶号（最多 65,536 个桶，二分定位），低 16 位落进该桶的容器，容器按当时基数在三种形态之间切换：

- **数组容器**，最多 4096 个值：低 16 位有序排列，每个 2 B，稀疏时占用随元素数走，上限 8 KiB。
- **位图容器**，超过 4096 个值：固定的 65,536 位（8 KiB）字数组，过了临界点占用就与元素数无关。
- **游程容器**，长连续区段：`(起点, 长度)` 成对记录，上万个连续值只需几十字节。

容器同时是存储单位和计算单位。两张位图按容器成对合并（`and`、`or`、`xor`、`and_not`）：数组与数组归并，数组按值逐个探位图，位图与位图按机器字 AND——目标支持时吃到 SIMD 字宽——任何一对容器都不会先展开成整张位图。固定的 8 KiB 是这套设计的关键：它刚好落进 L1 数据缓存，热点集合上的多路过滤于是花在缓存里的字上。

## 存储侧：编码一条拒绝理由都补不上

上面两条理由都不是空间问题。Roaring entry 会比朴素位集紧凑，但它仍要由该值组的每一行在每次 put、每次 purge 时重新编码——写侧那条反对意见不会因为值变小而减弱。读侧要的是一个比特地址，而编码不提供地址：一个位号就是位号，装它的容器是 8 KiB 还是 20 B 都一样。所以这个座位要动的是纯度契约本身，那是比编码更大的问题，而 `MODELING.md` 已经答否。

## 查询侧：比较对象是 `intersect`，不是扫描

这里的说法是比遍历有序键流更快，而要对标的对象是 `OrderedSets::intersect`：一趟惰性、零分配，输入顺序由索引免费给出。位图 AND 要物化两侧，所以它是另一种取舍，不是同一种取舍的更快版本，且只在三种情况下赢：

- **复用。** 流用过就没了；位图是一个值，可以被反复求交。拿同一个基集过多条谓词，或者把跨查询持有的摘要反复求交，才是这套编码的固定成本被摊掉的地方。
- **无序。** 输入本来不按键序时，流路径要么排序要么漏键——有序是契约，不是运行时检查——而 AND 根本不需要顺序。这是 `MODELING.md` 已经承认的唯一一条好处。
- **持有集合。** 跨查询或跨批次，集合总得存在某处；在那里 Roaring 就是一个稀疏到稠密整数集合的合适表示，与任何索引论证无关。

类型边界决定资格。`roaring::RoaringBitmap` 寻址 32 位值；`u64` 要用 `RoaringTreemap`，那是一层 u32 位图的映射，为拆分付费。okm 的键是任意声明宽度的字节段，所以「把扫出的主键编码成位图」只在键本身就是应用自有的序号时成立——`u32` 身份列，不是 `Str` slug，也不是稀疏 `u64`。定宽不够：比特要可寻址，而宽度不等于稠密。

## 场景分类：位图索引一般出现在哪

位图索引不是性能技巧，是形态匹配。三条前提要同时成立：值能映射成稠密整数（按比特寻址）；写是批量的、读是大量的（更新是整块重编码，不是追加一条记录）；查询是多条件集合运算（等值、IN、AND/OR/NOT、去重计数），不是范围与排序。

满足这三条的场合只有几类，而且都是「一个值一张位图、位是行序号、方向是值 → 行集合」这同一个模式：

- **搜索引擎倒排。** 位是段内文档号，值是 term，多 term AND = 同时含这些 term。Lucene / Elasticsearch / Solr / Tantivy；段不可变免费满足第二条前提，`RoaringDocIdSet` 与 filter cache 都长在这个形状上。
- **低位基数维度列（OLAP）。** 位是段内行号，值是维度取值，多条件 AND = 同时满足这些等值谓词。ClickHouse 的 bitmap skip index 与 `groupBitmap`、StarRocks / Doris 的 bitmap 索引、Druid 的 bitmap index；去重计数是 OR 之后 popcount。
- **标签圈选 / DMP。** 位是用户 id，值是标签，多标签 AND = 同时带这些标签的用户。这是 Roaring 在国内最典型的落地；分片按 id 区间切，圈选就是把各分片的位图各自 AND 再并集。
- **老式 bitmap index（Oracle 那一代）。** 位是 rowid 序号，值是列取值，多列组合谓词 = 多个位图 AND。只在批量加载、只读分析的数仓里存活，因为一次 DML 要锁住整条 key 的位图。

反方向或另一形态的三种，不是这个模式：

- **图邻接位图。** 一个位图对一行，位是邻居编号。两张 AND 问的是两个顶点有哪些公共邻居——是行的集合运算，不是值的。
- **行内位图字段。** 一行自带一个成员集合位图（权限、成员、类目），AND 是拿它跟另一张位图比较，问「我的集合是否包含你」。okm 里 bloom 按行走就在这个位置，只是 bloom 有假阳性。
- **bit-sliced 索引。** 一个位图对值的一个二进制位，回答范围（大于/小于），不是 Is-in。老一代 Fastbit 的做法，现在少见。

隐藏前提是**共享序号空间**：AND 有意义，是因为两张位图的第 r 位指的是同一行。所以 Lucene 必须 per-segment（跨段对不上，只能归并），DMP 必须全局统一用户 id 空间，跨表位图基本不能直接 AND。这条前提同时给出写侧代价：插一行要动 k 张位图（k = 这行带的取值个数），每张都是对共享块的读-改-写——段不可变或批量加载把它摊到一次整段重写上，逐行事务摊不掉，于是回到 Oracle 锁死的那条教训，也就是 `MODELING.md` 拒绝这个 entry 形态的理由。

## 什么情况下值得做

两个数，都还不存在：

- **集合步在查询时间里的占比。** `OrderedSets` 那条路径不分配、顺序免费，所以这个占比就是全部天花板。测量的形状已经在 `docs/internals/query-cost-attribution.md` 里：一次 1000 条 entry 的查询，引擎的索引读取占 943.8 µs 的 16.7 %，其余在取行循环里——集合步若是同一量级，这套编码就没什么可赢的。
- **复用比。** 同一个键集被求交超过一次的比例。等于 1.0 时没有东西可摊，位图就是一次带分配的、更慢的 `intersect`；只有复用基集的工作负载才让它划算。

在两者都测出来之前，「比遍历键流快几个数量级」和 index-shape 那份提案是同一类说法——而那一份止步于 1.20× 的上限。
