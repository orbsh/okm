# ADR-0019：部分索引——声明上的 `where(path)` 谓词，而不是返回 Option 的函数

日期：2026-09-21
状态：已实现。`where(path)` 是 `#[ok_index]` 的一条子句，常规字段索引与函数索引都可用；展开为 `KvIndex::admits` 覆盖，在 `entry_pairs` 开头短路。

## 背景

每条索引条目的代价由每一次写入永久支付。在真正需要过滤的分布里——工单表 99% 已关闭、队列表 99% 已出队——绝大多数存量行用不到某个访问方法，为它们建条目在键空间与写入成本上都是纯开销。需求是一个谓词："这一行属于这个索引，那一行不属于"。

当时有三个机制可走。

1. **函数返回 `Option<R>`**：`None` = 该行不产生条目。
2. **声明谓词**：`where(path)`，整行到 bool。
3. **什么都不加**——函数索引形态已经覆盖它：返回空 `Vec` 的 `func` 产生零条目，所以一个函数体内部决定成员资格的函数，事实上已经是部分索引，只是名字不叫这个。

## 决策

谓词**声明化**：`where(path)` 与 `fields`/`includes`/`key`/`func` 并列在 `#[ok_index]` 体内，两种索引形态都适用——过滤是"哪些行在这个索引里"的属性，不是"排序段怎么产生"的属性。

```rust
#[ok_index(open_by_assignee {
    fields(assignee_id, created_at),
    includes(title_len),
    where(ticket_is_open),      // fn(&Ticket) -> bool
})]
```

机制上它是一道接缝，不是一个子系统：derive 生成 `KvIndex::admits` 覆盖（`fn admits(document: &Document) -> bool`），trait 默认返回 `true`，写路径在 `entry_pairs` 开头对每行求值一次——那是条目生成的唯一位置，`put`、`delete`、`save_into` 共用。写路径没有别的地方能创建索引条目，因此过滤在构造上就是完备的：不新增键格式、不动扫描路径、无运行时簿记。

**否决：函数返回 `Option<R>`。** 既然有了谓词，`Option` 就是同一个行级条件的第二种拼法，而且是更隐蔽的那种——声明不再说明哪些行在索引里，函数体悄悄决定它。本系统的索引声明讲究端到端可读（slot、fields、includes、key 前缀全在声明上）；"覆盖哪些行"恰恰是最容易搞错的一维（查询完备性取决于它），把它埋进函数体是最差的存放位置。

另有两条独立理由：

- **便宜路径必须保持便宜。** 过滤的真实场景通常是普通列上的条件，不是计算值上的条件。走 `func` 会为一个平凡谓词强加一次函数调用与一次分配，并放弃 `includes`（函数索引与 `fields`/`includes` 互斥——那是解析期检查，不是机制约束）以及让 `fields(...)` 安全的编译期宽度校验。这笔交易还怪：把一个普通过滤索引改成函数索引形态，改变的不只是声明形状，还有此后每一次写入的成本。
- **把行成员资格混进值函数，会破坏 func 自己的不变量。** 函数索引的既有理由写在文档里："一条声明驱动两侧"——查询侧探针调用同一路径，归一化不可能漂移。一个既决定成员资格又投影值的函数会以一种隐蔽方式破坏它：探针侧只该镜像值那一半，而分辨哪一半是哪一半需要读函数体。有了声明谓词，切分是显式的：值那一半镜像，谓词那一半按定义不参与探针。

**未声明的那条路保留为逐值工具。** 返回空 `Vec` 的 `func` 仍然不产生条目；那是逐值丢弃（一行多 token 里某个 token 不要、其余保留），`where` 表达不了，因为 `where` 是行级的。两个机制按此分工写进文档：`where` = 行级条件（声明可见，常规索引也能用），函数体内过滤 = 逐值丢弃。

## 后果与边界

- **纯度契约扩展到谓词。** `delete` 经同一个 `entry_pairs` 从行重新派生删除集合；谓词读取时钟或外部状态会让删除时生成的集合与写入时不同，留下悬挂条目。与 `func` 是同一形状的契约，现在多覆盖一个函数。
- **谓词翻转会留下悬挂条目，而这是既有的覆盖写契约。** 条目地址由索引字段与主键决定，谓词只决定这次写不写。所以 `put` 覆盖一个不再被接纳的行不会移除旧条目——与今天"索引字段值变了也不移除旧条目"完全同类（`okm-core/src/model/document.rs` 的 put 文档明文写着这一点，`delete` 就是因此存在）。过滤带来的差别是频率："行离开索引"从事故变成常态。清理要用**生成该条目的那一行**去 delete；测试同时锁定了悬挂行为与正确的操作顺序。没有新增清理机制——发明一个会与"唯一条目生成点"的设计相抵触。
- **读侧无机制、无完备性校验。** 部分索引只是更稀疏：`scan::<I>` 不变，谓词在读时从不被查询。结果只对"查询条件蕴含谓词"的查询是完备的；okm 没有查询优化器，索引由调用方指定，所以这是建模纪律，写在建模指南里，机制无法校验。
- **谓词不进地址。** entry key 仍是 `[ns 2B][slot 2B][索引字段][主键前缀]`。被拒的行其 entry key 仍可算出——它就是该行的派生地址，只是写路径从没写它。
- **成本是每文档一次谓词调用**，不是每条 entry 一次：fan-out（多值）索引求值一次谓词后再展开。没有 `where` 子句的索引零成本（trait 默认内联返回 `true`）。
- **不变的部分**：slot 分配与声明 append-only 纪律、条目布局、`scan`/`scan_covered`、`save_into` 的编码面定位、`key(...)` 截断、`func` 与 `fields`/`includes` 的互斥。`deprecated` 声明照样不生成任何东西——其上的 `where` 子句是惰性的。
