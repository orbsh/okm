# 0042 — 布局版本是戳记，不是兼容承诺

> **语言：** [English](0042-layout-versions-are-stamps.md)（主） · [中文](0042-layout-versions-are-stamps.zh-CN.md)

**状态：** Accepted（2026-10-27）。同日应用：k10r 的 `EntityRow` 回到 `version = 1`，
使用计数挪到**前面**——读者会去找它们的位置。
**日期：** 2026-10-27

## 背景

payload 带一个版本字节，解码器有一条兼容规则：比读者新的 payload 拒绝，比读者旧的接受、
缺失的字段取默认值。这条机制是对的，而它也是块磁铁：一旦 codec 能吞掉形状变化，
形状变化就会开始**绕着它**设计。

在这条记录之前，有两处是那么写的。

- 实体行的使用计数被追在**尾部**，「因为尾部追加是唯一合法的加字段方式」——这是 codec
  决定了字段该放哪。读者去找一个节点的计数，会在 `name` 之后、在结构体本该放残渣的那一段里
  找到它。
- 删掉一个字段（向量，ADR-0019）让后面每个帧都移位，于是每个已有 store 都要重建——而这个
  重建变成了一段 ADR 里的论证，仿佛一个从没存过生产数据的记忆核心，欠它自己的临时目录一条
  升级路径。

## 裁决

**1. 版本字节是一枚戳记。** 它记录 payload 是按哪个形状写的。它不是「下一个构建能读它」的承诺。

**2. 字段放在它该在的地方。** 声明顺序为**读者**而选——身份在前，读会碰到的其次，残渣最后——
绝不为 codec 追加方便而选。

**3. 兼容是**按表、以书面形式**选择的。** 一张表只有在某条记录写清「这些 payload 必须活过形状
变化」、并写明理由时，才保留向后兼容。沉默即重建。

**4. 形状一变，号就重置。** 字段集变了而没有记录主张兼容，新形状就是这张表自称的形状
（通常重回版本 1），旧构建写下的 store 丢弃重生成。

**5. 真需要迁移的那天，走导出 → 导入。** bundle 与按表 Parquet 导出已经存在，装的是调用方
自己的行，是有归属方支持的路径。为历史上每一个形状都在位保留一个解码器，不是。

**6. 解码规则维持原样。** 更新的 payload 拒绝、更旧的取默认——这是让陈旧的 store 大声失败或者
落得合理的东西，不是保留每个形状的许可证。默认值是版本迁移语义，不是「字段可以缺席」。

## 后果

- **schema 保持可读。** 字段的位置说明它是干什么用的；没有任何东西因为「来得晚」而待在尾部。
- **不必为每次重建写 ADR。** 真实使用之前的记忆核心重生成语料，是提交里的一行说明，不是一份
  迁移设计。
- **陈旧的 store 永远不会被悄悄重新解释。** 号重置之后，旧 payload 要么被版本检查拒绝，要么解成
  胡说而它的主人会发现——所以诚实的指示是「删掉它」，不是「小心地读它」。
- **代价落在真正需要兼容的人头上**，而且落成一条**写下来的**要求，而不是 codec 的意外性质。
