# ADR-0056：segment 就是迁移通路

> **语言：** [English](0056-the-segment-is-the-migration-path.md)（正本）· [中文](0056-the-segment-is-the-migration-path.zh-CN.md)

**状态：** 已接受（2026-11-10）——仅裁决；回放路径一行代码都还没有。此后已落地：store 边界的捕获（`ChangelogStore`，§2）、自描述段容器（§7）、`ensure_baseline`（§3）、解码器与窗口合并进核心，以及取代 `okm-drain` 的独立程序 `okm-parquet`（segment → Parquet 窗口，§8）。回放已落地（`okm-parquet replay`：行经目标库的写路径重写、词表 id 重新 intern），并接上迁移后的对账扫描（`--reconcile`：扫一遍旧库的主面，旧库才是记录）；sink 把导出目录变成一张 Delta 表（`okm_parquet::delta`，在抽干 crate 里：每个窗口一条 JSON 提交，所以追加是一行而不是重建 snapshot；用 DuckDB 的 `delta_scan` 验过）；窗口把文档的开放字段作为 `variant` 列携带，物理形态是规范的 `struct<metadata, value>`，所以对只追加的表段路径是完整的；store 扫描导出降级为状态转储而非退役；切换握手已裁决、尚未实现（§6：每表一个 `owner` 文件、一份租约、以及新写者开工前必须成立的位置相等断言）；仍缺：delete file（或 deletion vector）、分区、文件大小目标——见同日 PLAN 小节。本 ADR 最初指名的 Iceberg 元数据写入器是被替换而非扩展的，见 ADR-0058。
**日期：** 2026-11-10
**依赖：** ADR-0010（线字节）、ADR-0034（表有名字）、ADR-0042（布局变更是版本，升级是部署形态）、ADR-0045（日志：捕获、段、抽干）、ADR-0046（`okm-series`，另一种只追加容器）

## 背景

ADR-0045 把日志留成了一条导出饲料：在提交边界捕获、抽干成 Parquet、喂给湖。两件它没回答的事，一件它回答得太窄。

1. **没有回去的路。** `okm-drain` 产出 Parquet；`parquet_io::import_parquet` 通过 `Table::put` 还原一个**带类型**的库。没有任何消费者能把 segment 变成库。日志是单向阀。
2. **sink 表达不了它收到的真相。** 含删除的窗口会让抽干停下（`okm-drain/src/lib.rs:227`），因为只追加的 Parquet 文件没法说“这行没了”。日志能带删除，sink 刻意拒收。
3. **ADR-0042 §7 点名了部署形态（蓝绿、短切换、增量补齐），没点它的载体。** 补齐被留成“import”，实践里就是 Parquet——而 Parquet 丢掉删除，并把历史压成追加。

同时，关于当前捕获的三个结构事实决定了什么可做：

- **被捕获的那半边本来就是真相半边。** `carried()`（`okm-core/src/changelog.rs:476`）丢弃声明索引、reduce、前导面、图的遍历面、向量快照和表元行，保留主行、动态段、四向词表和两面谓词。日志带的是文档，不是条目——而这正是写路径重建派生半边所需的东西。
- **过滤器按字节判断，不看声明。** `carried` 只读 key 的 header 前缀和 slot 号。因此它不需要 schema、不需要类型、也不需要装配点——只需要键空间。
- **捕获是按 collection 实例接线的。** `with_changelog` 是 `Collection` 上的构造器（`okm-core/src/model/document.rs`）：它打开该表的目录、写该表的 sidecar，并且只通过该实例的提交做暂存。没接它的实例写下的行，任何日志都不会提到；调用方自建的 batch 必须记得走 `Collection::commit_batch` 或 `stage_capture` / `flush_capture` 那一对，才会被捕获。

## 裁决

### 1. 术语：changelog、segment、baseline、drain、replay

| 词 | 是什么 |
|---|---|
| **changelog** | 机制：每表一条变更流，在提交边界追加，进程外抽干（ADR-0045） |
| **segment** | 这条流的封存文件单元（`.segment`），不可变，按名字排序 |
| **baseline** | kind 为**状态**而不是**增量**的段：某时刻整张表的真相半边 |
| **drain** | 把段变成别的格式的消费者（今天是 Parquet） |
| **replay** | 把段变回库上写入的消费者 |

`okm-series` **不是**第二种 segment。它的封存件是 `.log`，体完全不同（按桶的目录、时间差分、带索引的压缩块、nTLV 体，ADR-0046）。两种容器共享的只有约定——目录装分片、改名封存、撕裂即截断——别的一概不共享。所以每种格式带自己的 magic，读者拒收对方；跨格式没有 kind 字节。段格式内部保留一个 kind 字节，因为 delta 与 baseline 记录形状相同、扩展名相同，回放语义却相反。

### 2. 捕获挪到 store 边界，全局开启

捕获变成 `commit_batch` 之上的 store 装饰器（`ChangelogStore`），按 key 的 2 字节 header 分流到各表目录，启动时由配置一次开启，并支持按 ns 的排除表清单（应用自己的追加日志表、缓存之类）。理由：

- 所有写路径都以 `Batch` 穿过 `commit_batch`，包括调用方自建的跨表批——于是两种被记录在案的“隐身”方式（实例没接日志、批直接提交到 store）消失，而不是被写成纪律。
- `carried` 不需要声明，所以一个没有任何 schema 知识的边界就能执行真相半边规则。
- 进程级开关符合运维事实：日志要么是这张表的历史，要么不是，这不是每个调用点各自决定的。

两条后果是裁决的一部分，不是副作用：

- **sidecar 从 `with_changelog` 里搬出来，装配时无条件写**，内容来自 `CollectionSchema::of::<K, R>()`。全局捕获的表如果声明从没登记过，写出的段没有任何读者能解码。
- **排除清单按 ns 给**，因为在边界上拿不到名字。按表名排除需要一张运行期的 name↔ns 注册表，而 store 契约刻意没有它。

### 3. 先有 baseline，再信任第一条增量

启动时、捕获开启的前提下：某表若没有 baseline 段，就产一个——扫描该表的**真相半边**，把帧写进一个 kind 为 baseline 的段。原型已经存在，就是 `Collection::reconcile`（`document.rs:1443`，行 → 日志自己的 PUT 帧）；要扩的是覆盖面：不止 slot 0，而是整个真相集——动态段 `0x01`、字段名与谓词词表 `0x02`–`0x05`、每个分类词表的两个方向（`0x1nnn`/`0x2nnn`）。

这一步有两个结构性前提：

- **它只能在持有 store 的进程里跑。** KV 存储单写者，另一个进程打不开引擎目录。所以 baseline 是一次启动成本——每表一次有界全扫，只此一次，不是常驻税——这也正是本 ADR 不让导出依赖外部工具的原因。
- **中途开启的日志依然完整。** 没有 baseline，捕获之前写下的一切对任何消费者永远不可见；有 baseline，日志就成为迁移源，与它何时被打开无关——这才使全局开关在一个既有部署上可以安全地翻。

### 4. 日志仍是 hint，完整性靠 store 核对

本 ADR **不**把日志升格成预写记录。引擎提交返回 `Ok` 之前不追加任何东西（ADR-0045 §7，不变），热路径上没有 fsync，提交与追加之间崩溃仍然丢尾。迁移的含义因此要说一次，别让人在切换当天才发现：

**迁移以对仍存活的旧库做一次对账扫描收尾。** 回放覆盖大头；旧库是日志漏掉那部分的权威，包括删除——行扫描看不见删除（`reconcile` 修不了删除，它自己也这么说）。切换顺序把窗口压短：旧实例停止接受写入、发出封存段、一次对账范围扫描补上缺口的尾巴，然后切流量。

为什么不是反过来——先写日志再写表、每次写一次 fsync、日志当恢复权威？因为这里的每个引擎本来就有自己的 journal（fjall、redb、slatedb），在它上面再压一层是双记账，代价是每次写多一道延迟；也因为“至多一次 + 库侧核对”是对一个可能被撕裂的文件诚实的两种方式里更便宜的那一种。名字叫 WAL 会同时承诺“确认前已持久”和“可从中恢复”，而这份文件两样都没有。

### 5. replay 是迁移消费者，Parquet 是分析消费者

replay 按序读 baseline + 各段，并**通过新构建的写路径**应用它们：用 op 写下时那个版本的 sidecar 解码，按新声明重新编码，提交。派生状态（索引、reduce、前导面、图面、向量行）由写路径重建，永不复制。词表 id 必须**经 label 面重新解析**（`id → label → 新 id`），绝不复制，因为 id 是按各库首次写入顺序分配的（ADR-0032），而 label 才是事实。

分工是彻底的：**replay 是唯一能表达删除的消费者**，所以迁移走 replay；Parquet 保留它的本职——喂一个历史即追加、压实归 sink 的湖。于是形状变更完全不经过 Parquet。

### 6. 升级流程，完整形态

新构建作为第二个进程、配自己的 store 起来。它回放 baseline + 各段直到追平，然后发信号。协调者切流量；旧实例把尾巴抽进日志并优雅关闭；新实例应用这段尾巴（秒级），然后开始服务——写自己的 store，并追加到**同一份按表的日志**。日志属于表而不是某个 store 实例，所以无论它喂过几代 store，历史都是一条连续的流。

交接这一步不能含糊，因为它守的是单写者。**hook 返回零的那一刻旧写者还能提交，就是脑裂**，而进程状态无法排除这一点：`Changelog::drop` 是尽力而为的抽干、失败无从上报，被杀死的进程留下一个 `.partial`，而读端按契约忽略它。所以围栏的证据必须是**和分段同一个介质上的产物**，写权必须是一条**比任何单个进程活得久**的事实。

那个产物是每表一个文件，`<dir>/owner`，写法和封盘一样——临时文件、fsync、rename。内容是 `holder`、`epoch`、`state` 与位置，状态取 `writing`、`draining`、`handed-over`。写者只在状态是 `writing`、持有者是自己、租约新鲜时才允许提交；租约靠定时器续，**续不上就停写**，因为目录和对象前缀本身不提供互斥，后端给不出锁的时候，自我围栏是唯一正确的姿势。提交路径读内存里的闸门、不读文件：轮询是每几百毫秒一次 `stat`（或一次 HEAD），不在写路径上。

这个文件是文本，一行一个 `键 值`，不认识的键忽略——因为它的读者按构造就是另一个构建（旧版本写、新版本在升级时读），前向兼容必须免费，而 `cat owner` 必须能在凌晨三点看懂。状态是一个词（`writing`、`draining`、`handed-over`），不是一句话；位置写段文件名而不是序号，于是「名字怎么推出来」留在代码里，不必在协议里复述一遍。这个构建读不懂的声明是错误，绝不是默认值：猜，正是这个文件要防的那种脑裂。续租是「读回来确认再写回去」，只有后端支持条件写时才精确原子；不支持时由接手方重试，直到看见 `handed-over` 或放弃——损失是多一轮，不是第二个写者。

于是切换就是三次写入加一次断言。新实例追平后写 `draining`，`epoch + 1`；旧实例在下次刷新时看到，拒绝新工作，让在飞的提交落盘，`seal_last()`，然后写 `handed-over`，带上最后一段和它的位置；新实例看到 `handed-over`，再回放一轮，**只有当自己的位置等于被交出的那个位置时才能改写 `writing`**。不相等就再回放，还不相等就放弃切换、保持只读。

交接里那个位置就是最后一段封好的段文件，全部就这么简单——因为日志住在 POSIX 文件系统上：一块盘、一个 bind mount、一个 NFS 挂载。只有在那儿，封盘**才是**一次原子 rename，尾巴能在宣告交接之前 fsync 落地，两个进程能同时读同一个文件。对象存储不是日志（没有 rename、没有 fsync），所以 S3 不是 changelog 的位置；离开这台机器的东西以 Delta 表的形式离开（ADR-0058），它一个格式同时承担备份、恢复与分析，而且任何没听说过 okm 的工具都能读。远端文件协议（FTP、WebDAV）也不是位置：两者都把原子性交给实现，围栏就得按服务器逐个重讲一遍。需要跨主机共享日志的部署去挂文件系统，需要副本的部署去导出。

只增不减的日志等于永远在回放，所以压缩是一等动词，不是什么留给宿主的杂活。`ChangelogStore::compact(keep)` 逐表写一份 baseline——关掉写者、用捕获同一个过滤器扫一遍 truth half、封盘——然后删掉段号低于**这份 baseline 第一个文件**的所有段，只把其中最新的 `keep` 个留作给人看的窗口。baseline 是 checkpoint，所以它覆盖的东西没丢：回放应用最新的 baseline 及其之上的一切（ADR-0056 §3），而下面的那些段正是这份快照已经包含的历史。`keep = 0` 是这套机制用途的默认形态——历史住在 Delta 导出里，那儿的版本不归这里剪。
压缩是自动的，策略和其他参数一样挂在同一个参数对象上（`ChangelogConfig.compact: Option<CompactPolicy>`——未覆盖字节数、覆盖点的年龄、以及留几段）。触发点只有**轮转**：那里写者本来就在边界上、本来就付了 fsync、本来就是有权写的那个进程；检查在罕见事件上花一次目录读取，绝不是每次提交一次 stat。它在时间上是刻意惰性的——core 没有时钟也没有调度器（ADR-0045 §7），所以安静的库在下一次写时压缩，或者由宿主自己调那个动词。它也**不能**是独立进程：baseline 的扫描必须和写者的段号一致，一个在活写者旁边跑扫描器可能漏掉落进编号低于新 baseline 的段里的一行——不可恢复，而且没有任何断言会发现。第二个进程只能压缩没人正在写的东西，那它是维修工具，不是排程。

两条护栏，都关于声明。压缩只对有权写的那位持有者发生，且交接进行中绝不发生：持有者报出的位置在继任者到达时必须还在，而在它脚下被剪掉的段是一个永远完不成的切换。压缩删的是**日志**的历史，从不是库的状态。

也没有第二份段副本要维持一致。磁盘上的日志就是变更的记录；离开这台机器的东西以 Delta 表离开，把内部格式另存一份，等于留一个谁也恢复不了的备份，外加一件要保持一致的事。

读方一概不需要这套。封好的段不可变，回放可以在活写者旁边跑任意久；这个文件只回答两个问题——我能不能写、上一个写者停在哪。至于什么触发切换——信号、`kubectl delete`、或者应用自己暴露的 drain 路由——是部署层的选择，唯一的契约就是上面那条：非零即中止，而零只在旧写者已被围栏之后才算数。okm 不提供控制面，也不提供这个接口；它提供那个文件，以及推动它的动词。

交接的两侧在 `okm-core` 里各是一次调用，否则每个宿主都得自己重新推导这个顺序：`ChangelogStore::drain_and_hand_over` 封掉所有打开的表、等它等得到的副本、为每一份请求它让位的声明写下位置；`ChangelogStore::take_over` 逐表判定角色、发出请求、等待、按字节把日志应用到手交出来的位置、然后才拿声明——这个顺序本身就是安全性论证。捕获本身是一个参数，不是 okm 去读的配置文件：一个位置（`Local(path)`）或者 `Off`，`Off` 让装配保持一致、每次提交只花一个分支、什么都不打开、什么都不写。

布局变更会轮转分段并启用新的 sidecar 版本（`schema-v<N>.json`，ADR-0042），于是一份日志能承载多个纪元，回放按每个 op 写下时的版本读它。两个构建仍然永不共用一个 store：单写者是整个形态赖以成立的不变量，也是“旧的抽干、新的应用”能被定义清楚的原因。

### 7. 容器自我描述

今天的 segment 是裸记录流（`[u32 BE len][OpFrame]`），读它需要的一切都在目录名（header hex）和旁边的 sidecar 里。这正是它离开生产者之后不可用的原因，而离开生产者可用恰恰是文件迁移通路的全部意义。格式版本 2 增加：

```text
header  fmt u8 | kind u8 (delta=1, baseline=2) | layout_version u8 | hdr_len u8
        header | name_len u16 BE | name | schema 指纹 [16]
body    既有记录流：[u32 BE len][OpFrame] …
footer  body_len u64 BE | records u64 BE | ordinal u64 BE | crc32 u32 BE
```

- **头在打开时写，尾在封存时写。** 改名就是提交，所以紧挨着它写下的尾与文件一起原子。
- **`name` 与 `ns` 让表的身份跟着走。** 名字来自 `#[ok_name]` 的 `Document::TABLE_NAME`（ADR-0034），并成为 `CollectionSchema` 的一个字段——因为目录名是 header 的十六进制，而湖里的表需要一个名字。
- **指纹把字节钉到它的声明上**：读者核对找到的 sidecar 就是这份文件写下时用的那份，而不是相信目录。
- **序号（今天只在文件名里）与校验和让副本可信**：缺号变得可发现，而不是被 `> watermark` 静默跳过；短传被拒绝，而不是回放一半。
- **没有标记，也不留兼容。** 头尾都没有 ASCII magic：文件以格式字节开头、以 28 字节 footer 收尾，格式 1 的段不再读。标记原本有两个职责——区分 v1/v2，以及确认尾部那一块确实是 footer；第一个按决定取消，第二个由 `body_len` 对文件长度加校验和完成，标记改不动它。
- **段里不嵌 schema 体。** sidecar 按布局版本各一份，是声明的载体；每段嵌一份是同一份声明的第二个真相源，还会让文件的原子单位错位。原子单位是**表目录**：段 + sidecar，这既是复制要搬的东西，也是 `drain` 现在就拿的东西。

### 8. 工作区里的这一刀

- **核心留字节，并且收下抽干。** 段帧迭代、真相半边过滤（改为从 `SlotMap` 的边界推导，而不是手维护的清单——`declared_index_base` / `declared_reduce_base` / `declared_lead_base` 与两组词表已经说明了某个 slot 属于哪边）、窗口合并、水位，以及把一个窗口就地交出去的这一步，都属于产出这些文件的机制。`okm-drain` 不再是一个独立 crate：窗口合并下沉进核心，格式那半边搬出去。
- **文档解码器跟着一起下沉。** `okm_dynamic::decode_payload` 是对 `CollectionSchema`（本来就是 core 的类型）的纯函数，返回 core `DynamicValue` 的 map。它待在 core 之上是历史原因（它写在 planner 旁边），不是结构原因。把 `decode.rs` 移进 core，才让「抽干是核心功能」从名义变成事实，也去掉抽干唯一的向上依赖；`okm-dynamic` 继续 re-export 这个名字，现有调用点一个都不改。
- **搬出去的只有格式**：schema 驱动的 Arrow 列构建器（`okm_dynamic::arrow`）、Parquet、表格式日志、**typed 桥**（`to_record_batch`、图的边表）与**快照导出**（`parquet_io`）。core 不能向上依赖，所以容不下它们（ADR-0045 对 Arrow 批次构建器说过同一件事），而它们每一个都是段的一种投影，不是生产段的一部分。**回放不搬出去**：应用一个段——顺序、行解码、词表重新 intern、删除意味着什么——是机制，所以它和窗口合并并排住在 core（`okm_core::changelog::replay`）；core 唯一点不出名字的那样东西（schema 驱动的目标）通过 `ReplayTarget` trait 进来，由 `okm-dynamic` 为 `DynamicCollection` 实现。驱动它的那个二进制（`okm-parquet replay`）是这个 API 的 CLI，不是它的主人。不能向上依赖的 core 装不下它们（ADR-0045 对 Arrow 批次构建器说过同一件事），而它们没有一个是机制——每一个都是段的一个投影。
- **`okm-parquet` 是独立命令行工具，与应用没有链接。** 它读表目录（段 + sidecar），写 Parquet + manifest，再接 Iceberg 元数据。「应用必须给导出器提供一个接口」这个要求，随着需要它的 store 扫描导出一起消失：湖里的表名取自段头，列取自 sidecar。Iceberg 走同一条路，只是再往外一层投影。
- **replay 需要的是一个文件，不是一个接口。** 目标声明以新构建导出的 `CollectionSchema` JSON 的形式旅行，一次性；baseline、段、序号、sidecar 都在盘上。所以这个工具对 `parquet` 是全独立，对 `replay` 是「加一个文件」的独立。
- **水位变成 per `(consumer, table)`。** 每 consumer 一个文件、而段编号是每表独立的，会让多表抽干静默跳过所有落后于最高位的表（`okm-drain/src/lib.rs:182`）。

### 9. 本 ADR 不裁决的：S3、slatedb、多写、其它引擎

记下来是因为被问到了，而且它们约束下一步：

- **S3 进核心也可以，做成 feature。** 依赖上的顾虑不成立：`object_store` 与 `tokio` 本来就是 `okm-core` 的可选依赖（`Cargo.toml`，给 slatedb 后端用），所以一个 S3 sink 不会往依赖树里加 crate——它加的是一个 feature 和一条发运路径。必须守住的是：上传绝不在提交里面（封存段交给工作队列，写路径仍是一次 memcpy）、store 契约保持同步、feature 默认关闭。要发运的单位是表目录（封存段 + sidecar + baseline）；客户端是 `object_store`——S3 / GCS / Azure / 本地——不是 `aws-sdk-s3`。
- **`slatedb` 仍是引擎选项之一。** 从日志重建一个库是启动成本；住在对象存储上的库是另一种能力（不要本地盘、启动后低延迟写入）。日志 + baseline 放进 S3 让**系统**可恢复，并不会让任何引擎多余。
- **多写是被拒掉的，不是缺的。** 两个构建永不共用一个 store（ADR-0042 §7）；实现并发写者就要给契约加协调（租约、CAS、冲突解决），而契约的简单正是产品。需要多写的部署，是另一套系统。
- **任何满足 store 契约的引擎都够格**——有序 `scan_range` 加原子批。`surrealkv` 在能力上是候选；rocksdb 因构建成本被拒，不是因能力。

## 备选

- **拿 Parquet 绕一圈当迁移通路。** 拒：sink 拒收删除，经由它的迁移会静默丢删除；而经由列式文件的一圈，是对一个我们已经以“字节 + sidecar”拥有的形状做有损的重新声明。
- **原样回放段里的 op 字节**（不重解码/重编码）。拒：它把派生条目写回派生槽，形状变更会留下旧面和旧 reduce 总额，词表 id 还会跨库搬运，而它在另一个库里什么都不代表。
- **真正的 WAL：提交前追加、fsync、从日志重建库。** 拒，理由如上——在本来就有 journal 的引擎上面双记账，加每写一次延迟税，换一个我们并不需要的恢复权威。
- **保留按 collection 的捕获。** 拒：它按装配点选择开启，完整性取决于应用是否记得；还要为调用方自建批配一份书面纪律。
- **每段内嵌 schema。** 拒：一份声明的第二个真相源，且对读者毫无收益的体积。

## 后果

- 日志成为留存下来的东西：库可替换，目录就是历史。导出、迁移、湖加载读同一种格式。
- 热路径不变：一次 Option 检查、一次 memcpy、无 fsync。捕获对整个 store 要么开要么不开，排除清单是一行配置。
- 启动多一次有界扫描（某表第一次被捕获时），之后不再付。
- 两个失败窗口从此刻起明确并计过价：提交与追加之间崩溃（切换时对账扫描关掉），行扫描修不了的删除（把载着它的那个封存段发运过去关掉）。
- `okm-core` 留下字节、收下抽干（窗口合并与文档解码器）、交出文件格式；Parquet 与 replay 归一个独立二进制。
- 表名不再是导出路径的编译期秘密：它跟着段走。
- 交接要付一份租约：每个写者一个轮询循环加一道自我围栏，只有跑两个写者时才付。单进程部署根本不会打开这个文件。
