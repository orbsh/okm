# ADR-0064：SurrealKV 暂不作为后端

日期：2026-11-12
状态：暂缓 2026-11-12

**依赖：** ADR-0056（segment 就是迁移通路——那里把 `surrealkv` 记成能力上够格的引擎）、ADR-0059（异步面自成一个 crate——任何不在 core 里的引擎都要住的边界）、ADR-0028（浏览器内的 `VirtualStorage` 家族，其 §Withdrawal 已经了结浏览器那一半）

## 1. 背景

SurrealKV 是 SurrealDB 自研的嵌入式键值引擎：一棵 LSM 树——memtable、WAL、SSTable、compaction——索引是带版本的，所以每次写都落在一个版本之下，读方在提交进行中的同时看到一致的快照。它的表面刻意很窄：一个路径一棵 `Tree`，`begin` / `set` / `get` / `range`，提交是异步的，而点读与迭代是同步的。它还能跑在浏览器里（专属 Web Worker 上放 OPFS）、自带引擎内加密，Apache-2.0。

它一天之内被提了两次，来自一份外部提案（2026-11-10）：替换 okm 在浏览器里的 localStorage 引擎，以及更大的那一半——把它当作「那个」存储引擎。浏览器那一半已经关了，而且关的理由与它无关：localStorage 后端被撤除，是因为它唯一的消费者只存两个 UI 键，不是因为 SurrealKV 不好（ADR-0028 §Withdrawal）。桌面/服务端这一问，就是本 ADR。

它之所以有吸引力，恰恰是 okm 已经带的三个引擎分摊掉的那几件事。fjall 是写重的嵌入式 LSM；redb 是读确定的那个（mmap 上的 COW B-tree，没有恢复过程）；slatedb 是对象存储的那个，异步，住在 `okm-async` 后面。SurrealKV 是第四棵 LSM，区别性能力是引擎级 MVCC 快照、同步读之下的异步提交流水线、引擎内加密，以及同一个引擎也能跑在浏览器里——三者一个都不提供。

## 2. 在本机实测

链接成本，`rustc 1.99.1`，`lto = "thin"`，`codegen-units = 1`，二进制 `strip -s`。每个 bin 做同样的活（打开目录、插入 1000 个定宽键、全区间扫描、点读一个键），所以一行减去 baseline 就是被链接并且真正走到的那个引擎。

| bin | 引擎 | stripped | 相对 baseline | 传递依赖（含自身） |
|---|---|---|---|---|
| `bare` | 无 | 322,256 B（0.31 MB） | — | — |
| `tokb` | 仅 tokio runtime | 506,184 B（0.48 MB） | +0.18 MB | — |
| `rdb` | redb 4.5.0 | 1,264,376 B（1.21 MB） | +0.90 MB | 2 |
| `fj` | fjall 3.1.13 | 1,605,904 B（1.53 MB） | +1.22 MB | 74 |
| `skvt` | surrealkv 1.3.0 + tokio | 3,324,048 B（3.17 MB） | +2.86 MB | 150 |

也就是 fjall 的 2.3×、redb 的 3.2×；这 1.64 MB 的差额大部分是 surrealkv 自己的 LSM / vLog / 加密代码，而不是它需要的运行时。对一个服务二进制来说这是重量，不是否决。

决定落点的约束：`surrealkv` 把提交流水线 spawn 到环境运行时上，而不是在调用线程里内联跑完。用 `futures::executor::block_on` 或 `pollster::block_on` 驱动时，`tx.commit()` 直接 panic：`there is no reactor running, must be called from the context of a Tokio 1.x runtime`（`surrealkv-1.3.0/src/task.rs:165`）；换成 `#[tokio::main]`，同一个程序写 1000 个键、全扫、点读全部正确。于是没有同步的 `VirtualStorage` 实现（那个 trait 返回时必须已经提交），也不可能进 `okm-core`——它的依赖闭包由 CI 拒绝 `tokio`（ADR-0059）。唯一诚实的落点是 `okm-async`，与 `SlatedbStore` 并列，实现 `VirtualStorageAsync`——正是 ADR-0059 给「住在 core 之外的引擎」定好的形状。

吞吐与内存，三个引擎同一套 harness：50 万条 16 字节键、100 字节值，不压缩，每次提交 fsync，fjall 在判定其稳定状态之前强制把 memtable 刷成 SST，三次取中位数，每个引擎一个进程。

| 指标 | fjall 3.1.13 | redb 4.5.0 | surrealkv 1.3.0 |
|---|---|---|---|
| 装载 50 万，每 1k fsync | 703 ms | **436 ms** | 1099 ms |
| 全扫 50 万 | 103 ms | **18 ms** | 44 ms |
| 1 万次短区间扫描 × 100 行 | 198 ms | **41 ms** | 113 ms |
| 20 万次随机点读（热） | 475k ops/s | 1.24M ops/s | **1.51M ops/s** |
| 重开一个已稳定的库 | 1.7 ms | 0.3 ms | 1.4 ms |
| 重开后的 20 万次点读 | 35k ops/s | **1.05M ops/s** | 174k ops/s |
| 稳定后占盘 | 58.1 MB | 128.5 MB | 59.1 MB |
| 峰值 RSS | 115 MB | 116 MB | 117 MB |
| 链接成本（见上表） | +1.22 MB | **+0.90 MB** | +2.86 MB |
| 需要的运行时 | 无 | 无 | **Tokio** |

surrealkv 唯一的领先是热点读，比 redb 快 1.2×，代价是 2 MB 二进制、多 60 个 crate、外加一个运行时。当初为它撑腰的「读重槽位」早有人占着，而且占得更便宜：redb 全扫快 2.4×、短区间扫描快 2.8×、重启后的点读快 6×（COW B-tree 不需要恢复，页通过 mmap 到达时已经是热的；LSM 则要在冷块缓存上逐层查找）。redb 也是这里最快的写者；fjall 与 surrealkv 的写差距是 fsync 管道而不是吞吐——每 1 万次写提交一次时两者持平（486 对 526 ms），而 okm 是按段提交的，本来就是大批。

必须写清的边界条件：单机（Zen 5）、单进程、不压缩、100 字节值、每阶段只测一种读风格、redb 与 surrealkv 按每操作一个事务来用。surrealkv 的数字随提交粒度移动——同样是这份数据，每 1 万次提交时它的热点读阶段掉到 193k ops/s，RSS 涨到 140 MB。

## 3. 裁决

目前不集成 SurrealKV。不加依赖、不加 feature flag、不写适配器：存在的 flag 就是必须被实现、被测试、被一直保持能编译的 flag。它仍然是 ADR-0056 记下的样子——能力上够格的引擎——而不针对这份资格动手。

## 4. 理由

**版本历史不是引擎的活。** okm 的版本语义住在 changelog 段里（ADR-0056）；store 只被要求给出当前字节，别的什么都不问。快照 API 不在 okm 任何一个表面上，也没有消费者要过，所以引擎级 MVCC 是没人会花的能力。

**加密属于卷。** okm 的模型里没有任何东西要引擎持有密钥；需要在静态时加密的部署加的是卷。这是唯一无法用现有东西拼出来的能力，所以它也是回到这个决定的最短路径（见下）。

**覆盖已经完整。** 嵌入式写重是 fjall，嵌入式读重是 redb，对象存储异步是 slatedb。第四个嵌入式引擎重复一个已经填满的槽位——而 §2 实测显示，这个重复品恰恰在能为它撑腰的那些读上落后。

**吞吐不是瓶颈。** okm 的工作单位是一次文档编码加一次段追加；一个引擎在千键插入上快一倍，移动不了任何用户看得见的东西。这个仓里，store 级数字值得行动的时刻，都是某个具体负载被实测过的时刻，从不是一份基准表。

## 5. 后果

后端矩阵仍是 fjall / redb / slatedb，异步面仍是 `SlatedbStore` 加 `WireClient`。不加 crate、不加 feature、不加 CI 步骤。

以下三件事无论后面怎样都保持关闭：

- **不做 `block_on` 驱动的 `SurrealKV` 同步外观。** 今天它不工作（见 §2）；就算哪天开始工作了，它也等于把一个运行时藏进 `okm-core`，而那条边界正是 ADR-0059 存在的理由。
- **不为让浏览器故事与服务端「一致」而加它。** 浏览器的约束是 Worker 加 OPFS，是另一种程序形态，而当初引出这件事的那个面板只存两个键。
- **不按 crate 热度或厂商的表格来判它。** 链接成本与传递依赖是使用这个库的人真付的账；厂商的数字描述的是另一种负载下的裸机点读。

## 6. 什么会重新打开它

以下任意一条，带着实测：

1. **多进程或多实例的读方需要在另一个进程写入时拿到快照。** 这是整个栈里别的组件都提供不了、changelog 水位线也合成不出来的唯一能力。
2. **静态加密必须活在引擎里**——平台不肯加密卷，但肯让应用持有密钥。
3. **在真实负载里实测到 fjall 的写路径就是天花板**，数字来自本仓自己的 bench。
4. **原生与浏览器共用同一个引擎。** 如果哪个浏览器数据集真的到了需要一个真引擎的程度（ADR-0028 §Withdrawal 写明什么时候那不再荒唐），两端用同一个引擎比任何一边的基准都值钱。

第一条先是 ADR-0056 的形状问题，然后才是引擎问题：快照 API 是一个新表面，而无论换哪个引擎，它都得向 store 契约提出。

## 7. 这是推迟，不是否决这个设计

本文没有一句话说这个引擎不好。它的设计正是它成为 ADR-0056 里唯一被记下的候选的原因，它的提交/读分离正是它在 `VirtualStorageAsync` 后面好用的原因，它的浏览器故事是四个引擎里唯一对那个问题的真回答。这份记录争论的是成本与已经填满的槽位：fjall 2.3× 的链接成本与多 60 个 crate，是「在某个负载真的需要只有它才有的东西之前不要加它」的理由，而不是拒绝它的理由。

所以这个决定是带日期的，并按上面四条触发条件可复审；实测数字留在这份 ADR 里，让下一轮从这里开始，而不是从厂商的表格开始。
