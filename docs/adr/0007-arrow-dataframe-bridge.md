# ADR-0007: DataFrame bridge — Arrow RecordBatch as the single contact surface

Date: 2026-09-07
Status: Implemented (2026-09-11: to_record_batch eager bridge, parquet_io export/import; lazy pushdown load-gated)

## Context

OKM's query surface is the KV extreme: access paths are fixed at key-design
time, with no optimizer and no query language. Analysis loads (multi-dimension
aggregation, ad-hoc filtering over materialized rows) do not fit that surface —
they are exactly what DataFrame semantics (composable method chains, in-process
lazy graphs) exist for. The two are load-sharing, not competing layers: KV
provides persistence + row-level access (OLTP), the DataFrame provides the
in-memory analysis layer. The missing piece is the interface between them.

Polars is the chosen consumer on the DataFrame side (pure Rust, Arrow-native,
lazy optimization). Apache Arrow is the natural contact surface for three
reasons: it is Polars' native memory format, the physical basis of Parquet
(the snapshot path), and the closest columnar analog of OKM's pointer-slicing
decode (fixed offsets, zero parsing). One format aligns all three; no
intermediate conversion tax appears anywhere.

## Decision

**The bridge is a read path only, built on Arrow `RecordBatch`.** `Table`
gains the ability to stream its rows as `RecordBatch`es; Polars consumes them
directly. Concretely, two depths, phased:

### Phase 1 — eager export: `Table::to_record_batches()` / `to_polars()`

- Scan the primary segment (slot 0) via the existing `KvEngine` scan surface;
  decode each entry (key fields + TLV payload) and emit columns per batch
  (target ~8192 rows/`RecordBatch`).
- **Schema is generated by `RowEncode`**, not inferred: field names from the
  row declaration, type mapping fixed (`u32`→`UInt32`, `u64`→`UInt64`,
  `[u8; N]`→`Binary`, wrappers per their read path — `Enum<T>` decodes as its
  integer width, `Offset<T>`/`Delta<T>`/`Quant<T>` as their resolved logical
  values, `Reverse<T>` inverted before emission). This continues "code as
  DDL": one struct is the single source for key encoding, payload encoding,
  index slots, snapshot columns, and Arrow schema — five destinations, zero
  drift surface.
- The row→columnar pass is O(N) and is the one unavoidable layout conversion
  (row store → column store); it is paid per query, which is exactly the
  trade the eager tier makes for maximum freshness.
- `polars` is an optional Cargo feature (off by default); the core returns
  `RecordBatch`es with only `arrow-*` deps, so the bridge adds nothing to
  builds that don't ask for it.

### Phase 2 — lazy pushdown (deferred, load-gated)

A custom `LazyFrame` source letting Polars' optimizer push filters/projections
into OKM scans (predicate hits a `#[kv_index]` leftmost prefix → index scan +
fetch-back; else full segment scan). This is the full composability payoff —
method-chain forks/merges live in the Polars DAG while the data source keeps
embedded zero-RTT access — but it depends on `polars-plan` internals and pays
off only when analysis predicates actually hit declared index dimensions.
Deferred until the eager tier reveals the real load shape.

### Phase 3 — scale-out stays the snapshot path (already ADR-0006)

When data exceeds memory or analysis repeats on a hot path, per-query
row→column conversion stops being worthwhile: use the existing snapshot
export (rows → Parquet) and read it with `scan_parquet`. KV remains source of
truth; Parquet is a converted-once, allowed-to-be-stale analysis snapshot.
The two tiers complement: in-process bridge = pay conversion per query, buy
freshness; snapshot = pay conversion once, buy throughput.

## Boundaries

- **Read-only.** All writes go through `Table::put` — the primary-key +
  index-entries one-batch contract must not be bypassable from the DataFrame
  side. Analysis results that need to persist back are explicit new row types
  written through the normal write path. This preserves the KV-side as sole
  source of truth and prevents dual-write drift.
- **Single-machine ceiling is accepted, not fought.** The bridge is for
  in-process, medium-scale data (the KV + DF tier of the composition ladder).
  Beyond that, the answer is the snapshot/lakehouse path, not distributed
  pushdown inside OKM — OKM does not grow a Spark.
- **Indexes are not exported through the bridge** (same as snapshots): derived
  state, rebuilt deterministically; the DataFrame sees rows only.

## Consequences

- New module `okm-core/src/arrow_bridge.rs` (or `arrow_backend.rs`, mirroring the
  engine backend naming) behind an `arrow` feature; `to_polars()` behind the
  additional `polars` feature.
- **Export is feature-gated**: the bridge and its dependencies (`arrow-*`,
  `polars`) are optional features, off by default — builds that never touch
  the analysis path (embedded OLTP, CI, embedded devices) pay no compile time
  or binary size for it; export methods on `Table` are only generated when
  the feature is active, leaving the core API surface untouched.
- **ns ID restored to table name**: RecordBatch columns carry no ns bytes,
  but a batch must know its source table — the exporter reverses the key's
  `[ns 2B]` header through the ns dictionary (ADR-0002, dictionary lives in
  code) into the descriptive table name, attached as batch metadata (table
  name / column ownership). Same discipline as ADR-0006's self-describing
  snapshots: the binary ns header never leaks to consumers; the reverse
  mapping is owned by the exporter.
- `RowEncode` gains one more generated artifact: an Arrow `Schema` + per-field
  column builders, derived from the same field list as `PAYLOAD_FIELDS`.
  Macro complexity stays bounded: one item, one field list, one more output.
- Variable-length payload fields (String, still pending per PLAN Phase 2)
  map naturally to Arrow `Utf8` — the bridge does not block on them, and the
  mapping slots in when they land.
- Wiki documentation (query-language-design.md, KV + DF section) gains one
  sentence: the contact surface is Arrow RecordBatch; Parquet snapshot is the
  scale-out exit. No design exposition there — this ADR owns it.
