# 0044 — 键与行是两处独立的声明

> **语言：** [English](0044-keys-and-rows-are-separate-declarations.md)（主） · [中文](0044-keys-and-rows-are-separate-declarations.zh-CN.md)

**状态：** Accepted（2026-10-28）。落在声明面（`Collection<S, K, R>` 且
`R::Key = K`、`#[ok_ref]`、`Document::collection`），并由
`okm-core/tests/key_row_split_test.rs` 锁住。
**日期：** 2026-10-28

## 背景

每张表都有两半，职责不同。**键**是地址：定宽、有序字节，一次组合，按前缀扫描。**行**是值：
声明载荷、动态段、索引、嵌入。代码把它们声明成两个独立的类型——一个 `#[derive(KeyEncode)]`
结构体，一个用 `#[ok_ref]` 点出自己键类型的 `#[derive(DocumentEncode)]` 结构体——由
`Collection<S, K, R>` 同时携带，`R::Key = K` 在编译期钉住。

有两个后果一直是被逐案论证的，而不是一次说清：

- **副表**（ADR-0036：「一张以父表自己的键类型为键类型的第二张表」）。它能成立，只因为键类型是
  可以原样复用的独立声明——而这条原因从来没写下来。
- **两半里出现同一个名字。** 存储形状其实已经定了：分类器只走载荷声明，键的字节从不进 map。但
  「这两个同名字段互不相关」这件事没有写在任何地方，读起来像个该被防住的意外。

另有两种在别处通用的做法：把键嵌进行里（一个结构体，行自带地址），或让 ns 隐含键（根本没有键类型）。

## 裁决

**1. 两处声明，一处绑定。** 键类型独立存在——声明顺序、大端、定宽、自带一份 `FIELDS` 名字表。
行类型只是**指名**它（`#[ok_ref(K)]` → `Document::Key = K`），自身不含任何键字节。
`Collection<S, K, R>` 同时携带两者；`Document::collection(store)` 从 `R` 读出 `K`，调用点
因此不必重述键类型（ADR-0003）。

**2. 一个键类型可以给多张表当键；一张表恰好只有一个键类型。** 副表就是以父表键类型为键的第二
个行类型，住自己的 ns。键 payload 按构造就是逐字节相同的——两个主键只在 ns 字节上不同——正是这
一点让 ADR-0036 的副表成为「同一把键，多一次点读」，而不是第二套键空间。

**3. 同一个名字可以同时出现在两半，两个字段互不相关。** 不去重、不报错、读路径上也不比较：
- 键的字节从不进入整文档表面返回的那个 map（`fetch` = 载荷字段，再接动态段）；
- 分类器是**载荷声明**，所以一个名字只要是已声明的载荷字段就是一次行写入，键在这项判断里不起
  任何作用（ADR-0012）；
- 载荷里的副本与键不一致不叫损坏：键是地址，载荷字段是数据。

**4. 没人对账，也不该对账。** 把键字段反规范化进行内，是正当的建模选择——为了索引，或为了不必
从键重新推导就能读到它。在读路径上比对两者，换不来地址本来就已经保证的东西。

## 与 SQL 的分界——切分落在键上

关系引擎是**行优先**的。行是单位，身份由引擎掌管；一个过大的值在引擎**内部**走 off-row（溢出页、
TOAST），用行自己的 id 加一个追加在后面的分块序号来定位。schema 永远不会知道这件事发生过：
在建模者眼里是一张表，在引擎眼里是两块物理区域。

okm 是**键优先**的。一张表**就是**一段键空间——没有键就没有行——所以同样的切分是一次建模行为
（ADR-0036），而且它落在地址上，不落在引擎里：副表的 ns 变成主键的**前导**字节，键 payload
在后面逐字节不变。

和 off-row 是同一个想法，只是分片段挪到了键的另一端：

```text
SQL / off-row    [ 行 id .................. ][ 块 0, 1, 2, … ]    切分追加在后
okm / 副表 ns    [ ns 2B ][ slot 1B ][ 键 payload …………… ]         切分前置于首
```

这个逆转带来的一切，都在建模时就看得见：

- **切分是声明，不是存储开关。** 它有自己的 ns、自己的面、自己的提交，可以当作一张表来查询；
  关系库里那一版是隐形的，除了父行本身，没有任何东西能查它。
- **两半保持同一串键字节。** 键 payload 不变，所以父表的前缀结构仍然给副表排序：按 `org_id`
  在副表上扫描，读到的是和父表同一段物理区间。
- **没有任何东西把它们 join 回来。** 想要「行 + 副表值」的读者做两次点读（ADR-0036）。没有哪个
  执行计划能把它悄悄变成 join——组合是应用自己的事。
- **引擎从不替你做决定。** 没有「超过阈值就自动溢出」这回事，所以「什么时候切」是一次建模决策
  （MODELING「一个值大到放不进行里」），不是页布局的意外。

这就是这里 KV 与关系库差别的核心：SQL 把键藏在行里，okm 把键——因而把表、把分片——放在地址的
最前面，并把它交给建模者。

## 被否决的做法

**把键嵌进行里。** 一个结构体看起来更省：不用第二个类型、不用 `#[ok_ref]`。但行从此自带地址，
于是每次写都有两个真相来源，每张副表都要存一份副本，而且键的宽度变成载荷的属性——可键必须定宽、
载荷却允许以 `Str` 收尾。副表形态更是直接死掉：第二张表必须重述父表的键字段，还可能与之在字节
上跑偏。

**由 ns 隐含键。** 省掉整个类型，让键的形状成为约定。代价是键之所以有用的结构全没了：没有前缀
维度（`org_id` → `user_id`）、没有可在表间共用的键类型、没有编译期检查两张表是否认同一个地址，
排序规则也退化成一纸注释。

**去重或拒绝同名。** 丢掉载荷副本，等于删掉行本来想索引的数据；拒绝它，等于让反规范化的副本无法
表达。两者都是为一个零成本的碰撞向一个正当的建模选择收费。

## 后果

- `Collection<S, K, R>` 有三个参数，哪怕调用点很少把它们写出来。这就是分离的代价；要不要隐藏由
  ADR-0003 决定。
- 同名规则是编译期的沉默，不是检查。两份副本可能跑偏，对寻址无害，只有应用自己看得见。
- 键的声明顺序就是扫描顺序，行改变不了它：「按某个字段排序」是索引（ADR-0005），永远不是键。
- 副表的各个面住在自己的 ns 里。共用键从不共用存储，两张表各自独立提交。
