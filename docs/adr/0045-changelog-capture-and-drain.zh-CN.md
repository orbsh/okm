# 0045 — 变更日志：在提交边界捕获，在进程外抽干

> **语言：** [English](0045-changelog-capture-and-drain.md)（主） · [中文](0045-changelog-capture-and-drain.zh-CN.md)

**状态：** 已接受（2026-10-28）——只定设计，未实现。
**日期：** 2026-10-28

## 背景

原始提案是：在存储层把每次写记录下来，按时间和数量双因素积累（像日志轮转那样），攒够大小就转成 Iceberg 的写入。计数和轮转是容易的那一半；代码库里有六条事实决定了这条记录能是什么、能住在哪里。

- **存储边界只认字节。** `VirtualStorage` 只有 `put`/`get`/`del`/`scan`/`commit_batch`；槽位语义在 `model/index.rs`，把 payload 读回来还需要声明。坐在那个边界上的捕获器看到的是物理 op，不是行。
- **一次语义写是一个 `Batch`，而 batch 里不只是行**：主键条目、每个声明面一条、嵌入子文档、reduce 的 fold/unfold、词表增长。索引面、reduce 面、junction 面都是派生状态，导出契约本来就把它们排除在外（PLAN Phase 4）。
- **subscribe 的 sink 承载不了它。** 发射按契约是 best-effort，而 `save_with_prev_into` 刻意不发射（ADR-0031 §5）——于是 `merge`、`replace`、`purge` 以及每一次跨集合的批写都会看不见。
- **`epoch` 是进程内的。** per-Collection 的 `Cell`，在 `new` 里从 0 起，每次提交后加一，重启归零（ADR-0008 §5）。它给一个进程生命期内的写排序，不能当地址。
- **键上的时间是使用方的声明。** okm 任何地方都没有隐式时间戳；键是定宽的，`KeyEncode` 拒收 `String`。所以「新于某个时点的一切」不是每张表都答得出来的问题，扫描式增量只对那些把键排成允许区间查询的表存在。
- **引擎不是队列的形状。** fjall/slatedb/redb 是 LSM 或 B-tree 存储：先追加再按键序删除，正是压缩最讨厌的访问模式；每条记录要背它不需要的每条目开销；裁剪的代价是每条已抽干记录一次删除。

## 决定

**1. 捕获点是 `Collection::commit`**——每一个语义写都经过的私有漏斗：`put`、`delete`、`merge`、`replace`、`purge`，以及 `save_with_prev_into` 的调用方。过滤在提交之前于内存里完成；追加只在 `commit_batch` 返回 `Ok` 之后发生。不是存储边界（它分不清行和索引条目），也不是 subscribe 的 sink（ADR-0031 §5）。

**2. 一次提交的一批就是一帧，用 `okm_wire::OpFrame` 编码。** 这正是远端路径已经在用的编码（对 `(key, Option<value>)` 的 `write_batch`，键值全不透明）。文件是字节流，所以写者补上编解码器刻意不带的那一样东西：一层外层长度前缀。没有第二套格式；词表增长也不需要自己的记录——它本来就是 batch 里的一个 op。

**3. 过滤是一张「排除表」，只写一处，且朝湖侧 fail-closed。** 带上——也就是导出会带的那一套：主键 `0x00`、动态段 `0x01`、字段名词汇表 `0x02`/`0x03`、谓词词汇表 `0x04`/`0x05`。丢掉：声明索引 `0x3nnn`、reduce `0x4nnn`、junction `0x5nnn`、图的四个面 `0x06`–`0x09`（`Graph::reindex` 把它们清空、从主键行重建，所以一条边就是一行，照常随行走）、向量快照 `0x0A`、表元信息 `0x0F`，以及**裸面键**——长度等于 header 加 slot 宽度的键是面级单值（词表分配游标、表自己的元信息行），任何行都不会长成那个形状。不认识的槽位也一并丢掉：一份看得见不完整的日志能靠对账重扫补回来，一个悄悄装着派生状态的湖补不回来。面是代码里分配的（ADR-0030/0033），新增一个面就是一次代码变更，这张表是那次变更的必改项——没有东西替你检查。

**4. 日志是文件，不是面，也不是第二个引擎。**
`<root>/<header 十六进制>/<nnnnnnnn>.partial`（写入中），封存时改名成 `.segment`——后缀说的是产物是什么，不是承运方式（`.log` 会被读成应用日志，这里不是那个东西）。按字节数和墙钟轮转。写在文件而不是键空间里，因为三笔成本全部反转：纯追加是 1 倍字节、没有每条目开销；回收是整段 `unlink`，而不是每条已抽干记录删一次；热键空间的压缩预算一点不被占。

**5. 地址是 `(段号, 偏移)`，所以不需要生产侧计数器。** 下一个段号等于目录里最大的名字加一；偏移就是写者本来就持有的追加位置。没有预留、没有 hi-lo 块、没有要处理的序号空洞，而一个已封存的段名本身就是「它完整了」这个耐久事实。

**6. 顺序是先提交、后追加。保证是至多一次，且绝不出现幽灵行。** 两步之间崩溃会丢尾巴；湖里于是缺了库里还存在的行，靠对账重扫补。反过来排会把库里从未接受的行塞进湖——一个和库不一致的湖，比一个落后于库的湖更糟。`sync_data = true` 把洞缩小到一次追加的边界，不改变失败类别。

**7. 核心不拥有调度，写侧也没有读者。** 没有定时器、没有 executor、没有后台线程——事件层已经守的是同一条规矩（`subscribe.rs`：sink 是调用方注册的东西）。okm 提供写者、`seal` 和段读取器。开了 changelog 的 collection 只做追加和轮转，然后就忘掉这个文件；抽干、导出窗口、对账重扫和 Iceberg 写入属于拥有它们的那个进程。

读侧从不打开引擎，它只打开一个目录。所以它可以是另一台机器上的另一个进程，由任何搬文件的东西喂（拷贝、对象存储同步、一堆 blob）：已封存的段不可变，跨边界只有两条不变量——「`.segment` 永不改变」和「水位没过它之前，什么都不删」。

**8. 水位住在消费方提交所在的地方。** 一个消费者：把窗口 W 提交到湖这个动作本身就是水位——再维护一个和它同步的文件就是第二个真相。多个消费者：各一个小文件，用原子改名替换，永不原地编辑。

**9. 自描述止于名字。** 名字能还原，是因为词表面跟着走了。类型和键布局不在日志的任何字节里：键是定宽拼接、没有字段边界，payload 是位置式的。每个布局版本往同一目录写一份 schema sidecar（`CollectionSchema::of::<K, R>()`，`schema-serde`），才是把日志变成列的东西；没有它，日志作为字节可读，作为表无用。这份 schema 自身是够用的：它带着 `key_len` 和每个 `key_fields` 的偏移与宽度、hot/cold 字段列表与 tag、`layout_version` 和槽位表——正是 typed Arrow 桥用来拼列的那一套事实。

**10. 这不是第三种事件机制。** 事件层是 `reduce` 和 `subscribe`（ADR-0008）。这里是写集里的一个条目加一个文件：没有回调、没有声明面、除了 §6 的排序之外没有任何投递承诺。

**11. 开关在装配点，不在声明面。** `Collection::with_changelog(store, config)` 是可失败的构造；`Collection::new` 保持无 I/O（ADR-0043）。derive 属性会把一个 per-instance 的策略变成破坏性的声明变更，而这个开关和引擎选择是同一类决定。不加 cargo feature：写者不需要依赖，关掉时每提交一次只多一个 `Option` 判断。

**12. 默认只记键，不记行。** 记录带 `(op, key)`；需要行的读者去读主键条目，键没了就是行没了。连 payload 一起存换来的是历史（每一版，而不只是最后一次写），代价是每次写多付一份行字节；那是另一个决定，不是一个开关。

**13. okm 产出的是窗口，不是表格式。** 这条机制的输出侧是「一批已封存的 parquet 文件 + schema sidecar + 一份说明窗口内容的清单」。三层要分清：存储产出段与 sidecar；抽干器把 N 个已封存的段组成一个窗口（窗口多大是**抽干器**的策略，因为文件目标尺寸是 sink 决定的）；适配器把窗口装进某种表格式。Iceberg、Delta、以及将来取代它们的东西都是它**上面**的适配器，在自己的 crate、自己的进程里：每一种都吃「parquet + 清单」，所以 catalog、快照日志、删除机制归适配器，不需要湖的部署一分钱也不付。不能随格式变化的是语义——一个窗口是一次追加（行按提交时的样子），当前态视图要么靠压缩（重写）要么靠能表达删除的 sink，而任何 sink 都不许通过削弱 §6 的排序来给自己换一个更便宜的捕获。否则「格式无关」会变成一个格式一个 crate，各有各的保证。

适配器向 sink 要的东西只有三样：放得下键列；有办法到达「当前态」（原生 upsert 键、delete 文件、或者周期性压缩）；放得下动态段——原生 variant 类型，或者降级成 JSON 字符串，而那份降级映射由 okm **只写一次**（Binary 走 base64，`Int`/`UInt` 保留为数字，list/map 走数组/对象）。三样里 sink 提供哪样是适配器的事；映射不是，否则每个第三方适配器都会发明自己的方言。

## 已否决

**在同一个命名空间里开一个面**（`0x0B`–`0x0E` 是空闲带）。接起来最省事——捕获本来就是 batch 里的一笔写，于是和行原子提交——跑起来最贵：记录要背 LSM 的每条目开销，随层移动被反复重写，需要墓碑，再被压缩掉，一条有用的 30 字节记录可能在写放大上付出好几倍；而裁剪是每条已抽干记录一次删除，等于把一条为了省写而存在的流翻倍。捕获和存储是两个决定，为了原子性把它们绑在一起，买到的是错的那一半。

**本地第二个引擎实例。** 它把 churn 挪出热键空间，到此为止：仍然是 LSM（同样的每条目开销、同样的压缩），多一个 WAL 于是多一个耐久域——落在一个、没落在另一个的提交，要么是洞要么是幽灵；而 `VirtualStorage` 没有日志结构化的实现可以指过去。

**把日志当作真相来源**（提交前先追加并 `fsync`）。这让文件成为权威，然后 okm 就要接管恢复：打开时把未抽干的记录 undo/replay 回去。那是在本来就有 WAL 的引擎前面再放一个 WAL，而且它会是 `commit_batch` 耐久性的真正实现，而不是它的消费者。日志回答「什么变了」；它不能回答「什么是真的」。

**从 subscribe 的 sink 捕获。** 零新写路径代码，而且静默地错：`save_with_prev_into` 按设计不发射（ADR-0031 §5），于是 `merge`/`replace`/`purge` 和每一次跨集合批写永远不会出现在日志里。

**捕获索引、reduce、junction 面**。它们是派生状态；导出契约本来就不带，回放会重复写一遍库自己会确定性重建的工作。

**生产侧序号计数器。** 耐久计数器是键空间式日志需要、文件式日志不需要的东西：段号加偏移已经是一个全序，而且是免费的。

**精确一次。** 重试的写是第二条记录。在一个窗口内按键去重是消费者的事，说出来比承诺一个写者给不出的唯一性更便宜。

## 后果

- 热路径：一个 `Option` 判断、一次进缓冲写者的 `memcpy`；不多一次 `fsync`，热键空间里不多一个条目。对照用已记录的基线：语义 put 1.31 µs（内存引擎），256 B 的 fjall put 0.71 µs。
- 每张表头一个目录，所以分区表的各条流不会相撞，sidecar 与段文件并排。
- 导出之后从库里删行，只有在窗口已封存且已被接走之后才安全；崩溃之后先跑对账重扫，再恢复删除。这是卸载流程的一部分，不是调用方的自由裁量——否则那个至多一次的洞就变成永久数据丢失。
- Iceberg 那一侧仍然缺本篇不提供的东西：带 delete 文件的快照追加、分区、文件尺寸目标。`write_table_metadata` 对它拿到的那些文件写一个快照，所以天真地「一次 flush 一张表」，就把湖做成了一堆未分区的小表。
- 抽干方需要的东西比应用少、比文件多：`okm-wire` 读帧，sidecar 给类型，于是 `okm-dynamic` 不用把声明编译进来就能按 schema 解 payload——但 okm-dynamic 现在没有 Arrow/`RecordBatch` 这一面。不链接应用行类型的抽干进程要么补出这一面（schema 驱动的列构造），要么链接 typed 装配点、把声明一起背着。无论哪种，都是抽干侧的工作，不是对日志的改动——但列构造器本身应该进 core、和 typed 桥并排（它必须复用 `arrow_type`，否则同一张 `FieldType → DataType` 映射会存在两份），而 Iceberg 写入器（快照追加、delete 文件、catalog）应该进自己的 crate：那才是真有依赖的那块，而今天的 `bridge::iceberg` 是个零依赖的 metadata 编码器。
- 日志不让每张表的增量都变便宜：它是给「没有可用的时间序维」的表的答案。有那条维的表，键上的区间扫描或者索引上的区间扫描本来就是更便宜的增量，这个功能一分钱都赚不到。
- 配置：
  `ChangelogConfig { dir, segment_bytes: 64 MiB, segment_seconds: 300, buffer_bytes: 1 MiB, sync_data: false }`
  ——前三项是写者的轮转策略，最后一项是唯一改变崩溃窗口大小的旋钮。
