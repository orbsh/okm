# 0057：动态段的值不动，尾部加一张块表

> **Languages:** [English](0057-the-dynamic-segment-gets-a-block-table.md)（主）· [中文](0057-the-dynamic-segment-gets-a-block-table.zh-CN.md)

**状态：** 已接受（2026-11-10）——同日落地于 `okm-core/src/model/obj_segment.rs`；旧布局的段不再写、也不再读。**日期：** 2026-11-10
**依赖：** ADR-0012（动态段与它的词表）、ADR-0035（整文档面）、ADR-0042（布局版本）、ADR-0045（段是真值，所以它的字节不是派生的）

## 背景

动态段（槽 `0x01`）是库里唯一形状由运行时数据决定的载荷，所以它没法靠 schema 拿偏移。今天是平铺的 n-TLV 帧——`[id][type][len][body]`，`Obj`/`Array` 的体内联——按 name 序写，没有版本字节。

三条事实决定替代方案能长什么样。

- **没有流式，也不需要流式。** 写者把整个值建在一个 `Vec` 里、一次 `put` 交出去（`slot1_into`）。所以"值区要先完整、才能写索引"的布局没有牺牲任何东西——本来就不流式。
- **贵的不在走查。** 走到第 k 个字段要解析 k 个帧头，每个 3–7 字节，中间的值只是按 `pos += len` 算术跳过、不读。真正贵的是解码值与按 id 查词表。
- **难受的形状是帧头散在值中间。** 字段很多，或者中间夹一个大 `Bytes`：每个帧头落在自己那一页，想读最后一个字段就得跨过整段跨度。连续的块表解决的正是这个，而且有表就够了——不必为它存偏移。

## 裁决

**1. 布局 v2——值区、块表、末尾两字节的长度。**

```text
value  = toc_len u16 BE | blocks | values
values = 叶子值体，按块排：块 0 的叶子，然后块 1 的……
blocks = block*          （块 0 是顶层；子块按广度优先排）
block  = count varint | entry*
entry  = id varint | type u8 | len varint     （叶子；len 是值体长度）
       | id varint | type u8                  （Obj / Array；type 的最高位为 1）
```

- `id` 是词表 id；`0` 表示"没有名字"，数组元素正好是这个（id 从 1 开始）。
- type 的最高位表示"这个条目拥有下一个块"。它不占额外字节——type 本来就在——却让每个条目都能自定界：读者不必认识类型就知道后面跟不跟 `len`，于是不认识的类型仍然是"跳过这一个字段"（"更新的写者存了我看不见的东西"），而不是拒绝整段。
- `toc_len` 是块区的字节长度，写在最前、定宽。写者预留它，把表与值区写在它后面，`put` 之前回填；定宽正是能回填的原因——varint 一改长度，后面的字节全得挪。它也是读者能顺着读的原因：长度、表、值区，全程不需要知道这段值有多长。
- **表在值区前面。** 这是顺读成立的前提，也是将来做原地修改时想要的形状：表的位置固定，改一个值的长度只在值区里挪它后面的字节。今天没有原地修改（存储替换整个值，也没有为每个值预留冗余），但这个顺序不把这道门钉死。

**2. 表里不存偏移，位置靠求和得到。** 一个块的值基址 = 它前面所有块的叶子长度之和；块内每个叶子的体紧接前一个。块表本身连续——几十字节——所以这个加法是在手边字节上的算术。给每个叶子存一个偏移，省的就是这串加法，代价是每字段一个 varint 再加每个 composite 一个定宽字段；块表不需要这个帮助。

**3. 广度优先，而且顺序是格式的一部分。** 走块时遇到的第 j 个 composite 条目，拥有第 j+1 个块。这正是嵌套不需要存偏移的原因，也让写者的排队顺序变成承重规则——和块内条目的 name 序同一等级：顺序错了，读者会落到错的块上。

**4. 靠布局，不靠标记。** 没有魔数，没有版本字节：布局在字节之外声明——表与它的 sidecar（ADR-0042），这也是存储层干脆不读格式 1 段的同一个事实（ADR-0056 §7）。能抓住坏表的是必须自洽的算术：`toc_len` 在文件内、每个块的叶子长度之和落在 `values` 里、`count` 数与实际条目一致、composite 条目数与块数一致。

**5. 写者变成一个 builder。** `put_frame*` 是往字节流里追加，这个布局做不到：值区和块表是两个区域，而块表要等值区写完才知道。替代它的是收集 `(id, type, value)`，叶子按块写进值区、composite 排队，`finish()` 追加块表与 `toc_len`。`FrameScratch` 随内联体一起消失：composite 既没有长度也没有体需要缓冲。

**6. 不变的东西，和变小的东西。** 词表照旧把名字解析成 id；块内条目按 name 序写，所以同一份 map 还是编出同一串字节；条目仍然住在槽 `0x01`，仍然是整块值的一次 `put`。叶子条目与旧的帧头逐字节相同（`id | type | len`），所以平铺段只多出块自己的 count 和末尾两字节。composite 条目少了长度（它本来就没有），数组少了体里的元素个数——那个数现在由块的 `count` 承担。

## 否决

**表里存偏移（叶子的 `off`、composite 的 `child_off`）。** 每个叶子多一个 varint、每个 composite 多四个定宽字节，只为省掉在几十个连续字节上的一次求和——而那个求和正是今天的读者跳过一帧时已经在做的算术。字节才是这个布局存在的理由。

**值在前、表在尾。** 值缓冲可以直接当输出缓冲，拼接就只剩一次追加——每写一次省一次段拷贝。否决：每条读路径都得从最后两字节开始，不知道总长就解不了，将来做原地修改还要把表跟着搬。流式上的那点优势也是假的：存储的 `put` 收的是整个值，表没出来之前什么都交不出去。

**不存长度、靠相邻差值推。** 每个叶子省一两个字节，换来相邻依赖和值区末尾的哨兵；长度和体对不上这件事，从此没法逐个条目发现。

**只给顶层做块表，嵌套保持内联。** 落地便宜，也解决平铺那种情况，但一个大嵌套对象照样把兄弟隔开——而这正是本篇存在的理由。

**定宽条目。** O(1) 的按序号查找不是目标：每字段十一字节对比 3–7 字节，为一次没人要的查找付钱。

**尾部魔数。** KV 值末尾的两字节或四字节 magic 区分不了格式（那个事实在值之外声明），也抓不到长度与边界算术已经抓到的损坏。

**把静态载荷的冷区也改成同一形状。** 它的字段来自 schema，唯一的读者按声明顺序走，既没有字段数、也没有随机访问来支撑一张表。它保持 `[tag][len][value]`。

## 后果

- 读者解析尾部，按顺序走块，用叶子长度之和算每个块的基址——要到某个嵌套块，就要走过它前面的块。这份代码只付一次，在唯一拥有该布局的地方。
- 写路径建两个缓冲——块表与值区——在 `put` 前拼接一次：每写一次一份段大小的拷贝。两个缓冲本来就有，被排序的只是拼接那一步。
- 不做原地更新：存储契约没有部分写（`put` 替换整个值），这个布局也不为增长留洞。按位置改一个字段是另一道门，不是格式的性质。
- 旧布局写下的段不再读。已有的库要重写——段是真值（ADR-0045），所以迁移就是给每一行有段的记录重新编码。
- 数组的顺序由块顺序承载，不靠 id：它们的条目 `id = 0`，这也是 id 从 1 开始的原因。
