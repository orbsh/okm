# ADR-0034：表有名字，导出是表的形状

**状态**：已接受（2026-10-21）——同一轮已落地：`#[ok_name]`、
`export_parquet_with_variant`、`Graph::to_record_batch_table`、
`Graph::replace_into` / `attrs`（ADR-0035 之前的名字是 `put_fields_into` /

**日期**：2026-10-21
**英文版**：[0034-table-names-and-export-shape.md](0034-table-names-and-export-shape.md)
**依赖**：ADR-0007（Arrow 桥）、ADR-0012（字段名词汇表）、ADR-0017 §3（边的 ns
与槽位布局）、ADR-0023（reduce 预设）

## 背景

ADR-0007 Phase 1 导出的是**一个 collection**：列由行声明生成，写成 Parquet 文件。备份需要的
三样东西从来不在这幅图里，而且各自是一种不同的失败：

1. **ns 不是名字。** 一个列叫 `since_year`、`weight` 的文件，不会告诉你它是一条 `Employment`
   边——collection 唯一的地址是一个 16 位数，它在库里有意义，出了库没有。读文件的人、恢复的人
   都需要这张表的**名字**。
2. **边不是文档。** 边活在边 ns 自己的条目形状里（`EdgeKey` + `EdgeBody`），而桥只读
   `Document` 集合——于是图的「备份」只有节点。悄悄漏掉事实的备份，比明确拒绝的备份更糟。
3. **行的开区间不是列。** 文档的动态段（0x01）和边的开放属性都不是声明字段，按声明生成的导出
   会把它们丢掉。reduce 干脆不是行：累加器住在自己的槽位族里，没有文档。

## 决策

### 1. 表在 ns 旁边声明名字

行上写 `#[ok_name("messages")]`，derive 出 `Document::TABLE_NAME`（默认 `""`）。两条规则：

- **空串 = 未命名，导出拒绝它。** 拿 Rust struct 的名字凑数是导出时临时发明的第二套词汇——
  而 struct 名不是表名。
- **改名不动数据。** ns 是地址，名字是这张表在库外被叫作什么。改名只改声明和 catalog 的那一行，
  磁盘上一个字节都不动。

名字↔ns 的对应是一张 **catalog**：每张表一行的小元数据表，`(name, ns)`。纯分析用不到它——
导出的列已经自带标签；导入要用，任何「ns 41 叫什么」的运行时问题也要用。

### 2. 导出一张表的形状

键字段（声明序）→ 声明的载荷字段 → **一个 `variant` 列承载动态段**。列保持声明的顺序与类型，
`Vocab` 字段仍是标签。variant 列是动态路径在分析侧的孪生：嵌套对象与数组递归，名字走字段名
词汇表解析，没有动态段的行在该列是 `null`。

**索引不导出。** 它们是派生状态，导入时由 `put` 重建——文件里再放一份，就是又多一个要维护一致
的东西。

### 3. 边集合是一张表，端点是（表名，主键）

边表的列以 `[src_table, src_pkey, dst_table, dst_pkey, predicate]` 开头，随后是边声明的字段，
最后是 `variant` 列。节点引用**就是**（表名、主键）对，所以导出就这么写。

`src_pkey` / `dst_pkey` 是**原始键字节**。一张边表横跨各节点集合；把别的表的键解成那张表的字段，
需要那张表的声明——边 ns 不带它。`name_of` 由装配方提供（它知道 catalog）：不认识的 ns 导出为
NULL，而不是猜一个名字。

### 4. 边的开放属性归图

`Graph::replace_into(batch, edge_id, &map)` / `attrs(edge_id)`（ADR-0035 改名） 拥有 0x01 段，键是
`[ns][0x01][edge_id]`，名字在字段名词汇表里分配。重写（`link_into`）会在**同一个批**里删掉
上一段：属性派生自刚刚被覆盖的那条断言，继承它等于把旧主张的条件挂到新主张上。

在这份记录之前，这个段是消费方（Krystallizer）写的——槽位布局写了文档，但没有方法。没有归属
的格式等于有 N 个实现；导出成了第二个消费方，所以它有了家。

### 5. reduce 是自己的一张派生表

`(table, reduce, group, value)`，一条 reduce 条目一行，全表分组的 group 为空。reduce 不是行，
不该硬塞进行里；但它必须跟着备份走，因为**恢复出来的表如果水位没回来，会发出已经用过的 id**
——恢复的日志表接着 append 覆盖已有的 `seq`，那是静默的损坏，不是体面的缺口。

## 考虑过的替代

- **消费方自写 dump（JSON/CSV）。** 否：同一批行的第二份描述，要跟着声明同步维护，还会把消费方
  的字段名带进任何读这份备份的东西里。
- **一次备份一个归档包。** 否：看不出哪张表坏了，并且在恢复路径上多加一个容器解析器。一表一文件
  意味着局部恢复就是恢复一张表。
- **把端点键解成节点表自己的字段。** 否：边表不知道成员表的声明，而一份全局的键布局注册表就是
  ns 词汇表的第二个真相来源。
- **导出索引。** 否：派生状态，导入时重建。

## 后果

- 备份不依赖存储就能读：标签、表名、带类型的列。
- 恢复是一件有真问题的真操作：落到哪个 ns（请求点名表，schema 要对该表的声明核对，因为导入是
  **按列序号**读的）、覆盖还是合并、以及文件里的 `Vocab` 标签在目标词汇表里不存在时怎么办
  （导入选择拒绝而不是猜）。
- §5 的水位规则变成恢复的义务：导入一张表之后，它的 reduce 行必须先重放或重算，再允许下一次写。
- 在 catalog 里给表命名的消费方，事实也会进备份；没命名的仍然拿到节点与文档，而 catalog 会
  说明缺了什么。
