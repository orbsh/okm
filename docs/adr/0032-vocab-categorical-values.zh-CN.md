# ADR-0032：分类值是数据——自带两个族的 `Vocab<N>`

**状态**：已接受（2026-10-20）——**已实现**。`Vocab<N>` 端到端可用（derive 识别、写路径
intern、读路径补名、每个声明字段一对词表），`Enum<T>` / `EnumTag` / `FieldType::Enum` 已
删除：需要枚举语义的消费方自己包一层 Rust enum，在边界处转换。
**日期**：2026-10-20
**英文版**：[0032-vocab-categorical-values.md](0032-vocab-categorical-values.md)
**依赖**：ADR-0012（字段名词汇表）、ADR-0017 §3（token 词汇表）、ADR-0030（固定面与计数族）

## 背景

`Enum<T>` 把一个 C 风格枚举字段承载为一个字节的 tag，而 tag 表
（`EnumTag::TAGS`）是**代码**：一份显式的 `&[(变体, u8)]`，声明一次、之后不许漂移。
由此两件事，第二件是缺陷而不是取舍：

- **新增一个分类就是改代码。** 带着编译期枚举不认识的分类进来的数据，存不进去。
- **表不跟着数据走。** `FieldType::Enum` 导出到 schema 时只是一个 unit variant
  （tag 表没有载荷），所以动态读者——okm-dynamic、Python/Steel 摊位、任何运行时组装
  collection 的宿主——解出来的就是裸数字（`okm-dynamic/src/decode.rs`：
  `FieldType::Enum => Value::U8(0)`；`okm-dynamic/src/lib.rs` 把逻辑类型写成
  `"U8 (tag)"`）。名字只活在编译侧。

这破了"两个 schema 载体产出同一份字节**并且**同一套语义"的承诺：编译侧的写入方存了
`9`，而只有编译侧能说出 `9` 是什么。与之对照，字段名早就是数据——驻留在 collection
自己的词汇表面里，任何读者都能从 store 里解出名字。

承载分类值所需的机器已经存在：`VocabFaces { id_slot, name_slot }` + `VocabCache`
（`okm-core/src/model/obj_vocab.rs`），先见者得号、双向懒加载、依赖单写者纪律。
今天有两个词汇表在用它（字段名 0x02/0x03、谓词/节点种类 token 0x04/0x05）。

## 决策

**分类值成为一种词汇表，`Vocab<N>` 取代 `Enum<T>`。**

1. **映射是数据。** `Vocab<N>` 在内存里持**标签**、在 wire 上是 `N` 字节 id（`N` = `u8`…`u128`）；名字↔id 表
   以普通词汇表条目的形式住在 collection 自己的 ns 里。`Enum<T>` / `EnumTag` 退役：
   分类值的建模只有一条路，不是两条。

2. **一个词汇表占两个计数族、一个计数。** 两个 `Vocab<N>` 字段是两个独立值域，所以表按
   **字段**分；而一个词汇表有两个方向，所以**方向住在族号里**：

   ```
   FIELD_VOCAB      = 0x02, 0x03    // 字段名——固定面，不变
   PREDICATE_VOCAB  = 0x04, 0x05    // 谓词 / 种类 token——不变
   0x1nnn / 0x2nnn  label → id / id → label   nnn = 词表自己的编号
   ```

   第一个字段拿计数 1：`0x1001`（label → id）与 `0x2001`（id → label）；
   第二个字段拿计数 2，依此类推。一个词表一个编号，两个方向不可能因为差一而错位，容量是完整
   的 12 位（4095 个词表），也没有哪个族内部藏着奇偶约定。

   分配游标不占编号：它是 **id 面的面级单值**（ADR-0030），`[ns][0x2nnn]` 后面一个 id 字节
   都不跟。所以下面那些族保持原有号码——若为游标单开一个族，声明索引、reduce、junction 都得
   整体上移一位，换不到任何东西。

   两个 collection 级的名称域留在固定面：它们的**数量**是固定的，不需要分配，原地不动
   也就没有数据迁移（搬家意味着复制活的名称表——一种静默失败，见「后果」）。

3. **一条游标项，让分配变成点查。** 下一个 id 是**存**出来的——一条，而且不占任何面：
   它是 id 面的**面级单值**，键就是裸前缀 `[ns][0x2nnn]`，不带 id 后缀。该面的真实条目恒为
   "slot + N 字节"，所以零长度键在编码层面无法产生，两者靠**长度**不可能相撞，不靠保留某个
   id。（它不能住在 label 面：空串是合法标签。通用规则见 ADR-0030。）它替掉的是对 id 面求
   `max + 1` 的那次扫描。两个后果都是承重的：
   hot 路径不再扫描（早先那版每个 `put` 都整表加载，因为 derive 是每字段每次调用新建
   一个 cache），以及批量写入方能在自己的批里 intern——批能服务点读、拒绝有序读
   （ADR-0031）。早于游标存在的旧 store 不需要扫描就能认出——词汇表为空时 id 零必然
   缺席——首次分配顺手写下游标，此后这条回落路径就退休了。

4. **id 宽度由声明挑选，上限是精确的。** `Vocab<u8>` 一字节、装 256 个标签（id 0–255）；
   `Vocab<u16>` 两字节、65536 个；直到 `Vocab<u128>`。UTF-8 标签是唯一的值形态——数字编码
   就是数字字段，枚举语义归消费方。intern 超出宽度时**大声报错**，不回绕：答案是换更宽的
   `N`，或者把这个值建成 `String` 字段。

4. **intern 是写路径的一步，由 batch 路径承载。** `put` 在编码前 intern（这次 clone 只由
   声明了 `Vocab` 字段的表支付）；`save_with_prev_into` 在批之前经引擎 intern，于是词汇表
   增长、行与面落在**同一个批**里（`VocabCache::id_for` 本来就是这个纪律）；`save_into`
   无法 intern——它是契约上的"只编码"面、手里没有 store——所以它要求调用方已经通过
   collection 把 `Vocab` 字段 intern 过。这就是"编码是纯函数"这条规则弯折的具体位置，
   弯法与动态段早已存在的那处相同。

5. **读回时补上名字。** `decode_payload` 给出 id（它是纯函数、没有 store）；一个 deref 钩子
   ——与嵌入引用的 `__okm_embed_deref` 同形——把 id 解析成名字，于是 `to_map`、document API
   和所有读者看到的都是名字；表里缺条目时退化可见，而不是凭空造一个值。

6. **分类是标签：没有声明顺序。** 分类字符串没有内在次序，词汇表 id 是到达序。需要按语义
   顺序排序或范围扫描的字段，另声明一个 rank 列（普通整数字段）。这是类型的性质，不是
   免责声明：旧设计里"tag 号可以编码顺序"的说法从未被使用（没有任何测试或文档声明过），
   而且对每一个动态读者都不可见。

7. **快照带标签，从不带 id。** Arrow/Parquet 导出对每个分类字段扫一次它的 id 面，产出可空的
   `Utf8` 列：id 没有标签时写 NULL（空洞如实记录、不填补——凭空造标签是唯一禁止的结果）。
   Parquet 自己的物理字典（默认开启，每个 column chunk 一个字典页）随后给每个 chunk 一份
   本地词表：每个不同的标签在 chunk 内只存一次、行里存的是索引，所以更宽的值形态不必按行付
   （超过 1 MiB 字典上限的 chunk 回落到逐行存值）。导入走目标词汇表反向解析——它把每个标签
   重新 intern，于是恢复出来的行带的是目标库自己的编号，而且**每一行按构造都有名字**：
   旧的带 id 往返正是唯一能产出无名值的路径。对那种旧形态写出的文件不设兼容路径，导入按列
   类型直接拒绝。

## 后果

- 动态写入方可以引入分类，动态读者可以说出它——双模式对称性覆盖到字段的**值域**，
  而不只是类型。
- `okm-dynamic` 丢掉 `Enum` 那组分支：`Vocab` 字段像字段名一样解出名字，plan/执行路径
  与编译路径共用同一个缓存来 intern。
- 255 上限是一条建模约束，且带着明确的解法（收窄值域，或改用 `String`）。它是**每字段**
  的：两个分类字段是两个独立值域，schema 再宽也吃不掉某个字段的余量——这正是 collection
  级单表（或共用 `FIELD_VOCAB`）会毁掉的性质。
- 词汇表这一类最终有**两个家，按分配方式分**，这是有意的：两个 collection 级名称域数量固定
  （固定面、不分配），按字段的数据词表是声明序、开放式的（族 4）。这个分工恰好避开迁移活的
  名称表：搬面必须**复制**条目，忘了这一点 `get_fields` 会静默丢字段（未知 id 丢字段）。
- 因此迁移只剩分类值这一件事，而且**不可静默**：旧的一字节 `Enum` tag 解码不报错、但指向另一个
  分类，所以改写发生在 layout version 提升之后——一次布局变更，不做兼容垫片。
- 欠：`okm-python` / `okm-steel` 对 `Vocab` 的暴露（binding 现在只看到存储形态）。
  原先那条"词汇表面的快照/导出路径"以另一种方式结清：快照导出**标签**、导入时重新 intern，
  于是这些面由行本身重建，而不是随行一起搬。
