# 0072 — 临时引擎是打包 B+tree，因为收益在打包

状态：2026-11-20 裁决并落地。`okm-core/src/engine/ephemeral.rs` 取代 `engine/mem_store.rs`；下面的数字来自 `okm-core/examples/ephemeral_cost.rs`，本机实测（每个家族 4 万条，计数分配器，不是 RSS——`store.bytes()` 与它一致）。
英文：[0072-ephemeral-engine.md](0072-ephemeral-engine.md)
依赖：ADR-0020（扫描是惰性的）、ADR-0027（接口审计）、ADR-0045（捕获是装饰器）、ADR-0059（引擎可以住在 core 之外）
相关：aura ADR-0050 §6–§7（临时 realm 什么都不写）、`docs/ideas/schema-aware-index.md`、`docs/internals/query-cost-attribution.md`

## 背景

这个内存引擎从来没被当成引擎设计过。它是测试地图：`BTreeMap` 加一把锁，`#[cfg(test)]`，约五十行——只因为宿主想要一个内存模式、又不该自己造一个替身，才被公开。

它值得被正式拥有的理由，是整个项目赖以成立的那个前提：**模型声明一次**——键、索引、面、扫描、reduce——**引擎在装配处选**（README〈声明时定形，装配时选引擎〉）。**持久性属于这个选择，不属于模型。** 一个建模复杂到需要 okm 声明、而生命周期不一定需要活过进程的系统，不该被迫写两份自己：同一套声明应当既能跑在持久引擎上、也能跑在这个 store 上，变的只有保证。aura 的临时 realm（`RealmSet::create_ephemeral`，ADR-0050 §6）是这个模式的第一个消费者——一个用 okm 存状态、跑不落盘计算的计算引擎——不是它的定义。语义先变，形态跟着变。

形态由三个测量决定。

**开销按条目付，不按键的字节付。** `BTreeMap<Vec<u8>, Vec<u8>>` 无论值是否为空都要付两个 `Vec` 头（48 B）、每个键块一次 malloc 头，再加它那一份节点开销——在一个键只有 11–19 B 的条目上是 93–104 B。没有 `includes` 的索引条目存的是空值，照付全部。所以「省键的内存」上限就是这 ~95 B；压缩键内容本身是在打包之上再叠的一层，量到 6–11 B/条目（决定 7）。

**杠杆是打包；树形是二阶选择。** 任何把 `K`、`V` 当 Rust 值存的容器都会复现那 93–104 B，第三方有序容器也一样：它们的 API 是 `K: Ord, V`，而变长键在那里就是一个拥有所有权的 `Vec<u8>`。收益来自把它换成一个 12 字节槽位，指向一块共享 arena 里连续的 `[键][值]` 记录，用 `u32` 寻址。

**前缀树在这里不划算。** 同一语料上的路径压缩基数树（精确节点普查、ART 节点尺寸、`u32` 子索引）在六个家族里有四个与打包数组相差 ±10 B，在高熵定宽尾巴上反而输。它唯一大赢的地方是定宽键正好终止在某个节点上——路径本身就是记录——而这一处要拿「引擎知道 okm 的键布局」去换。打包已经把树想拿掉的开销拿掉了。

在打包之内，实测比较是 B+tree / 跳表 / `BTreeMap` 三者，同语料、同分配器：

| 家族 | 键 / 值 | `BTreeMap<Vec,Vec>` | 跳表 | 打包 B+tree |
|---|---|---|---|---|
| primary row（u64 id） | 11 B / 120 B | 224 B/条目 | 162 | 144 |
| uuid7 row | 19 B / 120 B | 232 | 171 | 153 |
| 索引 `by_org` | 16 B / 空 | 109 | 48 | **31** |
| 索引 `by_org_status` | 17 B / 空 | 109 | 49 | 42 |
| covered 索引 | 13 B / 8 B | 114 | 52 | 43 |
| 动态路径 | 33 B / 60 B | 185 | 125 | 117 |

这张表的数字早于决定 7：加上叶级前缀压缩后，打包那一列变成 137 / 148 / 25 / 36 / 40 / 99（见〈测量〉）。表定的是形态——B+tree 优于跳表、跳表优于 `BTreeMap`。

跳表每个条目付 24 B 节点头，每一步都是一次指针追逐；B+tree 每个条目只付共享节点里一个 12 B 槽位，走的是连续数组。B+tree 既小又快，多出来的唯一代价是再平衡。

## 决定

1. **一个类型，一个名字：okm 的非持久化模式。** `EphemeralStore`（`engine::ephemeral`）取代 `MemStore`——同一套声明跑在一个不承诺持久性的引擎上，和其他引擎一样在装配处选。aura 的临时 realm 是一个调用方；任何必须不落盘运行的模型也是。`okm-core` 的单元测试是第二个调用方，理由来自 cargo（一个指回本包的 dev-dependency 会让它编译两遍，两份的 `VirtualStorage` 是不同的类型——ADR-0059 记的双份编译问题）。它也进了 `okm-async` 的 `TestStore::matrix()`，于是每一个遍历矩阵的测试——前缀扫描、批量原子性、`ScanIter::seek`、句柄共享，以及表/图/reduce 的真实负载——都跑在它上面。宿主依赖的 store 不是免于契约测试套件的许可。
2. **它放弃的义务是真放弃，不是推迟。** 无 journal、无恢复、无压缩、无世代、无迁移、跨项无快照、无跨进程、无 changelog 捕获。每一条都是关于「落在介质上的字节」的规则，而这类 store 没有：`ChangelogStore` 装饰器根本不会包在它外面，崩溃就丢掉它，而这正是临时存储已经承诺的。
3. **它新增的义务是测试地图从来没有的那些。** 创建 O(1)，`drop` 归还每一个字节（没有任何进程级的东西），每一笔分配都记在 store 账上（`len()`、`bytes()`），并且普通契约一项不少：字节序、读己所写、`shared_handle` 即同一键空间、错误跟随扫描条目。
4. **形态是盖全键的打包 B+tree**：叶 32 个 `{记录偏移, 尾长, 值长}` 槽位外加一片叶子共享的前缀，内部节点 64 个 `(分隔键, 子节点)`，分隔键取子树里**最小**的键。选最小键这条约定，正是 okm 这种大量追写的键便宜的原因：追加永远不碰分隔键，而「取最大键」的约定每次插入都要重写一个。
5. **分裂在两端偏置。** 单调键流（id、时间戳、uuid7）从边上分裂——32/1 而不是 16/17——因为一片再也不会被碰到的半满叶子是永久的浪费。同语料实测：均匀分裂 43 B/条目，偏置分裂 31 B/条目。随机顺序插入仍然均匀分裂。
6. **store 里没有任何 `Vec` 靠翻倍生长。** 记录、叶、内部节点各住在一块定长 chunk 里，用 `u32` 索引寻址。一个翻倍的 `Vec` 静止时会占着两倍于存活量的字节，在 4 万条索引条目上就是 16 B/条目——打包所换来成果的大半。
7. **叶子里只存一次这片键共享的前缀，槽位只存自己的尾巴。** okm 键空间里 32 个相邻有序键共享 8–15 字节——`[ns][slot]` 头、索引字段、以及单调 id 的高位字节——所以键是 `前缀 ++ 尾巴`，比较时当两段读，只有扫描要交出键时才拼起来。三条规则让它保持便宜：
   - **新叶子把它的第一个键当作前缀**：压缩是白捡的，而前缀只会变松。它从不被加长，因为加长要重写尾巴。
   - **在前缀内部就分叉的键会让前缀变短**，并重写这片叶子的记录。对单调键这是字节边界事件（每 256 个 id 一次），不是每次插入一次；正确路由的键必然共享它所在叶子两端的公共前缀，所以常路从不重写。
   - **分裂把槽位原样复制进两半，共用同一个前缀**，因为尾巴是相对前缀的，而前缀对两半都仍然成立。分裂不制造 waste。
   同语料实测：索引面 31 → 25、42 → 36、43 → 40 B/条目；文档面 144 → 137、153 → 148；动态路径 117 → 99。分隔键改成自己的一条整键记录（每 64 个子节点一条），因为它原先指向的那个条目已经不再持有整键。
   最自然的写法——分裂时给两半各重算前缀并重编码——会让每次分裂都制造与存活量等量的 waste，把重写阈值推进永久重写循环；实测 2 万次 put 要 3.7 s，而不是 35 ms。
8. **删除由 B+tree 自己修复**：同一父节点下的相邻兄弟有余量就借，否则合并并删掉父节点里的那一项，逐层向上修，最后把只剩一个子节点的根塌缩掉。顺序链会跨父节点，所以只有「同一父节点下的相邻子节点」才算兄弟——跨父合并会让某个子项失去主人。删除留下的记录字节由一个**重写**回收：按序取出存活条目、在旁边造一个新 store、完整才换上去；触发条件是 waste 超过存活量一半且存活量在 64 KiB 以上。
9. **一批是一把写锁。** trait 默认按 op 上锁，在内存引擎上这不是微差别：这是并发读者看到两 op 批次是整段还是半段的差别。
10. **读拿读锁，写拿写锁。** 计算读远多于写，所以一次扫描不排在另一次扫描后面，一次点读也不排在一个迭代器后面。
11. **扫描逐项重新上锁，并保留一个带 epoch 的游标。** epoch 没变时下一项是一个槽位；任何写入之后游标作废，迭代器从它最后交出的那个键重新下降——所以扫描不重启、不重复、不向前跳项。**跨项没有快照**：两项之间的写入可以改变下一项是什么，这正是远端后端对分页扫描已经说过的契约（ADR-0021），也是不物化整个区间的代价。每一项都在锁内复制，于是一个键永远不会配上另一个条目的值。
12. **`u32` 引用上限是错误，不是截断。** 一条记录或一张节点表若会越过 4 GiB，写入失败（`Error::Engine`）：那个尺寸的 store 是部署错误，而悄悄改写寻址会破坏每一个槽位。

## 测量

每个家族 4 万条，单进程，堆字节来自计数分配器：

| 家族 | 键 / 值 | `BTreeMap<Vec<u8>,Vec<u8>>` | `EphemeralStore` | 比值 |
|---|---|---|---|---|
| primary row（u64 id） | 11 B / 120 B | 224 B/条目 | 137 B/条目 | 1.64× |
| uuid7 row | 19 B / 120 B | 232 | 148 | 1.57× |
| 索引 `by_org` | 16 B / 空 | 109 | 25 | **4.34×** |
| 索引 `by_org_status` | 17 B / 空 | 109 | 36 | 3.06× |
| covered 索引 | 13 B / 8 B | 114 | 40 | 2.85× |
| 动态路径 | 33 B / 60 B | 185 | 99 | 1.86× |

文档密集的面由它自己的 payload 封顶：120 B payload 加约 17 B 结构就是 137 B，没有哪种结构能改进它。索引面——store 里最多的那种，每声明一条索引每行一条——才是比值住的地方。那里一个条目是 12 B 槽位、它在叶头与叶子前缀里的一份摊销、以及 1–3 字节的尾巴：25 B，而 map 要付 109。

代价侧，同一次运行：点 `put` 86–211 ns 对 map 的 96–192 ns，点 `get` 210–340 ns 对 171–310 ns（1.1–1.3×），3 万条条目的 store 构建 3.5 ms 对 3.2 ms，整段扫描 2.17 ms 正向 / 4.05 ms 反向，而旧的物化路径是 0.95 ms——旧路径的峰值**就是**结果集，这一版只占 2.48 MiB，别的不占。尾巴变短也是点读从 1.4–1.5× 收到 1.05–1.3× 的原因：比较碰到的内存更少。

## 这没有重开什么

- **磁盘引擎的索引层。** `docs/internals/query-cost-attribution.md` 量过：在 fjall 上重写索引层端到端天花板 1.20×，这条结论不变。本决定新增一个引擎；它不替换任何引擎，也不改任何键格式。
- **schema-aware 前缀树。** 仍然只是记录、未设计（`docs/ideas/schema-aware-index.md`），但现在有了触发条件：某个索引面的键字节成为 footprint 主体。上面的测量说触发条件目前为假，因为打包已经把树想拿掉的开销拿掉了。

## 被否

- **用第三方有序容器。** 按现在的 crate 逐个查过：`scc::TreeIndex`（并发 B+tree，叶 15 槽，读无锁）、`crossbeam-skiplist` 0.1.3、`beets`（内存 B+tree，可插节点分配器 + slab arena）、`btree-plus-store` / `btree-slab`（arena 上的 `BTreeMap` 接口），以及 ART 一族（`oxidart`、`art-tree`、`congee`、`subms-adaptive-radix-tree`）。每一个都对 `K`/`V` 泛型，于是变长键在那里就是一个拥有所有权的 `Vec<u8>`：24 B 头加一块 malloc，键一份、值一份，正是本引擎要拿掉的那 64 B/条目。它们会把 109 B/条目原样交回来，只是树换了一种。第二，它们的 range 迭代器借用容器，塞不进 `'static` 的 `ScanIter`；要用它们只能物化——正是本 store 要避免的内存峰值。
- **每次分裂都重编码叶子。** 这是拿到好前缀最自然的做法（给两半各按自己的两端重算），但它让每次分裂都追加与叶子等量的记录，于是 arena 里的 waste 与存活量持平，重写逻辑（正确地看到 `waste > live`）就在每次 put 上跑。实测 2 万次 put 要 3.7 s。现在这条规则用「新叶子的第一个键就是它的前缀、前缀从不加长」换到同样的压缩率。
- **跳表。** 它是第一版并且能用；每个条目付 24 B 节点头加逐步指针追逐，同一面上实测 48 B/条目 对 B+tree 的 31。已替换。
- **自适应基数树。** 上面量过：在四个家族上与打包数组相差 ±10 B，唯一的大赢（定宽键终止在节点上）要拿「引擎知道 okm 键布局」去换。记录触发条件，不构建。
- **先做 head→face 分面表（`[ns][slot]` 前缀）。** 打包之后它值 4 B/条目加扫描局部性，不是 4×：它本想省的那 64 B 是两个 `Vec` 头加 malloc 头，arena 已经拿掉了。它还会把键布局耦合带进来。
- **缓冲式扫描。** 它会把 store 存在的意义——内存峰值——重新引回来：大区间上的 `LIMIT 10` 会先物化整个区间（ADR-0020 裁的是反过来）。
- **让 trait 默认重放 `commit_batch`。** 内存 store 上 op 本来就在本地，锁就是原子性的全部代价，省掉它什么也换不来。
- **在引擎里做内存上限。** 上限要一套记账模型和一个模型层必须解释的错误；`bytes()` 把数字交出去，宿主决定。等某个宿主长出自己看不见的失控再说。
- **给 store 加 journal 以便它能恢复。** 那是有额外步骤的持久引擎：要持久就选 fjall，模型一个字都不用改。

## 后果

- **aura**：`MqEngine::Mem(...)` 变成 `MqEngine::Ephemeral(...)`，`MqStore::mem()` 构造 `EphemeralStore`；临时 realm 仍然不包 `ChangelogStore`。依赖是 git 分支，所以本决定上游落地后，下游用 `cargo update -p okm-core` 取到改名。
- **`okm-core` 的单元测试与 `okm-vector` 自带的测试地图**保持各自形态；只有公开的那个引擎搬了家，而 `okm-core` 的测试现在跑在真实引擎上。
- **引擎矩阵多了一臂。** 把 `EphemeralStore` 放进 `TestStore::matrix()` 之后 738 个测试通过，包含遍历矩阵的表、图、reduce 负载——对一个后端来说这是唯一算数的证据。
- **ADR-0059 对这个 store 的描述**（「`BTreeMap` 加一把锁，`#[cfg(test)]`，约五十行」）早已不成立，在同一批里改正。
- **填充率现在是插入顺序的属性**：单调流约 97% 叶填充，随机流约 65%。这是不在插入时扫描的代价，而且是量出来的，不是假设的。
