# ADR-0011: 存储完整键——不剥前缀

日期：2026-09-14
状态：已接受

## 背景

到达引擎的每一个字节键都是**自描述的地址**：

```text
[ns 2B][slot 1B][key payload]
```

`ns` 是表的命名空间号（`#[ok_ns]` 声明，ADR-0002），slot 字节区分主键（0）与索引条目（ADR-0005），payload 是编码后的键或被索引字段。当远程发送方经过一个声明过的 `NestStorage` 时，接收方再前置一层——宿主前缀——线上字节到引擎上变成 `[host prefix][ns 2B][slot 1B][payload]`（ADR-0010）。

曾有替代方案：存储**剥离后的键**（只存 `[key payload]`），查询时再把前缀拼回去。每键省 3 字节。本 ADR 记录否决理由。

## 决策

键**连同全部前缀层**存储，与访问方法构造出的形态完全一致。任何读写路径都不剥、不拼：`primary_key` / `index_entries` 在派生生成的编码层一次性拼出完整键，所有消费方——get、scan、reduce unfold、索引回查、prune、edge 遍历、远程帧执行——原样使用同一字节序列。

## 否决：存时剥、查时拼

**省什么。** 每键 3 字节。即使千万行也只是几十 MB——系统里最便宜的字节，而且没有任何放大收益（它们本来就在同样的 WAL/compaction 副本里；剥前缀省的是固定 3 字节，不是一份拷贝）。

**付什么。**

1. **隔离从物理退化为逻辑。** 现在两个 ns 的键在字节上不相交：引擎的字典序天然分区，裸分片宿主能字节原样执行帧，恰恰因为发送方的字节已自带隔离。剥存方案下，隔离变成"每条查询路径记得拼对前缀"——naming filter，正是 ADR-0002 与 ADR-0010 一再否决的形态。前缀写进键让错误状态不可表达；前缀放在查询路径上，错一次拼接就是静默的跨 ns 读。

2. **scan 被破坏。** 范围扫描依赖存储字节序的前缀连续性：扫 `[ns][slot]` 能拿到该索引的全部条目，因为这些字节打头存在于每个存储键。剥掉后，scan 面必须每次调用重新推导"这个索引"覆盖的连续区间；`NestStorage` 接收方也无法再"前置声明前缀后不解析其后"——它得理解键结构才能把宿主前缀放对位置，ADR-0010 §5 确立为隔离机制的知识不对称直接被毁。

3. **引擎共居失效。** 一个引擎上挂多个表（测试矩阵、多租户托管形态）能共存，靠的是完整键字节互斥。剥存后，不同表相同的 payload 落到同一个物理键上。

4. **拼接点泛滥。** 现在拼接只存在于派生层的键构造一处。剥存要求每条读路径知道"这把键属于哪个表/ns"才能拼回——把一处声明变成 N 处散落的约定。

**且这 3 字节并非冗余。** slot 字节统一了主键与索引条目的头部（ADR-0005）；ns 字节是 ns 字典的物理载体。一把说不出自己属于哪里的键不是更便宜——是没有地址。

## 后果

- 键拼接保持单点（派生层）；任何读路径不携带拼前缀逻辑。
- 裸分片与托管 `NestStorage` 两种形态都保持字节一致的执行语义。
- 每键存储成本含 3 字节固定头部，作为物理隔离的代价接受。若键体积真的到需要斤斤计较的程度，杠杆是压缩 payload（ADR-0004 wrappers），绝不是剥地址。
