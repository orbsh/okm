# 0067 — 边没有自己的身份

状态：2026-11-14 裁决，已落地。取代 ADR-0017 §1 中关于 `edge_id` 的部分，并收窄 ADR-0066 的成员行。

## 裁决

一条边由 `(src, 谓词, dst)` 识别。没有边号：不需要发号、不需要在还原时保号、调用方也不需要记住什么。

这个身份是完全确定的，因为它的每一段都是既定的：

- `src` 与 `dst` 是 `NodeRef` = `[ns 2B][pkey]`，而按规则每个节点集合有自己的 ns（一个实体类一个 ns，永不复用）——ns 就是集合标记，两个集合不会相撞。
- 谓词是词表号（`0x04`/`0x05` 两面背后的 `Vocabulary::<u16>`），由声明定，不由写入方定。
- 节点键是定宽整数编码，不是字符串，所以整个元组是定式。

## 变了什么

`0x06` 不再是一个指向边的索引，它**就是**边：`[ns][0x06][src][pred][dst] -> 载荷`——遍历本来就需要的那一行。`0x07` 仍是反向面，仍然空。簇的成员行与边→簇索引携带元组而不是号。`Decl::edge_at`、边号发号器、"还原时保住原号"这条约束，全部消失。

除了少一堆概念，还买到两件：

- 同一条边写两次就是同一行。幂等从文档里的一句话变成键的性质。
- 级联删除不可能再留下"号被复用"的悬挂边，因为没有号可复用。

## 多条的问题

会有人问"同一对端点、同一关系出现五次"（五份合同、五次点击）怎么办。答案是那不是五条边：载荷是 `Variant`（`okm-value/src/value.rs`），能装数组，数组作为**一个值**被整体读取、整体替换、原子追加。冲突钩子让追加这件事显式：`on_edge_conflict(|old, new| { old.extend(new); old })`。

这也正是本 ADR 写不出在钩子存在之前的理由：只有一个只能看见存量行的 mutator 闭包时，多值除了复制结构没有别处可住。

## 被否：图内部的紧凑 id

考虑过，推迟，不是否决。每个节点一个稠密 `u64`，旁边放 `(ns, pkey) -> gid` 与 `gid -> (ns, pkey)`，键会变短：`u64` 键的 `NodeRef` 是 10 字节对 8 字节，而一条边的元组在键里出现两到四次，节点自己的映射行在两个到三个边之内就摊平。两行进 `Extension` 带做子类，不占核心槽位。

它输在读侧。今天一跳是从遍历条目里解出 `far`，不读任何行；键里换成 `gid` 之后，把 `far` 翻回 `NodeRef` 就是每跳多一次点读，或者把内部编码泄漏给每个返回边的 API。它还给了节点一个它们今天没有的生命周期：id 必须在节点首次成为端点时发出、在最后一条边离开时回收——模型现在没有的资源，反而要维护一个。

重新打开的条件是可测的：节点键明显超过八字节（复合键、键里带 `Refs`），或者度数高到元组每节点重复四次。在那之前，两个字节的 ns 不值一张映射表。

## 其它缩短键的办法，按代价从低到高

1. **ns 换成集合序号。** `#[ok_nodes(..)]` 是编译期已知的封闭清单，所以成员表在边键里可以写成一字节序号而不是两字节 ns。每次端点出现省两字节，运行期零成本，键仍是确定的。它用"序号是这张图内的集合标记"换掉了"ns 是集合标记"——所以它不是免费的：两张图不能再碰巧共用同一套键布局，读者在解读序号时需要图声明，而以前什么也不需要。
2. **谓词宽度。** `u16` 变 `u8` 只在词表上限 256 个标签时才成立。只对确定会小的图值得；上限是声明期的决定，不是运行期检查。
3. **其它办法，说实话没有。** 存储引擎的前缀压缩已经把重复吃掉了：同一个 `src` 下的行相邻，共享前缀按块只存一次。真正贵的是差异后缀与比较成本，不是磁盘字节。变长整数（varint）能省字节却会毁掉那些面依赖的排序，除非用保序变体——那时省下的也就是最宽的几个键上的一两个字节。

## 切分含变宽段的元组

`[src][pred][dst]` 去掉边号之后，首尾两段的宽度对读者不是先验已知的。比过三种编码。

**长度在前**（`NodeRef` 现在就是：`[ns][len varint][pkey]`）。从左往右读：读一个自定界引用、跳过两字节谓词、剩下的是 `dst`；校验方式是"严格解析必须恰好用尽整个键"。代价：每跳一到两字节，且同一个 `(src, pred)` 组内是按长度优先排序，不是按值。

**长度在尾**（`... [len_src][len_dst]`，定宽，从末尾往前读）。排序从内容开始，相邻行的共享前缀更长。代价：长度必须定宽（一字节即单键上限 255）、范围边界要带上尾部、以及"一个键是另一个键的前缀"时顺序会翻转——短键的长度字节会跟长键的下一个内容字节比较，所以只有长度恰好更小时才成立。经过前缀关系的值有序因此不可靠。

**不要长度。** 这是唯一重要的选项，因为它来自模型而不是编码技巧：每个集合的键本来就定宽（`KeyEncode` 按声明发出固定字节数），所以定宽身份让两个长度字段都变成多余。`[ns][pkey][pred][ns][pkey]` 只靠宽度就能解析、按值排序、每跳零额外开销。

由此得到一条值得写死的约束：**要出现在图里的表，键必须定宽**。变宽字段（`Str`、字节串、任何带长度编码的东西）在集合内部仍可索引，但作为图的节点身份要被拒绝。确实需要变宽键参与的场合，诚实的选择是补齐到声明宽度（右补齐且填充字节排序靠低时能保持字典序）或者接受哈希身份及其碰撞检查——而不是往每个键里塞一个长度。

## 图的自身身份将来怎么走：只在边界上的句柄

对外说的是元组身份，图内部可以带自己的句柄：每个节点一个稠密 `u64`，节点首次作为端点出现时发号，只在调用方、集合读取或删除需要真引用时解析出 `(ns, pkey)`。现在就把它记下来，因为它定死了将来要用的两张面的形状，此外没有别的。

两张**固定面**——各一字节、相邻，紧贴核心（`0x00`–`0x0D`）之后，都不进 Extension（`0x1E`）：

    0x0E  句柄 → 节点   [ns][0x0E][句柄 u64]         → [node_ns 2B][pkey]
    0x0F  节点 → 句柄   [ns][0x0F][node_ns][pkey]     → [句柄 u64]

方向**就是**面号，所以键里没有任何区分字节。分配游标（下一个要发的句柄）就是裸前缀
`[ns][0x0E]`——成立的理由是那张面的每条真实条目都恰好是它之后八字节。

遍历面的张数与槽位都不变，只换内部：`[src_句柄][pred][dst_句柄]`，恒为十八字节，与成员表的键有多宽无关。行里除了边的载荷什么都不多存——对端不需要抄进值里，因为句柄就是图的自身身份，解析它就是句柄面存在的理由。

代价与收益写在这里，是为了将来能**重新测量**而不是重新争论：

- 空间。今天一个元组是 `2 + 键 + 2 + 键`。普通情况是 `(u32, u64, u32)` 这类复合身份——十六字节——元组因此是三十八、句柄是十八：不到一半，而且每条边四份（`0x06`、`0x07` 和两张谓词面）。裸 `u64` 键是二十二对十八，那时省得不多。
- 登记表。每节点两行、合起来约五十字节，按节点付一次而不是按边付。所以十六字节的复合键平衡点在度数一以下——第一条边就付掉了端点那两行——而裸 `u64` 键要度数三四才在空间上赚回来。
- 读。一跳两种形态都不读行，因为 `far` 就是句柄、遍历全程在句柄上。一次引用解析发生在**每个结果**上，而且可以批量：句柄单调发号，排好序的结果集就是 `0x0E` 上的一次范围扫。
- 写。每个碎片里每个唯一端点一次句柄查找，首次出现再写两行。
- 生命周期。句柄在最后一条边离开后只是**浪费**，替代方案是引用计数——那是模型本来没有的资源。浪费的上界是"曾经有过边的节点数"，而 `2^64` 的号空间让它是空间问题而不是正确性问题。将来有紧凑化时从零重发即可。

顺序是发号顺序，不是键值顺序：按句柄的范围扫等于按"这个节点第一次出现的时间"扫，任何面都不许把它当值序用。这也是句柄永远不能充当键序代理的原因，也是图的自身面从不宣称按节点键排序的原因。

## 局部的东西不出库

句柄是访问结构，不是数据。它从身份可推导，所以永远不写进导出：不进湖、不进 parquet、不进 Python 的 dict。往返一致性按元组断言，绝不按句柄；恢复之后句柄表可以按任意顺序分配——唯一稳定的性质是“同一个库内单调、不复用”。

同一条规矩覆盖所有内部编码。词表项导出的是它的**标签**，不是它的号：号只对某个库的词表成立，恢复时由目标库按自己的发号顺序重新 intern（ADR-0062 已经裁定“标签才是身份、id 是局部的”）。

理由不是洁癖。局部编码是库为了让自己的访问变便宜而做的处理；导出的目的是让**别的东西**来读。列存格式自带压缩，而列存读的时候整列都在视野里——它该用的是字典、游程和适合这批数据的编码，而不是一个窄整数：后者的值只有发号的那个库才解释得通。导出标签与元组，文件因此自描述，存储引擎的压缩也比我们在写入时做的任何逐值选择更好。
