# 0047 — 同一次提交的两个面：内存里的事件，盘上的记录

> **Languages:** [English](0047-two-faces-of-a-write.md)（主）· [中文](0047-two-faces-of-a-write.zh-CN.md)

**状态:** 已接受 (2026-10-31) —— 两半都是裁决，且都有测试压着。**2026-11-10 更新:** 判据是接口形态而不是投递合同——subscribe 是观察者接口，变更日志是文件；五个轴保留为形态描述，投递语义与量级的差别记为属性、不参与裁决。同日：点式动词现在发出它们留下或拿走的那一行——`merge` 与 `replace` 在内——轴那一行按代码的实际行为写。**日期:** 2026-10-31

## 背景

有两条路在宣告「一次写提交了」，而且各自有 ADR：`subscribe`（ADR-0008）把类型化的 `Event<K, R>` 推给同进程的 sink；变更日志（ADR-0045）把字节帧追加到段文件，给另一个进程去抽。分开读，两篇都在讲自己为什么该存在；合起来读，像一次没人收尾的去重——而最自然的读法就是「其中一个是残留」。

它们不是同一件事，差在五个轴上。

- **住在哪。** subscribe：进程内存，一个加锁的 `SinkCell`，不落盘，也没有东西要清理。变更日志：`<root>/<header hex>/` 下的文件——写入时是 `.partial`、封存后是 `.segment`，此外还有决定段何时被删的保留策略。
- **带什么。** subscribe：`op`、`epoch`、key，以及**解码后的**文档 `R`——事件知道 schema，因为类型就是它的参数。变更日志：`OpFrame` 的 op 字节、key 与 value，完全没有 schema，而这正是「一个手上没有 schema 的读者也能抽」的原因。
- **谁消费。** subscribe：同进程的 sink——`okm-stream` 的组合子架在它上面。变更日志：另一个进程——`okm-parquet`（独立二进制，ADR-0056 §8），或任何会说 `okm-wire` 的东西。
- **怎么投递。** subscribe：写路径自己的调用栈里同步 `try_send`，best-effort，没人听就丢，也没办法告诉消费者它漏了什么。变更日志：提交前 stage、提交返回 `Ok` 之后才追加——绝不会有幻影写——至多一次，丢掉的尾巴靠对账扫描补。
- **说什么、代价几何。** subscribe：key、op 与解码后的文档，每个语义写只在点式动词上发一次——`put`、`upsert_with`、`merge`、`replace`、`purge`；批量写不发，只动动态段的写没有行交给事件，派生条目从不产生事件；没注册 sink 时零成本。变更日志：只收一批里的**真值那一半**——主行、动态段、名字面与谓词面、每个词表的两个方向——派生那一半丢掉重建；代价是每次写一次 memcpy，加上段文件与它们的保留期。

## 裁决

**两个都留，判据是接口，不是投递合同。** subscribe 是一个可以注册的接口，变更日志是盘上的文件。五个轴只描述两个面各自是什么，不裁决这道题；投递语义和性能也不裁决：best-effort 对 at-most-once、微秒对毫秒，正常使用下没有区别，真出大事故丢一部分尾巴也可以接受。合同照实写清各自承诺什么，但它们不是保留两个面的理由。

**subscribe 是解耦：一段反应只写一次。** derive 声明话题（`#[ok_subscribe]` → `SINK_<ENUM>`），消费者注册一个 `EventSink`——任意 `Fn(E) -> bool` 就行——反应逻辑就写在注册的那一处，写路径不知道谁在听。没有它，「数据变了之后执行某个操作」只能散进每个改数据的地方（`put`、`upsert_with`、`merge`、`replace`、`purge` 各写一遍，漏一处就静默失效），或者让这段逻辑自己读段文件、自己解码才能反应。名字记的就是这个角色：从 channel 改名 subscription，因为它是一个可以注册的接口，不是一条传输。

**变更日志没有这个点。** 它是盘上的文件加一套读法：说清发生了什么，任何进程都能读，但没有地方让人注册「我关心这些」——那里只有程序在读。

消费者用两个问题选边：它跟写者同进程吗，它需要解码后的文档吗？两个都是——subscribe。否则——变更日志。两个性质都要的消费者，是在造一个抽干器，那是独立 crate 的活（ADR-0045）。

不加第三个面，也不发明「统一事件总线」。总线就是两种代价的并集——持久、带类型、按表、常开——由各自只想要一半的消费者一起付。

## 否决

**把段文件 tail 起来喂进程内那一面。** 看起来最省事的统一：只剩一个机制，写路径上只挂一个钩子。它死在位置上——文件 IO 和一次 schema 解码卡在写与反应之间，每个订阅者为一份它没要的文件付钱，反应退化成一个读循环，也就是接口本身消失。换进来的是延迟和基础设施，换掉的是唯一值得留的东西。

**把类型化事件塞进文件。** 它需要写者手上可能没有的 schema，并把 push 变成带投递延迟的 pull。那个形状已经存在：它叫变更日志，它的消费者叫抽干器。

## 后果

- 批量写者（ADR-0031）不发 subscribe 事件。这现在是裁决而不是悬而未决的问题：批量是批量路径，它的消费者在别的进程，而变更日志就是另一个进程读的那一面——每表一批一帧，提交前 stage、提交返回 `Ok` 之后才追加（捕获的 store，ADR-0056 §2）。要让一批写产生事件，打开变更日志即可。
- 如果真出现「进程内的批量写消费者」，它需要的形状就是变更日志已有的那一个：事件与写一起 stage，提交返回 `Ok` 之后再 flush。那是那个调用方集合上的改动，不是新机制；今天没有，是因为没有人要。
- 类型化的那一面仍然按表、仍然 best-effort。需要精确的消费者应该内联——放进写路径里的 reduce 折叠——而不是挂在订阅上；这条分界是 ADR-0008 的，本篇不削弱它。
