# ADR-0065：检查点陈述的是日志，不是表

日期：2026-11-12
状态：已裁决并落地 2026-11-12

**依赖：** ADR-0058（导出的表是一张 Delta 表）、ADR-0061（湖是一个键空间——检查点就是多出来的一个键，经由同一个存储写出）

## 1. 背景

一个版本只带变化，追加因此便宜：一个窗口是一条 `add`，一次发布是一条 `add` 加上被替换文件的那些 `remove`。代价由**读方**付，而且随时间增长：「现在哪些文件是活的」是从版本 0 起每个版本 action 的累加，所以一个按间隔发布版本的生产者，交给读方的是一份必须整份重放、才能知道只有一个文件活着的日志。

drain 用 fold（`condense`）摊销这件事，但 fold 重写的是**文件**：它不缩短日志，fold 之后日志里仍躺着走到这一步的每一条 `add` 与 `remove`。`publish` 是这种形状躲不开的地方——它每个版本替换全部状态、把表维持在一个文件，日志却每个间隔稳定长一个版本。

Delta 的答案是检查点：每 N 个版本，写者把日志当前的成员集合陈述成一件产物，读方从那里开始。本仓库此前一个都不写（`read_log` 的注释里写明了），而 `publish` 就是第一个需要它的调用方。

## 2. 裁决：一件产物，装着日志自己的 action，落在 `<V>.checkpoint.json`

检查点是 `_delta_log/<V>.checkpoint.json`：JSON 行，装着与版本**同一套** action——最后写下的 `protocol`、表自己的 `metaData` 逐字照搬（id、schema、分区列、创建时间）、以及每个活文件一条 `add`，按日志顺序。删除被化解掉：检查点陈述的是成员集合，离开的文件就是不被点名。它像版本一样用 create-only 写来认领，所以两个写者不会对「某个版本的状态是什么」各执一词。

读方从**最新**的检查点开始，只重放它之后的版本；`absorb` 是两件产物共用的一个函数，这正是要买到的性质——检查点不是第二种格式，而是历史已经折叠好的日志。它背后的版本缺失不算错误：检查点就是读取的起点，它也陈述了 `max_version`。

`N` 是写者的旋钮，不是格式的：`PublishOptions::checkpoint_every`（默认 `0`，一个都不写），而 `delta::write_checkpoint` 是公开的，任何别的写者——drain 的 fold 是显而易见的下一个——都能按自己的节奏陈述日志。`publish` 在提交之后、删除之后写它，绝不夹在两者之间：一个点名了存储里已经没有的文件的检查点，会把一次节省变成一次失败。

## 3. 为什么是 JSON，而不是 Delta 的 Parquet 检查点

Delta 自己的检查点是 Parquet，带固定的 `checkpointSchema`（`add` 连同它的 `stats` 结构、`partitionValues` map、时间戳、可空性），外加一个 `_last_checkpoint` 指针文件。忠实写出那件东西，等于为「不是我们的读方」维护第二套 schema 并和日志对齐：本 crate 的读方本来就按 JSON 解析 action，而检查点在这里的职责是替它省事，不是服务外部引擎。

所以形态对自己的受众是诚实的：它被本 crate 读，不被别人读；等到某个引擎必须跳过日志的那天，Parquet 形态是**加在**它旁边，而不是替换它——action 清单是同一份，懂 JSON 形态的读方不需要第二次解析。把限制写下来，比写一个没人读其列的 Parquet 写入器便宜。

两条相关的「不裁决」，同一个理由。其一，没有 `_last_checkpoint` 指针：读方为了找版本本来就要列 `_delta_log/`，而指针是第二个可能和列表打架的表面。其二，检查点不是数据文件、也不是 `condense`：`condense` 把当前状态物化成**行**并提交一次替换，检查点陈述的是**哪些文件**持有那个状态、自己不提交任何东西。它们看起来像的地方恰好是「表的活文件集只有一个文件」——发布者的表——在那里检查点点名的正是 `condense` 会写出的同一个文件，所以两者容易被混为一谈，值得说清。

## 4. 它让什么变合法，以及什么没有建

最新检查点及其以下的版本，已经没有任何东西会读。回收它们因此是合法的，而这件事**没有**实现：删掉一张表的历史是有自己动词、自己默认值的保留决策，而且对检查点没有陈述的一切，日志的版本仍是格式的权威。一个顺带扫 `NNN.json` 的 vacuum 是下一步，不是这一步的静默插件。

解析不了的检查点是错误，而不是退回从版本 0 重放。检查点是优化，但它也是唯一陈述了它所替换的那些版本的产物；一个静默重放的小表会答对，并把这个坏产物藏到旧版本真正消失的那天。

## 5. 验证

`okm-lake/tests/checkpoint_test.rs` 在两种形状上都把这件事钉住。发布者的表用 `checkpoint_every = 3` 跑七个版本，只在版本 2 与 5 出现检查点、别处没有；它的活文件与行数，等于另一张不带检查点发布的表。随后从存储里删掉版本 0..=5，读方——只剩检查点加版本 6——答出同一个活文件、同样的行，这就是「从检查点开始」必须意味着的东西。第二个测试用三个窗口 drain 一张变更表，给它写检查点，删掉前两个版本，断言 `read::current_state` 折出来的 batch **等于**整份重放的 batch，键列也在内。

## 6. 后果

- 一次发布的代价是每 N 个版本多一次写：检查点的大小是活文件数，不是表的行数。
- `read_log` 现在既列版本也列检查点，并优先最新检查点；没有检查点的表行为与从前完全一致。
- 检查点的单位是整张表，因为日志陈述的就是整张表。一张有一万个活文件的表会得到一万行的产物；拆成多个部分是 Delta 的多段检查点，那是另一个决策。
- 检查点绝不会落在已经有检查点的版本上：再问一次就答出既有的产物，所以一次幂等的重复发布不会让日志的附属产物增长。
