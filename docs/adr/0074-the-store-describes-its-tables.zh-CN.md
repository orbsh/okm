# 0074 — store 自己描述它的表，日志读这份描述

状态：2026-11-20 裁决，尚未落地。

## 背景

ADR-0056 §2 给捕获留了一个开关的两个位置：声明（`Document::CAPTURED` 默认打开，`#[ok_uncaptured]` 关掉）和位置（`Location::Off`，给没有本地持久目录的部署）。这两个位置是够用的，而且都只在同一处检查——`register`。

实现里多出了第三个位置，而且没有人裁决过它：`Collection::captured(store)` 登记，`Collection::new(store)` 不登记。一张表进不进日志，取决于装配点碰巧调了哪个动词；而这两个动词在类型上无法区分——`ChangelogStore` 就是 `VirtualStorage`，任何收 store 的构造函数都收它。更糟的是 `register` 在三种情况下都返回 `Ok(())`：类型是 `#[ok_uncaptured]`、这个部署没有本地目录、表真的登记上了。一个值，三种含义，调用方无从分辨。

在日志只是导出面的时候，这还撑得住：少一张表就是少一份导出。ADR-0071 把日志变成基线的来源之后，少一张表就是**恢复**里少一张表——静默地，只在真去恢复的那一刻才暴露。

同一种形状还出现两次。ADR-0043 §4 让 `Collection::new` 保持零 I/O，因为它返回 `Self`，于是 attach 成了动词（`ensure_layout`）——而 `src` 里没有任何地方调这个动词，只有测试调。okm-dynamic 把 `CollectionSchema` 当构造参数收下、只存在内存里；全仓唯一持久化的副本是日志的 JSON 侧车，而它只有在 `register` 跑过之后才存在。

缺的那一半，store 里本来就有。`[partition][ns][0x1F]` 是每表一行，装着 `version`、`faces`、`table`（ADR-0043）——正是段头要盖的三样（`SegmentMeta::of::<R>`：布局版本、faces 指纹、名字）。这一行是 NAME → BYTES 的映射，值的含义归写字的人，所以一份声明可以搭在这行里走，不需要任何布局决定。

## 决定

1. **只有一个构造函数，而且它是 fallible 的。** `Collection::open(store) -> Result<Self>` 做 attach：点读 `[partition][ns][0x1F]`，没有就种下，代数不符就拒绝（`LayoutMismatch`、`LayoutUnstamped`）。`Collection::new` 不再公开；`ensure_layout` 与 `captured` 不再是调用方要记得调的动词。一张表不可能在没 attach 过的情况下被使用，所以也不可能静默地不在日志里。
2. **这一行携带声明，用 store 自己的编码。** 在 `version`、`faces`、`table` 之外，`schema` 装 `CollectionSchema` 的字节——手写 encode/decode、带头部的布局字节，规矩与 `TableMeta`、与记录编码相同。`capture` 只由 `#[ok_uncaptured]` 声明写出，别处不写；没有这个名字就是捕获，所以本决定之前写下的 store 读作「默认捕获」。JSON 退出写路径：侧车和任何给人看的视图都变成这段字节的渲染，需要时生成。「二进制」指仓库自己的编解码系列——`put_len` 前缀的字符串与字节串、定宽数值大端、编码自身带一个头部格式字节（与表的 `layout_version` 不是一回事）、解码对本构建不可能写出的字节直接断言（ADR-0040）而不是宽容解析。
3. **日志靠观察得知，不靠登记。** meta 行是一次普通的写，所以它像别的写一样过提交边界：`touched()` 看到落在 `[ns][0x1F]` 的 key，解码这一行，把 `ns → SegmentMeta` 记进内存。日志在这行写下之后才启用的情形，首次遇到未知 ns 点读一次，每进程一次。每次提交的路径不加任何成本，也不再有登记动作可以忘。决定本身也不许随表的数量增长——它是日志在每次写入时唯一要做的事，而今天是每个 key 一遍对全部已登记前缀的线性扫描，再对它找到的每张表把整批重新过滤一遍。站得住的形状是：`#[ok_uncaptured]` 命名空间构成的排除集合（通常是空的，所以快路是一次空判断）、以 `[partition][ns]` 这个字而不是字节前缀作键、并且把一批一次性切成每表一段，而不是扫描加二次过滤。天花板有实测：捕获的成本是每次写 +84 到 +99 ns（相对一次 fjall 持久写高 5–8%），那是帧编码加一次 memcpy 进段缓冲——路由必须在这旁边看不见。
4. **两处定义靠核对，不靠假设。** 声明必然存在两份——二进制里的编译期常量，和 store 里的字节——所以 attach 时比对：store 里的 schema 必须等于本构建从声明为该布局代数推导出的那份，不等就拒绝（原来只写在侧车里的规矩，搬到每次都会跑的位置）。faces 漂移仍是 ADR-0048 定性的 `Stale`，可修复；改变形状的声明必须换布局代数（ADR-0042）。
5. **okm-dynamic 从 store 打开。** `DynamicCollection::open(store, ns)` 从 meta 行读声明，一次性编译成 plan——字段位置、宽度、索引槽——于是某条记录的访问是 plan 上的下标，而不是每条记录解析一遍名字。plan 在 open 时推导、只存在于内存；store 里放的是声明，从不放编译后的形态。

## 由此而来

- 所有装配点都要改（`new` → `open`，调用变成 fallible）。这份返工本身就是执行手段：编译器负责让「attach 过」变得无法回避。
- 每张表在 store 里多一到两千字节，store 变成自述的。导出、湖、okm-dynamic、日志从此读同一份声明，而不是各自维护一条约定。
- 侧车文件不再是第二份真相，退成便利品。
- ADR-0043 §4 被修正：attach 进了构造函数。保留一个 infallible 的 `new` 的代价是一个可选的动词，而那个动词没人调。

## 被否

- **装配点的开关。** 本 ADR 存在的理由就是它。
- **在 `VirtualStorage` 上加默认空实现的方法**（`register_table`）：`dyn VirtualStorage` 出现在五处，泛型方法要付出对象安全，非泛型方法让引擎 trait 背上日志形状的类型——依赖方向反过来，引擎层开始知道「段」是什么。
- **首次写入时懒 attach。** 把一次性的成本搬进热路径，只为保住一个只是习惯上 infallible 的构造函数。
- **meta 行里放 JSON。** 线上是字节、边缘才渲染，是仓库在别处已经定下的规矩；store 对自己的描述不是破例的地方。
- **链接期声明注册表**（linkme 那类分布切片）：对二进制消费者可行，但它让 store 的内容取决于哪些类型被链接进来，而且对完全没有声明映像的动态消费者毫无帮助。
