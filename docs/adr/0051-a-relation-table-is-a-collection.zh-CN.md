# ADR-0051：关系表就是集合——Junction 退役

## Status

Accepted (2026-11-04)。取代 ADR-0050：它自己的结论「junction 是一张表」再往前一步——不是「用 junction 机械塑造成的一张表」，而是模型里已有的那张表。ADR-0015/0016 的 junction 载体随之退役。

## Context

ADR-0050 给了 junction 自己的 ns、装这对身份的主键面，以及装反过来的那对身份的反向面。形状是对的，载体不是。那次决定要现造的每一项能力，键为两个身份的文档集合本来就有：

| 关系需要什么 | junction（原状） | junction（ADR-0050） | 一个集合 |
|---|---|---|---|
| 正向扫描 | 每个端点 ns 一条条目 | 主键面 | 主键第一列，`scan_keys` |
| 反向扫描 | 每对再一条条目 | 反向面（只给身份） | `#[ok_index]` + **回表拿整行** |
| 关系属性 | 没有 | 要新增载荷类型参数 | 普通字段，可建索引 |
| 两个方向都写 | 手写 `link` 配对 | 一样 | `put` 一个 batch 写行与索引 |
| 重建派生状态 | 做不到 | 走主键面（未实现） | `rebuild_faces` |
| 进湖（导出） | 被排除（ADR-0045） | 只有主键面 | 行就是行 |

`okm-core/tests/relation_table_test.rs` 端到端证明了「集合」这一列：前缀正向、索引反向且带载荷、`purge` 带走索引条目、`rebuild_faces` 从行重建。

SQL 里也没有 junction 这个载体：多对多就是一张两列主键的表，再加关系自有的列；反向方向是二级索引。那在这个模型里就叫集合。

## Decision

**1. 关系就是键为这对身份的集合。** `MembershipKey { channel, member }`；第一个身份作为键前缀被扫描，行上带 `since_ms`、`role` 以及关系自有的其它列。

**2. 反向方向是声明索引** `#[ok_index(name { fields(member) })]`，写路径与行同一个 batch 维护它，`rebuild_faces` 可以重建。它不是事实的第二份。

**3. `Junction`、`JunctionEncode`、`KvJunction`、`0x5nnn` 段、方向位以及「junction 拥有 ns」这条特例，全部退役。** 没有声明、没有描述符、没有面。

**4. 级联仍是调用方的策略**，和其它地方一致。删一个端点 = 扫关系表的第一列并逐行 `purge`；不需要 `unlink_all`，因为逐行 `purge` 是同样的工作量，而且索引是免费维护的。

**5. 关系表像其它表一样导出。** ADR-0045 的排除清单里 junction 那条整个消失，而不是收窄。

## Alternatives rejected

- **保留 junction 并给它加载荷（即 ADR-0050 的写法）。** 它用手工重造 `put` + `#[ok_index]` 已经自动完成的事，并保留一个派生面无重建路径的载体。
- **把 junction 做成集合之上的语法糖**（生成键结构与索引的宏）。糖必须解释自己何时适用；而底下的形状本来就是建模者必定要写的两条声明，给同一个机制起第二个名字，正是 ADR-0027 命名一节已否掉的做法。
- **两张互为镜像的文档表**（本轮讨论的起点）。依旧否决：两份真相、手配双写、谁都不可重建。

## Consequences

- 关系可以带数据，并且无需任何新机制就能参与索引、reduce 与导出。
- 模型里少一个概念：「多对多」不再是载体，而是一种键布局。
- 迁移：已声明的 junction 改成集合。正向前缀照常工作；反向变成索引；junction 的编号分配被释放。
