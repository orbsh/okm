# ADR-0012: Object 模式——单一编码，声明字段加动态段

日期：2026-09-14
状态：已接受（2026-09-14；机制已落地——obj 载荷的两个 slot、字段名词汇表、双向 `DocumentEncode`、`Ref`/`Refs` 嵌入）。动态段的值布局现在是 ADR-0057 的形态：值区头部一张块表，下面这串帧不再写、也不再读。

## 背景

外部数据（MQ 消息、JSON 文档）在写入时没有固定的 Rust 结构体。现有 row 模型要求先声明结构体才能落一个字节；存这类数据今天只能硬造一个包装 row 或摊平成 ad-hoc 键。两套编码——严格的 row 与松散的 object——意味着双倍表面积：两个 derive、两种布局、两条解码路径、两份维护与教学成本。

消解这个分叉的观察：声明式 row **本身就是**动态段为空的 object。单一编码覆盖光谱两端，声明端完整保留现有全部能力。

## 决策

**一个模型，名为 obj。** 公开概念是 object；derive 是 `DocumentEncode`，声明式 row 就是"只有声明字段的 obj"。

为什么不用 document：这个概念确实与 document-oriented 存储（CouchDB、MongoDB）同宗，这层亲缘值得承认——但 `obj` 这个名字靠双关挣得位置：编程语言中的对象，也是存储格式意义上的 object。object/doc/variant 三个词各自标记静态/动态光谱上的三个不同位置，obj 刻意与 document 区分开：

- **document**——逻辑与物理上全动态；每个字段都走动态路径（词汇表编号 + 每帧值类型）。
- **variant**——动态内容整体嵌为一个声明的静态字段（`Vec<u8>`/`Bytes` payload 字段）；动态性活在值里，不进键布局。
- **obj**——逻辑上全动态（运行期可出现任意字段），但声明的静态字段嵌入动态整体：hot/cold 段、索引、schema 导出对它们照常生效。声明式 row 是动态路径为空的退化 obj；纯 document 是声明路径为空的退化 obj；两者是同一编码。

所以 obj 不是 document 的改名——静态嵌入动态才是区别所在，而 "obj" 一词在指向 object 的同时不放弃与 document 的对照。

每个 obj payload（slot 0，主表）的字节布局：

```text
[hot 段][cold TLV]
```

——与今天的 row 完全一致。声明字段保持现有编码：定宽字段在 hot 段连续排列，变长字段为 `[tag][len varint][bytes]` 帧排在 cold 段，tag = 声明序号。类型来自编译期 `FieldDesc` 表（`Row::FIELDS`），永不在字节里。

**动态段（固定面 0x01）。** obj 可以额外携带未声明字段，每行一条记录存在 `[ns][0x01][key payload]`——与索引条目同一骨架（`[ns][slot][...]`，slot 紧跟 ns），中间没有字段段，主键落在尾段。每行的数据挂在行键下：不带 pkey 的话所有行的动态段会叠在同一个物理键上互相覆盖。共享的 `[ns][0x01]` 前缀也让整个段可前缀扫描（prune、重建）。其值是**值区之上的一张块表**（ADR-0057——本 ADR 最初规定的扁平帧列表已退役；完整条目语法、顺序契约与尺寸区间见[动态段](../internals/dynamic-segment.zh-CN.md)）：

```text
[动态面的值] = [toc_len u16 BE][blocks][values]
[块]         = [count varint]([field-id][type][len varint][value])*
```

- `field-id`：字段名词汇表编号（见下）。
- 块 0 是顶层条目；composite 条目拥有**下一个**块，所以嵌套按广度优先——走表途中遇到的第 *j* 个 composite 拥有第 *j+1* 块。表里不存偏移：块的值基址 = 它前面各叶子长度之和，块内同理，都是手边字节上的算术。
- `len` 只出现在**叶子**条目上，用的是 `VarInt` 那条前缀单调 varint 编码（`wrappers/wire.rs`），与 cold 段帧、Array/嵌套 Map 的元素帧共用：小条目的头部从 5 字节降到 2–3 字节。composite 不带长度——由它那个块的 `count` 定界。
- `type`：小型运行期值词汇表——这是唯一真正的新元素。声明字段的类型在编译期 FieldDesc 表里；动态字段必须自描述，其条目以一个值类型字节开头（int / float / str / bytes / bool / null / array / obj 保留变体），而**这个字节的最高位标记「该条目拥有下一个块」**——于是每个条目都能在不理解类型的前提下自定界，不认识的类型仍可跳过。嵌套可递归复用 obj 帧；词汇表先留保留变体，嵌套支持可后置。取帧方式是 **CBOR 衍生，不是 CBOR**：只取 major type 模式——每帧以类型 nibble 开头——结构编码也在同一方案里。CBOR 的 major type 含列表和映射；有了字段名词汇表，OKM 只需要列表——映射就是 nTLV 列表（编号、类型、长度、值），结构信息活在值里，不进 per-document schema。
- 顺序：条目不承诺任何顺序。仓内每个写入方接收的都是按名字键控的 map（`BTreeMap`），所以字节按名字序写出——既不是 id 序，也不是调用方插入名字的顺序。读取方按 id 寻址动态字段，绝不依赖位置；因此"blob 内 id 递增、可以二分"这类假设不成立。

**声明字段走自己的面索引；动态字段经声明的 path 索引。** 索引需要稳定的字节序和定宽比较键——自描述的动态值**作为 key 材料**不具备这些。ADR-0029 从另一侧补上：一条 path 索引在声明的 path 上为每个解析出的值物化一条条目（值类型限有存储形态编码的那些），挂在 schema 驱动的写路径上。动态**名字**永远不能当 key 材料：名字是运行期数据，动态路径只能靠它的声明被寻址，不能靠 key。某个动态字段若真以 key 形态变热，仍然把它声明出来（一行 schema 改动加一次表重建）——row 模型的纪律不变。

## 字段名词汇表（固定面 0x02/0x03）

动态帧以编号携带名字。词汇表是**运行期的、每表一个的双向映射**——OKM 存进 KV 的第一个可变词汇表（ns 保持编译期；ADR-0002"词汇表留在代码"说的是 ns 层，不适用于此）：

```text
固定面 0x02: [ns][0x02][field-id]      → 名字字节   （编号 → 名字）
固定面 0x03: [ns][0x03][名字字节]      → field-id   （名字 → 编号）
```

纪律，从 ns 词汇表复制：

- **Append-only。** 编号永不回收、永不重编。写路径首次见到某个名字即领取下一个空闲编号（单写者分配，由引擎互斥锁串行化）。
- **逃逸编号，而非重编号。** u8 迟早不够；重编已存储数据的成本过高（这正是否决重编的原因）。改为编号 `0xFF` 作逃逸：其后跟 `[0xFF][u16 id]`。扩展是 append-only 的，存量数据零迁移；字段数 ≤254 的文档每帧只付 1 字节。
- **扁平映射，不用 trie。** 双向都是引擎自身字节序结构上的 point get。trie 的名字前缀共享被评估并否决：常规业务名字共享前缀少，trie 的多级跳转与 UTF-8 基数开销换不来收益，扁平双向映射让编号→名字与名字→编号一样便宜。
- **内存镜像是每句柄一份；一次分配只有在其 commit 落地后才算数。** 一个镜像存活于整个 `Collection`（每操作重建时，每个动态字段都变成一次 point 探测——读门写门都如此）。名字→编号方向只有在该词汇表写入所在 commit 返回 `Ok` 之后才免探测直接信任；被拒的 commit 否则会让读者拿到一个没有任何条目定义的编号。分配游标从不缓存：同一引擎上的两个句柄共用同一个计数器，缓存的水位会把另一个句柄刚领走的编号再发一次。两个写者并发分配时仍然在游标上竞争——单写者假设不变。
- **一次写入写两个方向，于是一个面就是完整映射。** 一次分配把 名字→编号、编号→名字、游标 写进同一个 batch，所以单靠编号面就能反向重建整张表：schema 驱动侧一次扫描建出某个句柄的词汇镜像并反转，然后**保留**它，未命中时才点查——另一个句柄分配过的名字在拿到第二个编号之前先被采纳，不认识的编号去编号面查。名字面的价值在点查，不在重建。每次分配立即提交的写者（图侧的边路径用的是真实 store，不是边 batch）在写入返回时就把它采纳；把增长塞进调用方 batch 的写者只采纳该 commit 携带的那些编号。
- 也考虑过帧里直接放原始名字（完全不要词汇表）：对目标形态（MQ topic 内同表文档高度同构、名字强复用）是最贵的一端——每文档每帧都付完整名字。真正 schemaless 的表（每行名字都不同）词汇表退化为 1:1——不比原始名字差，且仍换来单一的查询结构。

**为什么首见分配优于推断和封闭枚举。** 目标负载是字段词汇有界但开放的交错流——Aura 的有限类型 event 以任意顺序到达 MQ、结构化日志有固定的时间/级别/事件加不可预估且持续新增的其它字段。两个标准答案在这里都失效：

- **首记录推断**（Elasticsearch 式）假设第一个文档揭示 schema；类型 B 在类型 A 之后到达，猜测就变成 mapping conflict 和运维事故。词汇表没有"首记录"概念：名字在它首次出现时领号，无论什么顺序。
- **封闭声明枚举**（编译期注册全部字段名）每来一个新类别就要重建——正是负载排除掉的不可预估性。词汇表在运行期吸收新类别，零重编译、零预估。

相比之下 type byte 保留在每帧：同一条流在相同帧位置交错不同的值类型，类型重复率不可假设，类型词汇表化一无所得。（完全同构的集合——数值列存形态——不是 object 模型的目标；它们由嵌套的声明式 obj 承接：重复结构在嵌套层恢复 hot 段 O(1) 偏移和索引，外层 obj 保持纯动态。）

## Slot 分配

```text
0x00       主表                  [ns][0x00][key payload]
0x01       obj 动态段            [ns][0x01][key payload]
0x02       字段名词汇表            [ns][0x02][field-id]        → 名字
0x03       字段名词汇表            [ns][0x03][名字字节]        → field-id
0x04/0x05  谓词词汇表            [ns][0x04][predicate_id]    （ADR-0017）
0x06–0x09  图面                  （ADR-0017、ADR-0041）
0x0A       向量索引快照          （okm-vector 缓存）
0x0F       表元信息              （ADR-0043）
0x3nnn     声明索引              [ns][0x3nnn][...]
0x4nnn     reduce                [ns][0x4nnn][...]
```

obj 自己拥有的每一面都是单字节的**固定面**；声明索引与 reduce 是**计数族**（family nibble 加 12 位计数，两字节）。slot 自定界——首字节自己说明后面还跟不跟计数字节——所以固定面与计数族不可能混淆。完整分配由 ADR-0030 拥有，它取代了 ADR-0016 统一的 4 字节头。

## 改名：kv_ → ok_

属性家族是 `ok_`（`ok_ns`、`ok_index`、`ok_ref`、`ok_subscribe`、`ok_default`、`ok_event_enum`），取代 `kv_` 前缀；row 概念名为 obj。`o` 是双关：编程语言中的对象，也是存储格式意义上的 object/doc/variant。derive 宏名跟随同一词根（`KeyEncode`、`DocumentEncode`）。

## 后果

- 单一编码、单一 derive 家族、单一解码路径；声明式 row 是动态段为零的特例，无需迁移。
- OKM 迎来第一个运行期词汇表（字段名），带 ns 词汇表纪律：append-only、逃逸式扩展、单写者分配。
- 动态字段的值类型成为线格式契约的一部分（okm-core 里一个小封闭枚举，schema 导出同步镜像）。
- 动态字段处处可读；索引它们要走一条声明的 path（ADR-0029），在 schema 驱动的写路径上为每个解析值物化一条条目。名字是运行期数据，永远不是 key 材料——某个动态字段若需要 key 形态的访问，仍然要声明出来。
- 实现覆盖：`DocumentEncode` derive、slot 1 读写路径、词汇表维护、值类型枚举、schema 导出扩展。
