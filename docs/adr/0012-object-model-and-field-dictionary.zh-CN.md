# ADR-0012: Object 模式——单一编码，声明字段加动态段

日期：2026-09-14
状态：已接受（设计定案；实现待 PLAN 排期）

## 背景

外部数据（MQ 消息、JSON 文档）在写入时没有固定的 Rust 结构体。现有 row 模型要求先声明结构体才能落一个字节；存这类数据今天只能硬造一个包装 row 或摊平成 ad-hoc 键。两套编码——严格的 row 与松散的 object——意味着双倍表面积：两个 derive、两种布局、两条解码路径、两份维护与教学成本。

消解这个分叉的观察：声明式 row **本身就是**动态段为空的 object。单一编码覆盖光谱两端，声明端完整保留现有全部能力。

## 决策

**一个模型，名为 obj。** 公开概念是 object；全量改名时 `ObjEncode` 更名 `ObjEncode`，声明式 row 就是"只有声明字段的 obj"。

为什么不用 document：这个概念确实与 document-oriented 存储（CouchDB、MongoDB）同宗，这层亲缘值得承认——但 `obj` 这个名字靠双关挣得位置：编程语言中的对象，也是存储格式意义上的 object。object/doc/variant 三个词各自标记静态/动态光谱上的三个不同位置，obj 刻意与 document 区分开：

- **document**——逻辑与物理上全动态；每个字段都走动态路径（字典编号 + 每帧值类型）。
- **variant**——动态内容整体嵌为一个声明的静态字段（`Vec<u8>`/`Bytes` payload 字段）；动态性活在值里，不进键布局。
- **obj**——逻辑上全动态（运行期可出现任意字段），但声明的静态字段嵌入动态整体：hot/cold 段、索引、schema 导出对它们照常生效。声明式 row 是动态路径为空的退化 obj；纯 document 是声明路径为空的退化 obj；两者是同一编码。

所以 obj 不是 document 的改名——静态嵌入动态才是区别所在，而 "obj" 一词在指向 object 的同时不放弃与 document 的对照。

每个 obj payload（slot 0，主表）的字节布局：

```text
[version u8][hot_len u16 BE][hot 段][cold TLV]
```

——与今天的 row 完全一致。声明字段保持现有编码：定宽字段在 hot 段连续排列，变长字段为 `[tag][len u32][bytes]` 帧排在 cold 段，tag = 声明序号。类型来自编译期 `FieldDesc` 表（`Row::FIELDS`），永不在字节里。

**动态段（slot 1）。** obj 可以额外携带未声明字段，每行一条记录存在 `[ns][1][key payload]`——与索引条目同一骨架（`[ns][slot][...]`，slot 紧跟 ns），中间没有字段段，主键落在尾段。每行的数据挂在行键下：不带 pkey 的话所有行的动态段会叠在同一个物理键上互相覆盖。共享的 `[ns][1]` 前缀也让整个段可前缀扫描（prune、重建）。其值为帧列表：

```text
[slot 1 value] = ([field-id][value-type][len u32][value bytes])*
```

- `field-id`：字段名字典编号（见下）。
- `value-type`：小型运行期值词汇表——这是唯一真正的新元素。声明字段的类型在编译期 FieldDesc 表里；动态字段必须自描述，其帧以一个值类型字节开头（int / float / str / bytes / bool / null / array / obj 保留变体）。嵌套可递归复用 obj 帧；词汇表先留保留变体，嵌套支持可后置。取帧方式是 **CBOR 衍生，不是 CBOR**：只取 major type 模式——每帧以类型 nibble 开头——结构编码也在同一方案里。CBOR 的 major type 含列表和映射；有了字段名字典，OKM 只需要列表——映射就是 nTLV 列表（编号、类型、长度、值），结构信息活在值里，不进 per-document schema。
- 顺序：帧按写入序排列；读取方按 id 寻址动态字段，不依赖位置。

**只有声明字段可索引。** 索引需要稳定的字节序和定宽比较键——自描述的动态值不具备。动态字段可读但不可索引；某个动态字段热到需要查询时，把它声明出来（一行 schema 改动加一次表重建）——这正是 row 模型一直在教的纪律。

## 字段名字典（slot 2/3）

动态帧以编号携带名字。字典是**运行期的、每表一个的双向映射**——OKM 存进 KV 的第一个可变词汇表（ns 保持编译期；ADR-0002"字典留在代码"说的是 ns 层，不适用于此）：

```text
slot 2: [ns][2][field-id]      → 名字字节   （编号 → 名字）
slot 3: [ns][3][名字字节]      → field-id   （名字 → 编号）
```

纪律，从 ns 字典复制：

- **Append-only。** 编号永不回收、永不重编。写路径首次见到某个名字即领取下一个空闲编号（单写者分配，由引擎互斥锁串行化）。
- **逃逸编号，而非重编号。** u8 迟早不够；重编已存储数据的成本过高（这正是否决重编的原因）。改为编号 `0xFF` 作逃逸：其后跟 `[0xFF][u16 id]`。扩展是 append-only 的，存量数据零迁移；字段数 ≤254 的文档每帧只付 1 字节。
- **扁平映射，不用 trie。** 双向都是引擎自身字节序结构上的 point get。trie 的名字前缀共享被评估并否决：常规业务名字共享前缀少，trie 的多级跳转与 UTF-8 基数开销换不来收益，扁平双向映射让编号→名字与名字→编号一样便宜。
- 也考虑过帧里直接放原始名字（完全不要字典）：对目标形态（MQ topic 内同表文档高度同构、名字强复用）是最贵的一端——每文档每帧都付完整名字。真正 schemaless 的表（每行名字都不同）字典退化为 1:1——不比原始名字差，且仍换来单一的查询结构。

**为什么首见分配优于推断和封闭枚举。** 目标负载是字段词汇有界但开放的交错流——Aura 的有限类型 event 以任意顺序到达 MQ、结构化日志有固定的时间/级别/事件加不可预估且持续新增的其它字段。两个标准答案在这里都失效：

- **首记录推断**（Elasticsearch 式）假设第一个文档揭示 schema；类型 B 在类型 A 之后到达，猜测就变成 mapping conflict 和运维事故。字典没有"首记录"概念：名字在它首次出现时领号，无论什么顺序。
- **封闭声明枚举**（编译期注册全部字段名）每来一个新类别就要重建——正是负载排除掉的不可预估性。字典在运行期吸收新类别，零重编译、零预估。

相比之下 type byte 保留在每帧：同一条流在相同帧位置交错不同的值类型，类型重复率不可假设，类型字典化一无所得。（完全同构的集合——数值列存形态——不是 object 模型的目标；它们由嵌套的声明式 obj 承接：重复结构在嵌套层恢复 hot 段 O(1) 偏移和索引，外层 obj 保持纯动态。）

## Slot 分配（修订）

```text
slot 0      主表                  [ns][0][key payload]
slot 1      obj 动态段            [ns][1][key payload]
slot 2      字段名字典            [ns][2][field-id]        → 名字
slot 3      字段名字典            [ns][3][名字字节]        → field-id
slot 4–13   保留（两端向中间增长的缓冲带）
slot 14     edge 正向             [ns][14][A·id][B·id]
slot 15     edge 反向             [ns][15][B·id][A·id]
slot 16+    索引与 reduce（声明序），[ns][slot][...]
```

固定角色自 0 向上增长；edge 居顶端（14/15）向下增长；4–13 是两侧增长之间未划分的自由缓冲——类堆栈内存布局。内部不做区域划分：未来的固定角色从需要的那一侧领下一个号，两侧相遇即耗尽。固定角色区与声明分配区的分界在 nibble 边界（`0x0?` 固定，`0x1?` 起声明），hex 测试一眼可辨。edge 的 14/15 两个 slot 属于"edge 走 slot"决策（PLAN Phase 10）——列在这里使表格呈现完整的终态分配；ADR-0001 的方向位 niche 被它取代。）

现有声明式 row 字节兼容：它们只是不用新 slot。保留段（4–13）是廉价保险（十个编号）；索引/reduce 从 16 起，单表可用 240 个编号，充裕。

## 改名：kv_ → ok_

属性家族 `kv_` → `ok_`（`ok_ns`、`ok_index`、`ok_ref`、`ok_subscribe`、`ok_default`、`ok_event_enum`），row 概念更名为 obj（`ObjEncode`）。`o` 是双关：编程语言中的对象，也是存储格式意义上的 object/doc/variant。改名随 obj 工作落地，赶在 crates.io 发布之前——发布后再改就是 breaking change。derive 宏名跟随同一词根（`KeyEncode`、`ObjEncode`）；`ObjEncode` 消失并入 obj 概念。

## 后果

- 单一编码、单一 derive 家族、单一解码路径；声明式 row 是动态段为零的特例，无需迁移。
- OKM 迎来第一个运行期词汇表（字段名），带 ns 字典纪律：append-only、逃逸式扩展、单写者分配。
- 动态字段的值类型成为线格式契约的一部分（okm-core 里一个小封闭枚举，schema 导出同步镜像）。
- 动态字段处处可读，但声明之后才可索引——schema 演化是刻意手动的逃生口。
- 实现由 PLAN 排期：ObjEncode 改名、slot 1 读写路径、字典维护、值类型枚举、schema 导出扩展。


## 更新 2026-09-19：帧长改为 varint（P2）

动态段帧 `[field-id][value-type][len u32][bytes]` 变为
`[field-id][value-type][len varint][bytes]`——长度前缀使用 `VarInt`
（P1）引入的前缀单调 wire 编码，在 `wrappers/wire.rs` 中实现一次，
字段包装器、动态段帧、Array 与嵌套 Obj 的元素帧共用。小帧的头部
从 5 字节降到 2-3 字节。元素类型词汇表、字典与排序规则不变。声明
字段的冷段帧（`[tag][len u32]`，ADR-0004）暂保持定长。
