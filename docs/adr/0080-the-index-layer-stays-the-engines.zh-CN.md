# ADR-0080 — 索引层留在引擎那边，因为代价是整台引擎

**Status：** 2026-11-23 裁决（无代码）。关闭 2026-11-12 记录的两份提案。**2026-11-23 更新，变宽那一侧：** 本 ADR 关闭时答不出的一刀现在有了形状——布局能从地址预测的键用改进编码，尾部字段变宽的键用现有帧格式。这是**按声明**的划分、编译期就知道，不是运行期分支；它消掉了前提那条反对，但两个数字一个都没动（§1、§3）。语料普查在 `docs/ideas/schema-aware-index.md`：五个仓、78 条索引声明，13 条（16.7 %）的编码段带变宽字段、键里一条都没有，而本 ADR 那次测量用的负载整条落在可改进那一侧——所以混着来只缩小覆盖，1.20× 天花板不动。

## 1. 提案说了什么

两份外部提案，一个前提，两个层级：进程内的 schema-aware 前缀树，和 SSTable 内的 schema-aware 块索引。共同论点是 OKM 在编译期锁定键布局——`ns` 是常量、索引字段宽度按访问方法已知、`segment_start` / `key_prefix_width` 已经在量布局而不是在假设——所以索引不必付「我不知道键长什么样」这笔通用税。

这个前提在定宽键上成立，在尾部变宽 `Str` 字段上变弱：那个字段是裸 UTF-8、无帧，截断的 `key(...)` 前缀只带主键的一部分（`PrefixKey` 的 `taken < KEY_LEN` 正是为此）。对这类 entry，路径不再复现键，「字节从地址即可知」之下的全部主张一起弱化成「大致可知」。两份提案都没说这一侧怎么办。

这一刀本身是现成的，而且**按声明**划、不是按行划：derive 知道字段宽度，于是一条索引要么 `key_prefix_width() == KEY_LEN`（完全可预测），要么不是——而 `model/index.rs` 拆 entry 时读的正是这个数（`segment` 加 `taken` 字节的 `tail`）。所以编码可以在声明处选：完全可预测的键用改进布局，带变宽 `Str` 尾的键保留今天的帧格式。第二类没有「下层 KV」可委托——索引 entry 就是同一个键空间里的键，走同一个 `VirtualStorage`，所以「保留现有方案」本身就是那份委托。它做不到的是移动两个数字：被改进的集合是 §2 所测集合的子集，天花板因此至多 1.20×；块布局那些条目也一条都没有变成 OKM 能改的东西。

## 2. 量到了什么

20 万行 fjall 语料、memtable 已封，一次取 1000 条的带取回索引查询 **943.8 µs**。其中引擎的索引读占 16.7 %——而索引重写真正会碰的那部分，搜索本身（块索引上一次下降，用空探针测），只有 **2.76 µs，0.3 %**。16.7 % 的其余部分是读那 1000 条查询正当要的 entry 并拆开；没有哪种树形状能让这些字节变得不必读。

所以这个负载上重写索引层的端到端天花板是 **1.20×**，现实数字接近 **1.0×**，因为搜索只占 0.3 %。点读 622.8 ns，其中文档层 32 ns：没有哪种树形状能改进「就是取一行」。

提案自己的头号案例也已经答过了：一个不存在的租户由前缀 Bloom 回答是**现有引擎上的 2.76 µs**，比扫那个租户的数据便宜约 110 倍——把它整个消掉，省一次查询的 0.3 %。

测量真正支持的是别处，而且已经存在：覆盖索引（193.6 µs 对 943.8 µs，**4.87×**），以及操作层——gallop 在偏斜输入上 **35×**。

## 3. 代价是整台引擎，不是一个特性

块索引清单上的每一条——定宽打包 entry 换零解析二分查找、footer 里的 per-ns 段目录、前缀 Bloom filter、块内键值分离、最短分隔符截断——改的都是块布局、过滤器位置与分隔符编码。在 fjall 里这些是实现内部、不是旋钮，其余引擎的过滤器与分隔符接缝同理。没有任何配置能碰到它们。

前缀树更糟：不是程度更糟，是种类不同。排序、持久性、恢复、压缩、快照与 seek 契约今天都归引擎（fjall / redb / slatedb）。在文档层之上放一棵前缀树不是 OKM 的一个特性，**是一台新引擎**——而一旦 OKM 拥有它，就永久拥有上述全部。

ADR-0010 把引擎设成边界，正是为了让这份所有权留在外面。两份提案都越过了这条线。

## 4. 前提是 OKM 的，不是引擎的

编译期锁定的键布局是这个系统少见的地方；通用 KV 引擎无法假设它，所以它的索引要付这笔税。这让提案自洽——也让它对任何 OKM 不自己写的引擎都不适用。既然收益约 1.0×、代价是 fork 或新引擎，前提为真并不让这笔交易成立。前提为真不等于购买许可。

## 5. 裁决

索引层留在引擎那边。两份提案都不设计、不排期、也不作为「差一半的备选」继续温着；记录在 `docs/ideas/schema-aware-index.md`，测量在 `docs/internals/query-cost-attribution.md`。

**重开条件：**两条同时成立，不是任一条——有一个测出来的负载，其中**搜索**部分是花钱的那一项（而不是它守着的那次取回），以及一个「自己拥有存储引擎」的裁决。两条都成立之前，这就是一份为 0.3 % 的科目重写别人组件的计划。

如果哪天真的拥有存储，块索引仍是两者中低风险的那条：它保留 SSTable 的页纪律、只改编码，而树要重做节点编码、分裂与序列化。

## 6. 被否的替代

- **靠配置 fjall/RocksDB 拿到其中一部分。** 不成立：块布局、过滤器、分隔符都是实际使用的那个 crate 的内部。
- **树放在文档层。** 直接是一台新引擎，为 0.3 % 的部件买下来。
- **只做块索引，当成有界改动。** 仍然是引擎的 fork；「有界」只意味着新代码更少，不是没有新代码。
- **作为「已记录、未设计」继续挂着。** 它已经记录并且已经测过；挂在 Open 会暗示测量还没做，而它的答案是 1.20× 天花板、现实约 1.0×。
