# ADR-0040：编解码的解码半边中止，而不是返回 `Result`

- **状态**：接受
- **日期**：2026-10-24
- **取代**：无。它限定 ADR-0037 / ADR-0038 / ADR-0039 的范围——那三篇给了面向存储的动词错误面，编解码一直被留在外面。

## 背景

ADR-0037 让读动词返回 `Result`（"存储答不上来就是一个 `Err`"），ADR-0038 把读故障挂到 scan 的 item 上，ADR-0039 对写动词做了同样的事。三篇都没碰**编解码**。它的解码半边签名上是不会失败的：

```text
DocumentEncode::decode_payload(&[u8]) -> Self      （derive 生成，每个行类型一份）
VectorElem::decode_le(&[u8])          -> Self
Vector::decode_payload(&[u8])         -> Self
ReduceCodec::decode_acc(&[u8])        -> Self
EdgeKey::decode(&[u8])                -> Self
rev_decode / offset_decode / varint_decode / dec_wire  -> Self
```

于是不匹配的字节从内部把进程打死——`try_into().unwrap()`、`expect("offset width")`，以及 `payload[p..p + W]` 这种在转换之前就先 panic 的切片。

在本仓的规矩"不许 `panic!`/`unwrap`；可能失败就返回 `Result`"之下，这看起来是约 40 行的机械转换。它不是：签名里没有放 `?` 的位置，而保持签名不变只有两个答案——**全部加宽**，或者**编一个值出来**。

## 决定

**1. 解码半边保持不会失败的签名，失败即中止。** 字节对不上时，带消息的 `unwrap` / `expect` 就是规定行为。

**2. 理由。** 编码器与解码器是同一件产物，一起发布。因此本 SDK 解不开的字节不是本 SDK 写出来的：版本或构建错配，或者绕过 API 直接写进去的字节（手工注入的裸 key、从别处恢复的备份、与另一个 okm rev 共用的存储）。这里没有"重新解释"可做——解码器若知道怎么读那些字节，编码器当初就会那么写。

**3. 中止也是这笔交易里更安全的一半。** 一个解错的文档不会停在本地：它被写回派生状态——索引条目、reduce 累加器、词汇表 id——损坏是静默且持久的。快速失败在第一个坏字节处停住，而不是把它扩散开；死掉的那个进程，正是拿着一个自己看不懂的存储的进程。

**4. panic 类 lint 只在编解码所在处放开，并且只在那里。** 每一处 allow 都就地写着理由：

| 位置 | 范围 | 理由 |
| --- | --- | --- |
| `okm-core/src/model.rs` | 模块（`model` 及其子模块） | 编解码本体——同一构建的编码/解码配对 |
| derive 生成的 `decode_payload` | 生成的函数 | 编解码本体，落到消费方的 crate 里 |
| `bridge/arrow_bridge.rs` | 整个文件 | 导出侧：我们自己的字节、我们自己拼的列 |
| `bridge/iceberg.rs::stamp_batch` | 函数 | field-id 压印保证的是我们自己的列位 |
| `SlatedbSync::open_mem` | 函数 | 构造，只跑一次：起不了 runtime/线程就没有存储 |
| `TestStore::slatedb_mem` | 函数 | 测试替身的构造 |
| `okm-vector/src/codec.rs` | 整个文件 | 存下来的 code 是本构建自己写的字节；`Codec`/`Prepared` 配不上、或 code 比它自己的 norm 前缀还短，说明这行来自别处，而编出来的距离会被直接折回图的边里 |
| `Nest::serve`、`Nest::apply` | 函数 | `serve` 被调用两次；scan 帧丢了它的 begin |

**5. 什么仍然是 `Result`。** 凡是字节来自外部、或存储可能答不上来的地方：存储动词（ADR-0037 / 0039）、scan item（ADR-0038），以及**导入**路径——由别的生产者写出的 Parquet 文件属于输入，所以列的实际 arrow 类型与声明不符时返回 `Err`（`column_as`，`tooling.rs`）；变体元数据帧改用 `first_chunk` 读取，不再是"先查长度再 expect"。判据是字节的来源，不是调用的方向。动态侧几乎整片都属于这一类——它的
schema 是以数据形式来的（走 JSON 往返）、字段名是运行时才出现的——所以冷字段没有 tag、
字段 id 用尽宽度、写到引擎被拒，在那一边都是 `Err`，不是中止。

## 边界：什么时候 panic 仍然是对的

本 ADR 只是下面这条规则的一个实例，规则不是「绝不 panic」，而是**「调用方对失败
做不了事的场合不 panic」**；`Result` 留给能对失败作出反应的那部分：

- **本来就要停的程序，`Result` 换不来任何东西。** 一次性运行——CLI 一次调用、
  迁移、批处理——编译期的过程宏、测试：它们本来就会停，panic 只是更早地停，还带
  行号和消息。把它改造成 `Result` 只是把同一次中止往上挪一层，并且让中间每一行
  都背上 `?`。
- **「用户得自己修环境」也是同一类，常住程序也不例外。** 配置文件不在，可以写一
  份默认的，也可以拒绝启动让用户自己创建；两者离「能用」都只差一个动作，区别只
  在报错信息友好程度，不在失败是否可处理。
- **编解码器是这一类的极端情形**：读不懂的字节来自另一个构建，既没有解释，也没
  有调用方动作，中止本身就是那条消息。

门禁针对的是相反的那一类：**必须继续运行**的代码——请求路径、serve 循环、后台
worker——把失败变成静默的错误数据（ADR-0038 的「`None` 即不存在」）或半应用状
态。在那里，`Result` 不是一个消息，而是一个决策点。

这也决定了 lint 的适用范围：在服务他人的 crate 上 deny。`bin/`、build script、
过程宏 crate、批处理工具上 deny 什么都换不来；若 workspace 已经统一 `[lints]`，
正确做法是给那个 crate 一个 crate 级 allow **并写明这条理由**，而不是把工具改造成
`Result` 泥潭。

## 后果

- **门禁写在 manifest 里，不写在评审者的习惯里**：`Cargo.toml` 拒绝
  `unwrap_used`、`expect_used`、`panic`、`unwrap_in_result`、`panic_in_result_fn`，
  九个成员全部继承，测试目标按 crate 单独放行。全 workspace 的
  `cargo clippy --all-targets` 干净；门禁也验过会咬人——临时插一处 `unwrap` 就会失败。

- **编译期那一面属于 allow 类，不是待改造队列**：`okm-derive`（130 条）与 `okm-core/build.rs`（9 条）在拒绝一个声明时本来就中止构建——中止就是那条报错，没有调用方能对它做事。按上面"边界"一段，它们拿到的是带理由的 crate 级 allow，而不是 139 个 `Result` 签名。哪里值得换成更好看的诊断（`syn::Error::to_compile_error` 带 span，panic 机制不带），那是逐点打磨，不是门禁前提。
- **持有外来字节的存储，现在会让读者中止。** 这是接受的代价。也正因如此，协议 rev 校验属于缝的位置：边界应当在编解码被迫面对之前就拒绝外来 rev。
- **"检测损坏字节"不是一个功能。** 若某个存储必须扛住外来字节，修法在边界（rev 校验、显式的完整性报告），永远不在解码器里。
- **上面的 allow 清单就是"允许 panic 的地方"的登记表。** 增加第四处需要修改本篇——这条约束让门禁不会因为习惯而放宽。

## 否决的备选

- **把所有解码都加宽成 `Result`。** 约 40 个直接点，外加生成的文档解码会伸进每个消费方的每条读路径。它换不到中止给不了的东西：对"这些字节不是我的"，调用方唯一合理的反应就是让这次读失败——中止做的正是这件事，只是早一帧，且没有半成品在传递。
- **解成默认值（`unwrap_or_default`、空行、零值字段）。** 等于编造数据，并在下一次写入时把它存回去。比另外两个选项都坏。
- **保留 panic 但不留 allow 清单。** 那样 lint 无法把这些 panic 与本轮正在清理的那些区分开，门禁要么永远落不了地，要么带着一片空白豁免落地——那正是"不许 unwrap"退化成装饰的方式。
