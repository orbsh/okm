# 0046 — 追加日志：一小时一个桶，时间存差值，词表要自己挣出位置

> **Languages:** [English](0046-append-only-log.md)（主）· [中文](0046-append-only-log.zh-CN.md)

**状态:** 提议 (2026-10-28) — 仅设计；尚未实现。**日期:** 2026-10-28

## 背景

需要的是一个日志：按时间顺序追加一条记录，按偏移或按时间读回，丢弃旧数据时不付逐条删除的代价。队列是它上面的一层，时间序列是它的一种用法。让它必须成为独立产物（而不是 okm 的一张表）的压力来自**保留**：被消费的消息和过期的采样点都是"没了"，而在 LSM 里每一条都留下一个 tombstone，引擎于是把压缩预算花在一张表上，效果只是变小（aura 的 `MqData` 正是这个形状：按 `HighWater` 序号追加，删到最慢游标之下）。

四条事实决定形状。

- **墙钟时间要以声明的精度活下来。** 队列要顺序，序列要时刻。每条记一个 `u64` 纳秒戳是 8 字节买一个几乎总是「比前一条大一点」的信息。
- **保留按时间，所以文件本身就是保留单位。** 任何"逐行丢弃旧数据"的做法都在复现这个日志想消除的问题。
- **载荷是 nTLV，不是不透明字节。** 通用消息队列存二进制、让每个消费者自造 schema；这份自由在 99% 的流里一文不值，只让每个消费者都写一遍解码器。nTLV 是一种自描述的小编码，转成别的东西只是遍历一遍条目。
- **字符串词表是个坏默认、好例外。** 字段名与取值只有二十种形状的事件流，intern 是大利；键(每条唯一)的流（id、请求路径、user agent），词表是纯亏而且无限增长。编码必须能在同一个文件里两种都走，而且**按证据逐键决定**。

## 决定

### 1. 桶：按墙钟一小时，一个目录

一个日志就是一个目录。`log.meta` 声明三件永不改变的事：`epoch`（创建时的 Unix 毫秒，给人看，也用于拒绝负时间）、`precision`（s / ms / µs / ns，写侧施加的量化单位）、`bucket`（每桶秒数，默认 3600）。

桶号 = `floor(unix_seconds / bucket)`。是绝对对齐，不是相对创建时刻：一个"小时文件"对机器上每个日志都是同一个区间，这才使得多个日志能按名字对齐、分片的目录列表才有意义。

<log>/log.meta<log>/LOCK                      单写者，进程生命周期内持有<log>/<bucket>/part-<n>.log     记录，只追加，靠改名封存<log>/<bucket>/part-<n>.dict    挣到了编码的那些字符串，同生同死

一个 part 由 `.partial` 改名封存（沿用 ADR-0045 的纪律）。part 可以因为体积上限提前轮转，于是同一桶里有多个 part，而保留就是 `remove_dir_all(<bucket>)`——每小时一次系统调用，没有 tombstone，没有扫描。

### 2. part 内的时间：一个基准加差值

part 头带 `first_offset`（u64）、`base_ts`（首条记录的完整时间，按声明精度）、`bucket`（u32，重复一遍让文件自描述）、`record_count`（封存时填，打开期间为 0）。

一条记录是：

[len u32][ts 差值 varint][nTLV 体]

`ts = 上一条 ts + 差值`，首条的差值是 `base_ts`。繁忙流的差值是一两个字节（任何精度下都如此），稀疏流就让它长大——varint 变宽，而不是让文件谎报分辨率。

**时间由写者盖，调用方给不了。** `append` 只收一个体。没有可以填错的时间参数，没有需要在配置里指定「时间字段名」的东西（指定了就必然和某个真字段撞，而且撞不撞事先说不清），也没有逐条记录去相信谁的时钟：日志在写入的那一刻读自己的钟，于是时间轴**就是接收顺序**。体里当然可以带应用自己的时间，用任何标签，那是数据，不碰记录的地址。

两个后果，都是刻意的：

- **不能回填。** 上周的样本无法写进上周的桶，它会被盖成现在。时间轴是接收顺序的日志，不可能同时是历史时间的仓库；假装可以，就是让「一小时一个目录」的布局开始对自己的目录名撒谎。
- **钟倒退就夹紧，不拒绝。** NTP 跳变、机器挂起、容器从快照恢复：调用方没有做错任何事，所以记录写在该流见过的最新时间上。两条记录可以共享同一个时间戳，偏移仍然排得出先后。

于是单调是**流**的属性而不是 part 的——这个区别在调用方还能给时间的时候是个真窟窿（更旧一小时落进更早的桶、开出没有历史的新 part，逐 part 比较无从谈起）。日志记住每个流见过的最新时间（打开时从各 part 恢复）并把它当兜底。（读侧把这个时间以它自己的名字交回——Python 绑定叫 `_ts`——因为体里是标签，没有名字。）

**没有逐条校验和，这是一个决定。** 给定 §3（没有 fsync 就不确认）以及「part 只在末尾写」，崩溃能造成的伤害只有截断尾：于是撕裂的那条记录就是 `len` 越过文件末尾的那条，这一条规则就是全部恢复过程。校验和并不能多抓一点崩溃——它能抓的是**存储栈说谎**（介质位翻转、网络文件系统、没真正发生的 fsync），而针对那种事的完整性属于字节的所有者：设备的 ECC、文件系统的校验、对象存储自己的验证。记录格式反正修不了翻掉的位，它只能拒绝读，把数据问题变成停机。这个基底负责的是**边界**：封存的 part 在 footer 里带整段摘要（§8），所以复制、导出、传输用一次哈希校验它搬的东西，而不是每条记录一次。

读一个 part 是顺序的：「从偏移 N 读」= 挑 part，然后通过它的区块索引（§8）在内部定位。

### 3. 持久性反过来

ADR-0045 是提交**之后**才追加，至多一次，洞靠重扫存储补。这个日志背后没有存储：`append` 只有字节 fsync 之后才返回偏移。代价不同（不批量就一次一条 fsync；接受窗口的调用方用 `sync` 动词），纪律不两样：被确认的记录在盘上。

### 4. nTLV，以及字符串去哪

条目编号承载字符串的**形态**，这才使得加宽是改一个字节，而且热路径没有分支：

- `n = 0` — 内联：`[len varint][utf8 字节]`。
- `n = 1` — 词表 #0，体长是该词表的宽度（u16）。
- `n = 2` — 词表 #1，宽度 u32。
- `n = 3` — 词表 #2，宽度 u64。

词表 #k 的宽度写在它自己的块头里（`u16 << k`），所以体长可推导，读侧不猜。同一个编码用在条目的标签半与取值半：nTLV 文档的**字段名**也是字符串，而无 schema 的流恰恰是它们重复的那种。

### 5. 什么时候一个字符串挣到编码：按自身宽度的分档

词表属于 part（见 §6）。part 开着的时候，写侧维护 `字符串 → (次数, id 或空)`，**次数达到它长度所在档位的阈值**就升格。单位是字节：`L` 是字符串字节长度，`W` 是它将要落进的那个块的宽度（2、4 或 8）。

| 长度 | 升格阈值 | 理由 |
| --- | --- | --- |
| `L <= W` | 永不 | 比自己的编码还短的字符串只会越存越大：一个字节的 `GET` 对上 u16，无论出现多少次都是亏 |
| `W < L <= 4W` | 10 | 短端：每次省得少 |
| `4W < L <= 8W` | 5 | |
| `8W < L <= 16W` | 3 | |
| `16W < L` | 2 | 长端：再多一次出现就已回本 |

最后一行正是「一条长错误消息在第二次出现时就进词表」不算特例的原因——那是档位在起作用；它也是「固定 10」不能作为整个策略的原因。

这张表是**配置而不是格式**：`[[4, 10], [8, 5], [16, 3], [0, 2]]`（编码宽度的倍数、升格次数；`0` 表示没有上界）。改它只改变**将来**的 part 升什么，读侧永远不需要知道——这是一个可调参数必须具备的性质。

分档表达不了、但同样重要的两件事：

- **门槛是绝对的。** 比自己的编码还短，无论多少次、无论怎么配，都不值得进词表。这是唯一不可调的一条。
- **计数按 part 划界，每小时从零开始。** 所以阈值每小时都要重新付一次：一小时出现九次的消息会被 `16W` 那档升格，永远不会被一个全局常数 10 升格。这是「只有短端才保守」的最强论据。

**为什么不用精确交叉点。** 记 `L_+ = L + 长度字段`，算式上的交叉点是 `f* = ⌊L_+ / (L_+ − W)⌋ + 1`——8 字节字符串对上 u16 是 `f* = 2`，也就是说分档在短端保守了 5 倍，在长端是精确的。这个取舍是有意的：早升格每次出现省 `(f − f*) × (L_+ − W)`，判断错只在一个 part 内亏一份字符串副本，而四行表是运维在凌晨三点能想明白的东西，一个带两个推导量的除法不是。如果某个 part 的词表在短端确实回本，就收紧那张列表——参数就是为此存在的，盘上什么都不用改。

晚升格不重写任何东西：更早的记录保留内联副本，这正是 part 的词表只增不改、文件保持纯追加的原因。键唯一的流什么都不升、全部内联：无限基数在这里是默认路径，不是失效模式。

计数不持久化。part 的计数量的是一个随 part 一起消失的窗口；持久化计数会成为第二个真相来源，而它服务的决定最坏只亏一份副本。

### 6. 为什么词表属于 part 而不是日志

日志级词表是诱人的设计（一张表、从头部链式扩展块），而在这个场景它是错的：

- 一个 part 必须**自包含**——它是保留单位、导出单位、也是复制或入湖消费方拷贝的单位。一个离了某个比它活得久的文件就读不出来的 part，不能单独丢弃、归档或搬运。
- 日志级词表只要有 part 引用了某条目就永远删不掉，于是需要引用计数或者 GC——而这类机制的失效方式是静默损坏。
- 频率在时间上局部。"这个字符串热不热"的窗口就是一小时，per-part 词表量到的正是这个窗口。

代价是重复：每小时都要的那个字符串，每小时存一份。它是有界的、可预测的，而且只落在本来就会重复的字符串上。

计数表的键是字符串的 64 位散列，不是字符串本身，并且到 2^20 个键就不再收新键。两条理由都是量出来的。为了计数而持有每个不同字符串的副本，意味着"每条记录都唯一"的字段（trace id、带 id 的 message）会把表塞满永远到不了分档门槛的字符串：在一百万条记录的 part 上，那是两百万个活着的 `String` 和每条记录 1,077 ns。散列键的碰撞只可能让某个实际只出现一次的字符串被提升——浪费一个编号，绝不会解析成错的文本，因为块和 `promoted` 表都以字符串本身为键。而一张只增不减的表等于没有上界，所以超过上限后新文本一律内联：计数器是策略的输入，不是发生过什么的记录。

### 7. 加宽链留在 part 里

词表 #0 在 `part-<n>.dict` 的固定偏移上（紧接头部），所以常见路径不需要间接寻址。每个块头带 `width`、`count`、`prev_offset`；一个块的 id 空间用尽（u16 的 65535），就追加一个宽度翻倍的块，它的 `prev_offset` 指向前一块。

链从最新的块**往回走**，而这正是它重要的地方：最新的块由 `<bucket>/part-<n>.dict.tail` 指名——一个四字节文件，靠改名替换。改名是原子的，于是「加宽词表」——过去唯一需要原地改头部的事件——变成又一次追加加一次改名。**因此一个 part 里没有任何原地修改**，这才是 §2 那个论断成立的前提：崩溃能损坏的只有文件的尾，而要紧的尾只有正在追加的那一个。读到 `n = 3` 却没见过 `n = 2` 的读者，沿 `prev_offset` 走两次。链是 per part 的，所以"加宽"最多发生两次。

### 8. 区块：压缩，以及让 part 可定位的索引

part 的体是一串**区块**：默认 64 KiB，各自独立压缩（zstd 1–3 级；CPU 比压缩率更要紧时用 lz4）。

- **按区块而不是按记录。** 一条 40 字节的记录单独压就是「头 + 噪声」——zstd 帧在开始省之前就要花掉十几字节。值得压的重复住在记录**之间**（同样的字段名、同样的 level 取值、同样的 URL 形状），只有区块能看见它。
- **全部区块，不是只压长的。** 按长度设阈值会让同一个文件长出两种形状，而且仍然不知道这条记录能不能压：压缩率是邻居的属性，不是它自己长度的属性。
- **在冲刷时压，不是封存时压。** 区块缓冲满就压，于是追加路径每 64 KiB 付一次（而不是每条记录一次），文件只写一遍。封存时压能拿到整个小时的窗口，但会把每次封存变成整段重写——几个百分点的压缩率换 2 倍写放大。

**与词表（§5）的重叠真实存在，而测量说它比纸面论证要窄**（`docs/internals/benchmarks.md`）：值来自小闭环集合时，intern 在压缩之上再砍四倍字节，而且因为交给编码器的体更小，不额外花写时间；每条记录带一个唯一 id 时，它用约 15% 的写时间换 3% 的字节。所以 `Config::dict` 是 per-log 开关、默认开，判断它不是「这是不是文本」，而是「这些值是闭环集合，还是每条记录都是新的」。

**压缩默认开（zstd 1 级），理由是测量而不是偏好。** 64 KiB 的块每约一千条记录才压一次，编码器的成本落在追加路径的噪声里：最难压的那种形状上，压缩 872 ns/记录、不压 857；而在压得动的形状上压缩一侧明显更快（357 对 347，文件小 22 倍——写系统调用搬的字节更少）。3 级不做默认：它在高度重复的数据上省 9% 的字节、其他形状上什么也不省，而**块大小比压缩级别更值钱**——同样 5 万条记录，16 KiB 块 2,267 ns/记录、64 KiB 块 942、256 KiB 块 556，因为每块的活（压缩、写、fsync、索引行）压过了每条记录的活。`Codec::Raw` 留给「体本来就是压缩过的」调用方。

索引刻意**不**逐块 fsync：它是派生数据，恢复时按块头重建，去掉那次多余 fsync 让写路径快了约三分之一（64 KiB 块上 1,345 → 882 ns/记录）。

索引是 `<bucket>/part-<n>.idx`，每个区块一行，在区块写出时追加——与日志本身同样的纯追加纪律，没有协调，没有封存期重写：

[first_ts u64][first_offset u64][file_offset u32][len_c u32][len_u u32][records u32]

定位：偏移 → 先二分各 part 的首行，再二分 part 内的行 → `file_offset` → 解压该区块 → 走记录。索引里唯一缺的区块是打开中 part 的最后一个，而打开中的 part 本来就是扫尾读。按时间定位白得：行按时间序，而每个 part 头本来就带着自己的区间。

索引为什么按 part、而不进 `log.meta`、也不按 bucket：

- `log.meta` 是**身份**——epoch、精度、桶宽——每个进程打开时都读、只写一次。往它末尾追加区块行，等于让身份无界增长，并把每 64 KiB 变成一次对共享文件的写。
- 一个桶里有 1..n 个 part，但自包含的单位是 part（§6 的论证，也是词表放在那里的同一个理由）：跨 part 的索引没法跟其中一个一起丢掉，而「保留 = `remove_dir_all(<bucket>)`」之所以成立，正是因为 part 旁边没有别的东西。

part 的 footer（封存时写）只带读者没法便宜推出来的东西：记录数、最后时间戳、区块数、整段摘要。**刻意不写的**：字节数（文件有长度、索引每区块一行）、首条时间戳（头部有）、词表条目数（词表文件自己数）。重述盘上已有东西的 footer 是一份可能跟原件吵架的副本。

### 9. 统计与分区：与 lakehouse 的类比到此为止

一个封存的 part 免费知道读者开口之前想知道的全部：从哪开始、到哪结束、多少条、盘上多少字节、多少词表条目。全是**物理**的，全是写的时候顺手得到的，而这正是与 lakehouse 的类比必须停下来的地方。

- **没有字段级统计。** 某个字段的 min/max/distinct 需要 schema、要扫一遍数据，而且回答的是「哪些行」——那是查询引擎的问题。那正是 Iceberg manifest 和抽干器写 Parquet footer 统计在做的事。长出字段级统计的日志，会变成一个布局更差、写路径更热的列存。
- **按字段分区是路径，不是索引。** 日志在创建时声明一个体标签，它的值变成目录：`<bucket>/p-<hex(值)>/part-<n>.log`。用十六进制，所以体能装的任何值都是合法目录名；`p-` 前缀把它和桶目录（纯数字）分开。写者每个分区保持一个打开中的 part；词表变成 per（分区, part），对「值得分区的那种字段」是更好的局部性；保留仍按桶，因为桶是时间区间、分区不是。
- **偏移属于流（stream），这是块布局的推论。** 块头只带它的首个偏移，读者从那里往上数——所以如果计数器是全局的，一个与别的分区交错写入的 part 根本读不回来。偏移因此属于 (bucket, partition)；没声明分区时属于日志本身，那是同一条规则只有一个流。跨分区读按时间序返回，而不是按目录序。
- **一个日志一个 `LOCK`，不是每个分区一个**——这是对本文最初写法的偏离。持锁的写者拥有根下的所有分区；分区级锁只在「两个进程分别写同一日志的不同分区」时才有意义，而现在没有这个需求。锁仍是「进程之间只有一个写者」成立的原因，但 pid 是**进程**的身份，看不见同一个进程里的第二个写者：同进程里为同一个 root 再开一个 `Log` 会通过 pid 检查，然后把自己的追加交错进同一个 part。以规范路径为键的进程内登记簿（`root`、`root/.` 和指向它的符号链接算同一个根）补上这一半，冲突时返回 `Error::AlreadyOpen`；条目随 `Drop` 移除，所以关掉再打开不受影响。
- 创建时声明、永不更改，理由和 `bucket` 不能改一样：读不出一个目录是哪种布局的读者，读不了它。缺少所声明标签的记录被拒绝（`MissingPartition`），绝不被塞进一个「看起来合理」的位置——会撒谎的布局读不回来。

## 后果

- 这个 crate 不是队列，也不是时序数据库。它没有 ack、没有重投、没有 per-consumer 游标（那是偏移之上的协议，可以住在它上面）；它没有聚合（那是对记录做 reduce，也可以住在上面）。它是「追加 + 读回」这一半，只做一次。
- 偏移是**每个流**一个写者的 u64 计数器——一个流是 (bucket, partition)，没声明分区时就是日志本身——重启后从该流任何 part 达到的最高偏移接着数（§9）。截断从不倒退它。
- 入湖这条路白得：一个桶目录本身就是一个窗口。
- **ADR-0045 的段不搬到这个基底上**，这条原来写的是反的。两者共享的是**约定**——一个目录、part 文件、改名封存、截断撕裂尾——大约一百五十行。不共享的是契约，而且三点上方向相反：这里每条记录都要单调时间（变更日志根本没有时钟，塞一个进去意味着 NTP 一跳就可能让之后每次提交的捕获变成错误）；这里每一条被确认的记录都先 fsync（变更日志是先提交后追加、洞靠重扫补，搬过去要么给写路径加一次 fsync，要么让这个 crate 的保证变成谎话）；这里的保留是时钟（那边是每个消费者一条水位线——段只有在湖那边拿走之后才能删）。同一套约定的两份实现是这笔交易里便宜的那一边；变更日志那份已经跑通、已经被抽干器读过。真正值得以后借的只有一件：段文件内部的块压缩，那是 `changelog.rs` 自己就能做的事，不必认一个时钟。
- okm core 一点不动。这是一个兄弟 crate（`okm-series`），只依赖 `okm-wire` 已有的 varint 与 nTLV 原语；它不实现 `VirtualStorage`，没有键、没有面、没有 reduce、没有 changelog，也不假装自己是一张表。
- 两个问题**故意不在这里回答**：第二个写者（复制）对偏移和词表做了什么；同一个日志被多个分片写时词表该不该共享。两个都改文件布局，所以两个都等真正需要它的需求出现。
