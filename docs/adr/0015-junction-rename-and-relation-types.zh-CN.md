# ADR-0015: Junction 改名与两种关系类型

日期：2026-09-17
状态：已接受（改名、双 ns 寄生与 2 字节 slot 段号制定案；ns 派生方案已否决；图 Edge 落地为 ADR-0017；字段位自动同步 `#[ok_relation]` 于 2026-09-20 分析后否决——命令式 link/unlink 成对操作确立为 junction 接口）

## 背景

现有 `EdgeEncode` / `Edge<S, E>` 类型名不符实。分析它的实际行为：

- 它存储的是**双向物化的关系条目**——FWD 与 REV 两条 key，value 皆为空，两条总是同时写入。图意义上的"方向"不存在（有向边携带非对称语义；这里的 FWD/REV 是同一事实的两个观察面，是为双向 O(1) 前缀扫描做的反范式冗余）。
- 条目 value 为**空**——无法携带关系属性（加入时间、角色、权限），而这正是 SQL 中间表的经典需求。
- ns 是**手工编号**（`#[ok_ns(4)]`）——ADR-0005 为索引消灭的负担（per-index 手工编号 + 洞簿记）在关系上原样重现。且手工编号引入失效模式：两条关系撞 ns（静默重叠）。

它实际实现的模型是 **SQL junction table**（多对多中间表，两端身份都在 key 里），双写物化以换取双向扫描。用图术语说，它根本不是边。

与此同时，嵌入文档工作（`Ref<D, K>` / `Refs<D, K>`）把一对多关系放进字段位，成为类型化的 key 引用；MODELING 的一对多一节早已描述过其物理形态（外键 + 列表，子文档在自己 ns 内范式化存储）。这让分类学出现一个命名空洞：多对多的对应物叫 "Edge"——读起来像图词汇，而项目并不实现图。

## 决策

### 1. 改名：Edge -> Junction

`EdgeEncode` -> `JunctionEncode`，`Edge<S, E>` -> `Junction<S, E>`。名字直说本质：连接表（junction table，SQL 对多对多中间表的正式称呼）。`Relation` 被否——在关系代数词汇里它指"任意表"，与 Collection 撞义。`forward_key` / `reverse_key` 保留：FWD/REV 双物化是机制的本质，这两个名字是准确的。

### 2. 双 ns 寄生：每个端点的 ns 各承载一个方向

junction 声明上的手工 `#[ok_ns(N)]` 移除。junction 的两个物理条目分别寄生于**两端文档各自的 ns**——每个 ns 一条，不需要第三个 ns：

```
ns_org  [ns_org ][slot 0x3nnn?][org·身份][user·身份]   // 从 A 端看（ADR-0016：
ns_user [ns_user][slot 0x3nnn?][user·身份][org·身份]   // 每端一条 entry，本端身份在前，
                                                       // 方向位在区分号低位）
```

junction 是**每条目单向**的：每条 entry 只回答一个查询方向（ns_org 里的回答“这个组织的全部成员”；ns_user 里的回答“这个用户所属的全部组织”）。两条 entry 是同一关系事实的两次写入——让两个方向都 O(1) 的双物化。无派生 ns、无哈希、无第三个命名空间：关系与它的端点住在一起，每端一条 entry。`nnn` 是 junction 区分号（`#[ok_junction(n)]`），区分同一端点对上的多条 junction；方向由条目所在的 ns 承载，不由 slot 位承载（ADR-0016）。

为什么否决派生独立 ns（早稿方案）：编译期哈希两端 ns 值被否决——不是因为撞号，而是**不确定性**。哈希出的 ns 是一个与端点关系不可见的透明度归零的数字，而项目的身份纪律（key 显式声明、ns 显式声明、不制造任何东西）延伸到关系存储：条目住在端点所在的地方。

**与普通索引的隔离**：slot 加宽并分段（ADR-0016）：**2 字节（u16，大端）**——4 bit 段号 + 12 bit 段内计数。普通索引与 junction 只差段号（`0x1` vs `0x3`），是结构区分而非编号约定。完整段表、文档自身段布局与后果（头增长、计数器解耦、hex 锁重写）见 ADR-0016——此处早稿的分配方案（字节宽段号、junction 在 `0x80`/`0x81`）在评审中被取代：方向完全移出 slot（每端 ns 一条 entry，见上），junction 只需一个段；段作为 16 项枚举，把其余位宽让给计数器。

### 3. 分类学：两种关系类型，两种载体

MODELING 的一对多一节早已描述物理形态；嵌入工作给了它字段级载体。全景：

- **一对多**：字段位的 `Refs<D, K>`——外键集合，子文档在自己的 ns 内范式化，单向（子 key 携带父身份；反查即对它的前缀扫描）。寄生于父文档；子不回指。
- **多对多**：`Junction`——一等关系事实，两端身份都在条目 key 里，双物化换双向 O(1) 扫描。不是字段：关系事实独立于任一端点的文档而存在；物理上是**双 ns 寄生**——每端 ns 各存一个方向（见决策 2）。

分界线即 MODELING 对 edge 与 index 已画出的那条：**关系能否从两侧都不经过全扫而找到？** Junction 说能（两条条目）；字段位 Refs 说不能（单向，反查 = 子 ns 全扫——在子 key 携带父身份的一对多场景，这可以接受）。

### 4. 复数建模的完整分类学（本轮补充）

建模文档需要一节完整的复数类型指南。按"元素是否有身份"与"同质/异质"两根轴：

- **一对多（元素有身份，单向）**：`Refs<D, K>`——上文。
- **多对多（双方都有身份，双向）**：`Junction`——上文。
- **向量（同质列表，作为整体使用）**：元素同类型，整体读写。存储：变长冷段 TLV 帧，与字符串同类——载荷 = [count u32 BE] + 元素；同质定宽元素是裸 V（每元素零开销），动态宽度元素逐元素 LV。长度是数据不是 schema；`#[ok_len(N)]` 是编码期应用合同（导出给动态 reader 作 `expect_len`；解码不检查——绕过解码器是读取者自己的问题）。典型用例：嵌入向量（okm-vector）、数值序列。get_document 时提升为 DynVal::Array——动态层没有 Vector 类型。多维形状是应用层解释。元素是纯值——不是关系载体。
- **数组（异质列表）**：`DynamicValue::Array`——元素类型可混合，动态段帧递归。
- **集合（set，去重元素）**：尚无载体。候选实现是倒排索引（元素值 → 持有它的文档主键），机制与 `#[ok_index]` 的多值函数索引（func 返回 `Vec<V>` fan out）完全同构——集合的"成员关系查询"天然是倒排形态。是否需要独立类型（`#[ok_set]` 之类）还是文档化"用函数索引表达"，待真实消费者出现再定。

分界线的判据不变：**元素有身份（要独立索引、共享、独立更新）→ Ref/Junction；元素是纯值（整体读写、无独立生命周期）→ 向量/数组**。

## 后果

- `EdgeEncode` / `Edge` 改名波及 derive、core、测试与四份文档（中英）。
- Junction 声明去掉 `#[ok_ns(N)]`——对下游是破坏性变更（aura mq.rs 无 junction 声明；k10r 无；迁移成本当前为零，这正是改名放在 crates.io 发布前的原因）。
- 手工 ns 移除同时是未来 `#[ok_relation(...)]` 字段位声明的钩子：文档中的 `Refs` 字段可以点名它的 junction，`put` 时 diff 字段与已存 junction 条目（自动 link/unlink）。记为未来工作——它用 RMW 换声明式同步，落地前需要一致性论证。（更新 2026-09-20：该方案已否决，见未来工作 §B。）
- junction 每条目单向：旧设计的"每条关系两个 slot（一个 ns 里的 14/15）"变成"每个端点 ns 各一条"——关系事实按端点 ns 各写一次，各自承载该 ns 要回答的方向。

## 未来工作（明确不在本 ADR 范围）

### A. 图 Edge——真正不同的类型

图边——有向、携带属性、可遍历——是不同的数据结构，用不同的名字（腾出来的 `Edge`）。属性是动态的（`DynamicValue` 形态，无 schema 预定义，无字段名压缩——动态帧本就内联携带名字）。「边名的 ns」问题（ns 是编译期声明的数字；"has"/"belong" 这类边名是字符串）：早稿的"从 `#[ok_edge("has")]` 字面量编译期哈希出 ns"方案随决策 2 一并否决（不确定性）。图 Edge 的命名空间机制（独立 ns 段内如何分配、边名如何进 key 或 payload）留待设计——与 junction 的双 ns 寄生不同，图边通常独立于任何端点文档存在，寄生方案未必适用。此处不进一步设计；尚无消费者。

### B. 字段位关系声明 + 自动同步 — 已否决（2026-09-20）

更新：`#[ok_relation(JunctionType)]` 经分析后**未实现即否决**。决定性论证链：

- 机制上是 Refs put-time diff（stale-release）的直接推广，机械成本不高；代价在语义：**junction 的真相源没有天然宿主行**。Refs 成立是因为父行是唯一所有者（结构上单向）；junction 的两端是对等的——单侧声明字段后，另一侧的 `delete` 无法清理（要么反向 RMW 链，要么残留字段 key 在下次 put 时复活已删的边）。
- 同一 junction 出现两个写入口（字段 diff + 显式 `link`/`unlink`）会互相打架：一个 handler 直接 unlink，后续保留字段的 put 又把旧 key diff 回来。
- diff 只有在反查是硬需求时才有收益——而"要不要这条边"正是 MODELING 已有的克制点。没有反查需求的关系本就不该建成 junction。
- 命令式成对操作（`link` 写两条、`unlink` 删两条）保住了"代码即事件"的性质：调用点就是因果记录，永不重建旧状态，写域也从不隐式越过对端 ns。

命令式成对操作确立为 junction 的接口。若未来出现真实消费者、确有"以单端集合形态整体重写关系"的需求，轻量出口是显式的 `Junction::sync_from(row)` 命令——同样的 diff，但是显式动词，不是 put 路径魔法。没有具名消费者前，勿再提案字段位形态。

### C. 向量类型的物化

已落地（PLAN P3.5，2026-09-19 第二版）：`Vector<T>` 冷段变长 TLV 帧——头存 count，同质定宽元素裸 V，动态宽度元素逐元素 LV；`#[ok_len(N)]` 编码期合同检查。本 ADR 锁定分类位置：同质、整体读写、冷段动态部分、与字符串同类。
