# ADR-0063：文档 map 是一个类型

日期：2026-11-12
状态：已裁决并落地 2026-11-12

**依赖：** ADR-0012（object 模型：一个 map 就是一条 n-TLV 列表）、ADR-0035
（整份文档 API：`fetch` 答的是 `Dict`）、ADR-0057（动态段的块表，按 map 的插入序写）

## 1. 背景

文档的「名字 → 值」map 过去在公开枚举变体里写成
`Variant::Map(BTreeMap<String, Variant>)`。这让容器本身成了 API，由此产生两件事，
而它们无法各自独立地解决。

**顺序是名字序**，因为 `BTreeMap` 会排序。文档是按名字插入的顺序组装出来的——先是解码出的
行的声明字段，再是动态名字在线上出现的顺序——这个顺序是**出处**：它就是这份文档被造出来的
方式。把它排序掉，等于让每一个在意「哪个名字在前」的调用点另找地方重新推出顺序，而别处
并没有记录。

**容器换不了。** `Variant::Map` 点名了它的载荷类型，所以每个写
`match value { Variant::Map(m) => ... }`、或在签名里接受
`&BTreeMap<String, Variant>` 的调用方，都把容器烙进了自己的 API。以后要换 map——
换成按插入序的、换成小 map 优化、随便换成什么——都会是跨每个 crate、每个下游调用方的
破坏性变更。

## 2. 决定：一个类型，通过显式方法清单给出表面

这个 map 是一个类型：`okm-value` 里的 `pub struct Dict(IndexMap<String, Variant>)`，
字段私有，`Variant::Map(Dict)` 是唯一写法。变体说抽象（一个对象：名字到值），
类型说承载它的东西，契约归这个类型。

表面是一份显式手写的方法清单，每个方法转发给底层 map：`new`、`with_capacity`、
`insert`、`get`、`get_mut`、`contains_key`、`remove`、`len`、`is_empty`、`iter`、
`keys`，外加方法承载不了的 trait 实现（`Clone`/`Debug`/`Default`/`PartialEq`、
`From<IndexMap<..>>`、`From<[(String, Variant); N]>`、`FromIterator`、`Extend`、
`Dict`/`&Dict`/`&mut Dict` 的 `IntoIterator`）。清单没点名的就不存在。
这份清单是从真实调用点推出来的，不是想出来的：删掉 `Deref`、编译整个 workspace、
编译器要什么就补什么。`clear`、`values`、`iter_mut`、`entry` 没有任何调用点，
因此不在清单上。

插入序就是契约：覆写保留名字原来的位置，新名字落在最后，`remove` 是 **shift 形态**
（`shift_remove`）——删除是把空位合上，而不是把最后一个名字挪进洞里；任何东西都不排序。
相等仍然忽略顺序，因为文档是名字 → 值对的集合；插入序是出处，不是身份。

## 3. 否决

**保留别名（`pub type Dict = ...`）。** 别名不是边界：它只是容器的另一个名字，
容器照旧在每一个签名里，它的整套方法照旧可达，包括那些会重排的。
要让边界存在，类型就必须是类型。

**在变体里直接暴露 `IndexMap`，再写文档说「别依赖它」。**
`Variant::Map(IndexMap<String, Variant>)` 一旦写下来就把容器冻进了公开 API——理由同 §1。
文档注释撤不回一个已经出现在调用方 `match` 分支里的类型。

**解引用到 `Deref`/`DerefMut`。** 这正是本裁决之前这个类型的样子，被否决有三条理由：

1. **强制转换是对外的泄漏。** `Dict` 若解引用到它的容器，任何地方任何接受
   `&容器` 的函数都能接受 `&Dict`。于是外部的签名点出了我们的底层 map——正是这个
   类型存在要来阻止的事——而且调用方可以自己写 `fn takes(&IndexMap<..>)` 再把
   `Dict` 传进去。容器从后门回到了 API 里。
2. **整套方法都暴露了。** 解引用把容器有的一切都放出来：`swap_remove`、`sort_keys`、
   `swap_indices`，以及其余。其中任何一个都能重排或改写 map，破坏这个类型存在的理由。
   一个「隔一次方法调用就能违反」的保证不是保证。
3. **解引用藏不住表面的一部分。** 没有办法解引用到「这张 map，但只要那十一个方法」。
   这里要的恰恰是部分暴露，而解引用在构造上就是全有或全无。

## 4. 后果

**换容器只改一个 impl 块。** §2 的每个方法都转发给 `self.0`；把 `IndexMap` 换成别的，
只改这些函数体，外加两个必须点名入参类型的转换实现（`From<..>` 与 `IntoIterator`
的关联类型），别的一行不动。调用方的代码一行不用改——被堵住的泄漏恰恰就是「本来得改」
的那一种。

**代价是一屏转发样板。** 这是这份保证的诚实价格：另一种做法是文件更小、而契约说不出来。
这个文件就是按「整份契约一屏读完」写的。

**存储的字节不受影响。** 编码写的是文档的 schema 声明序，动态段写的是按 map 自身顺序的块表
（ADR-0012、ADR-0057）；除了类型已经承诺的那部分，它们不看容器的排序。相等也没变
（名字 → 值对上的、忽略顺序的 `PartialEq`）。

## 5. 与 `Variant::Array(Vec<Variant>)` 的刻意不对称

`Array` 持有朴素的 `Vec<Variant>`，这一点保持不变。`Vec` 是规范序列：实现只有一个，
行为由标准库完整规定，点名它不花模型任何代价——没有藏起任何设计选择。按插入序的
「名字 → 值」map 不是这样：有序、散列、插入序、每名字内存都不同，这个选择通过迭代序
可见，而且是文档的读者唯一能观察到的东西。所以序列直接暴露、map 包起来。规则不是
「什么都包」或「什么都不包」，而是：一个类型承载了一个选择时，它才配一层包装；
map 的顺序是选择，向量的序列不是。
