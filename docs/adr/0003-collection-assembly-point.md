# ADR-0003: Collection as the sole assembly point; no KvRecord macro

Date: 2026-09-06
Status: Accepted

## Context

The original design had three macros: `KeyEncode` (key side), `ValueEncode` (value side), and `KvRecord` — an assembly-layer macro binding a key struct and a value struct into one record type with generated access methods (`#[kv_record(key = K, value = V)]` on a unit struct).

The rationale for a separate assembly macro was that key fields and value fields have different physical destinies (byte-ordered encoding vs serialized blob), so forcing them into one struct with attribute-based partitioning would blur semantics.

## Analysis

Binding key and value types does not require code generation at all. `Collection<S, E>` — a struct generic over the engine and the edge/record type — achieves the same with plain trait bounds:

- The binding is a type parameter, not generated code; nothing needs to be "expanded".
- A third macro means a third item to maintain, worse IDE diagnostics, and a redundant indirection the type system already provides.
- The original motivation (avoiding mixed key/value fields in one struct) is preserved by the two-macro split itself: key side uses `KeyEncode`, value side will use `ValueEncode` ([ADR-0004](0004-value-side-and-wrappers.md)); the assembly point consumes both via bounds.

## Decision

`KvRecord` is dropped. The assembly point is `Collection<S, E>` (runtime crate), parameterized by engine `S: KvEngine` and edge type `E: KvEdge`. Query methods are generated by `EdgeEncode` onto the endpoint types (e.g. `user.get_session(&edges)`), not onto a record marker type.

Atomicity note: `Collection.link()` performs the forward+reverse double write as one logical operation; true cross-collection atomic writes remain an engine-level property (one WAL commit over a shared batch) and stay on the engine side when needed.
