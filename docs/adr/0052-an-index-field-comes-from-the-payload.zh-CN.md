# ADR-0052：索引字段来自负载

Date: 2026-11-05
Status: Accepted

## Context

一条索引条目是 `[ns 2B][slot 2B][索引字段…][键尾巴]`，其中**数据段**——紧跟头部、参与排序的那一段——由文档生成。`KvIndex::encode_named` 同时收到键与文档，但生成的实现里每个名字都取自负载；`fields(...)` 与 `includes(...)` 在展开期按负载的字段表校验。

关系表的反向读正是靠这条成立（ADR-0051），而代价也被它定死：键里已经有的字段，行上也必须有，否则声明写不出来。`memberships` 为此付两次——一次是行负载里的那一列，一次是条目在数据段之后追加的尾巴：

```text
[ns 2B][slot 2B][member_id 16B]   [channel_id 8B][member_id 16B]
                 ↑ 来自行上的列      ↑ 完整主键
```

同一批字节还有另一种读法——让 `fields(...)` 命名键里的字段，使数据段与尾巴都来自键——没有采用。理由值得记下来，因为它看起来像白捡的字节，而且还会被再提一次。

## Decision

**索引字段是负载字段。** 声明里的名字按文档解析，条目的数据段在写入时从文档编码，键只负责尾巴。`key(...)`（ADR-0016）决定尾巴装主键的哪一段，它不改变数据段的值从哪来。

读侧依赖的两条后果：

- 尾巴完整（`KEY_PREFIX` 为空）意味着 `taken == Key::KEY_LEN`，扫描能解出整条主键并在同一次调用里回表；
- 尾巴被收窄意味着 `taken < Key::KEY_LEN`，边界之后的字段补零，扫描只给键、不给行——主键由调用方自己拼。

## Rejected：让数据段从键取

**省下的。** 行上那一列（每行 16 字节）与条目里的第二份（每条 16 字节）：`Uuid7` 身份放在 8 字节容器键里，条目从 44 降到 28 字节；u64 的对从 28 降到 20。查询侧不会变慢。

**付出的。**

1. **`fields(...)` 的编译期校验，而且对所有声明生效。** 键结构是另一个 derive，在文档的展开点不可见，于是「不是负载字段」与「打错了」不再可区分：检查从编译器挪到第一次写入（`unknown group field: <name>`）。这是唯一落在被改声明之外的代价——索引字段表不再在写它的地方被验证。
2. **类型化探针 builder。** 它的每一步由负载字段的类型生成，类型同时给出宽度与顺序。键字段没有负载类型可命名，只有运行期的 `KeyEncode::FIELDS` 表，所以从键取字段的索引不发射 builder，查询侧传裸字节——只在调用方的编码与声明一致时才正确。
3. **一种索引形态变两种。** 负载作为唯一来源时，每个索引的契约都一样：字段是行字段、`taken == KEY_LEN`、扫描给键和行、builder 存在。从键取把这份契约劈成两种形状，而它们的差别在调用点是**看不见**的——读的人得先知道某道索引的字段来自哪儿，才知道 `decoded` 是否完整、会不会回表。

每行每条 16 字节，买不起第二种索引形态和一个更弱的检查。

**什么条件下会翻。** 不是体积——`KeyEncode` 的键按契约定宽，复制永远放得下。翻的是当这份复制**变错**而不只是冗余：出现「索引条目可证明等于身份」这类不变量，列与键的分叉不再算写者的 bug 而算正确性洞。真要重开，得先把上面两条付掉：一是能活下来的编译期检查（对 `Key::FIELDS` 的 const 断言），二是让 `PrefixKey` 带上「尾巴 + 数据段字段 → 整条主键」的重建规则。

## Consequences

- 关系表的反向读保留那一列。条目把字段存两次、尾巴存完整主键；一次扫描给回键和行，两段解码值都是真的。
- `rebuild_faces` 从键**和**行重新派生条目——这正是复制必须落在行上的原因：只有键产生不了数据段。
- 字节布局与读侧的算术在 `docs/MODELING.*`（多对多那节）；本篇拥有的是裁决，不是那张表。
