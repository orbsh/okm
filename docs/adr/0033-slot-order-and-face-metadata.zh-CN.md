# ADR-0033：slot 留在 ns 之后，面的元数据留在面上

**状态**：已接受（2026-10-21）——布局规则如文所述；本文不改动任何代码。
**日期**：2026-10-21
**英文版**：[0033-slot-order-and-face-metadata.md](0033-slot-order-and-face-metadata.md)
**依赖**：ADR-0002（ns 词汇表）、ADR-0012（字段名词汇表）、ADR-0030（固定面与计数族）、
ADR-0032（分配游标）

## 背景

每个键是 `[0xFF][part]（可选）[ns 2B][slot 1–2B][后缀]`，而 slot 用高半字节自带宽度：
`0x00–0x0F` 是固定面（一字节），其余是计数族（两字节、12 位计数）。ADR-0030 又允许每张面在
**裸前缀**上放一个元数据值——`[ns][slot]` 不带任何后缀——成立条件是该面所有真实条目至少带
一个后缀字节。ADR-0032 用它放词汇表的分配游标（id 面上的零长度后缀）。

随之而来三个问题，既有记录都没回答：

1. 迭代会走过自己起扫的那张面吗——从一个 slot 越到下一个，以及跨过一字节/两字节的接缝？
2. 既然数据和元数据共用一张面，长度判断的代价是多少——按每个键，还是按每次扫描？
3. 如果这代价真的高，元数据是否该搬离数据；同理，slot 是否该挪到 ns 前面？

## 决策

**1. 迭代由前缀端点界定，不靠逐键检查。** `scan_suffix(p)` 就是
`scan_range(p, prefix_end(p))`（`engine/storage.rs`），而 `prefix_end` 是字节序后继：末位小于
`0xFF` 就加一，遇 `0xFF` 进位，全 `0xFF` 则无上界（只有整串 `0xFF` 才会——真实 header 不会）。
端点是**在 prefix 长度上**的排他界，于是：

```text
[ns][0x02]          → end [ns][0x03]        0x03 面在界外
[ns][0x0F]          → end [ns][0x10]        [ns][0x10][nn] 排在 [ns][0x10] 之后
[ns][0x10][0x01]    → end [ns][0x10][0x02]  下一个计数在界外
```

第二行是两种 slot 宽度唯一可能相撞的位置，而它不相撞：键排在自己的前缀之后，所以更长的族键
落在"以一字节形态结尾"的区间之外。读路径里没有任何逐键边界校验，也不需要。唯一能越面的方式
是自己调 `scan_range(begin, None)`——引擎的无界形态，OKM 自己的读路径在遍历面时从不用它
（树里唯一的 `None` 是 `NestStorage` 对自身前缀空间的宿主键扫描）。

**2. 后缀长度就是分离手段，代价是一次比较。** 面的真实条目要么恰好 `N` 字节（词表 id 面），
要么至少一字节（图面的 `edge_id` 尾段）；元数据条目是零字节。读者按长度区分，也就是对内存里的
长度做一次整数比较：不读值、不分配、不逐字节遍历，每张面最多跳过一条。它只出现在三种形状里：

- 枚举面且不能把游标当数据的读者：`Graph::predicates`（`suffix.len() == 2`）、
  `VocabMirror::load`（同）、导出的 id → label 扫描（`suffix.len() != f.width`）；
- 部分索引匹配（`index.rs`）：`suffix.len() == taken` / `>= taken` 加一次减法——这是**正确性**
  条件而非边界检查：探针可能被键的尾段字节满足，只有长度能说明是哪一种；
- 别处没有。定宽解码器本身拒绝长度不符（`VocabId::from_be` 只收正好该宽度），所以漏了过滤
  得到的是拒绝，而不是错的 id。

本文不声称任何实测数字，能确定的是形状：每个被枚举的条目 O(1)、无 I/O，并且融在本来就要解码的
循环里——与引擎的键比较加值拷贝相比是噪声。

**3. 面的元数据留在那张面上。** 两种"分开"的做法都被否掉：

- *单开一个族*——早先的 `0x3nnn` 游标设计。它把索引挪到 `0x4nnn`、reduce 到 `0x5nnn`、
  junction 到 `0x6nnn`（这个顺序在 2026-10-20 被撤回），而且把"某张面的水位"变成"又一个族的
  实例"：它描述的是一张面，却与各家族平级存放。
- *单开 keyspace 或前缀区*——游标不再被 collection 的 ns 覆盖。drop、清 ns、按 partition 的
  隔离范围都盖不到它，漏清就会把旧 id 发给新数据，而且是静默的；"词表增长 + 行 + 游标同批提交"
  也变成跨区提交。

同面存放不要代价，因为区分是**结构性**的（0 字节与 `N` 字节，后者不可表示成数据），不是运行期
猜测——ADR-0030 的规则已经是这条保证。

**4. slot 留在 ns 之后。** 挪到前面（`[slot][ns][后缀]`）会：

- 让 ns 的偏移不再固定——slot 是一或两字节，每个读者都得先解出 slot 宽度才能找到 collection
  的身份；
- 把 `0xFF` 的 partition 转义挤离首位。它之所以合法，正因为合法 ns 永不等于 `0xFF`
  （ns 词表是 `0x00–0xFE`）；slot 的值域 `0x00–0x5F` 正好占着那个位置；
- 让一个 collection 不再是一个连续区间。今天"属于这张表的一切"就是前缀 `[part][ns]`；slot
  前置后它按面分裂成若干段，任何整表操作都变成 N 次按面循环，或全库扫描 + ns 过滤。

换来的只是一次整数比较。

## 考虑过的替代

- **保留值当哨兵**（一个特殊 id、一个特殊长度）代替零长度键：ADR-0030 已否——分离必须是结构性的。
- **扫描时逐键做边界校验**（拿每个键的后缀长度对照该面声明的宽度）：多余。前缀已经界定了迭代，
  解码器也会拒绝宽度不符；加上它只是每个键多一条分支去重算一个编译期常量。
- **把元数据塞进别的条目的值里**（例如停靠在 ns 词典中）：每次分配多一次读，而且写入不再与它
  管辖的那些条目同族同批。

## 后果

- 只要一张面的所有真实条目至少带一个后缀字节，它就能在裸前缀上放一个元数据值——不占 slot、
  不占族、无需迁移。词汇表游标的全部代价就是这些。
- 定界规则是承重的：将来若出现 `0x0F` 以上的固定面、或 `0x10` 以下的计数族，接缝会静默失效。
  `FIXED_FACE_MAX`、`write_slot` 的断言和十六进制锁定测试就是守住它的东西。
- 枚举面的读者必须按宽度过滤；拿点键的读者永远不会碰到游标。
- 整表操作仍然可以写成每面一次前缀扫描；将来真要跨面遍历，就写显式的多前缀循环，绝不写
  "全库扫 + 过滤"。
- 布局错误不会自我暴露：一对词表的 id 面指到了邻居的 slot，本地检查全过，只会表现为跨进程边界后
  id 重开。所以每个族都要有自己的测试——
  `graph_edge_test::the_predicate_cursor_is_the_id_faces_bare_prefix` 钉住 `[ns][0x04]`、
  "不写字段名词汇表游标"，以及"重启后从游标续号"。
