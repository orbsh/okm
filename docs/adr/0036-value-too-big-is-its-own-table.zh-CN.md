# ADR-0036：字段太大，放进副表

**状态**：拒绝——`#[ok_offrow]` 不实现，定案是副表
**日期**：2026-10-23
**英文**：[0036-value-too-big-is-its-own-table.md](0036-value-too-big-is-its-own-table.md)

## 背景

一份 payload 把所有声明字段装进 `[ns][0x00][pkey]` 底下的同一个值：定宽字段连着摆在热段，其余是冷段的 TLV 帧（ADR-0004、ADR-0006）。所以只要有一列的体量比别的列大几个数量级——一个 blob、一份渲染好的文档、一个 embedding——它就带来两笔代价：读这一行必然把它整个读出来，写这一行的**任何**字段都要把它重编一遍。

提案（`#[ok_offrow]`，PLAN 2026-10-22 批准，次日撤回）：给声明字段打上这个标注，它就离开 payload，住在自己的键下，于是按名字更新的路径可以只写这一列而不重写行。

- **布局**：所有 off-row 字段共用一张固定面，`[ns][0x0C][pkey][ordinal u16 BE]` → 裸值；`ordinal` 是 off-row 字段之间的声明序，append-only。一次前缀扫描 `[ns][0x0C][pkey]` 取回一份文档的全部 off-row 字段。
- **类型面**：off-row 字段不出现在生成的结构体里，默认访问路径（`get` / `put`）因此永远不为它付钱。derive 为每份文档生成一个 tag enum（一个 off-row 字段一个变体，discriminant = ordinal）外加**一个**字段级访问方法，用这个 tag 选择要读的列；整文档的 map 动词按名字把请求路由到列上。假如字段留在结构体里，本来还要一个解码后回填的钩子。

两半各自都是对的——诊断（整体访问会让这个功能失去意义）和选择子形态（一个 tag enum 而不是每字段一组方法）都是对提出来的那个问题的正确回答。

## 决策

**不实现，也不在行 codec 内部给它找替代机制。** 这件事由副表完成，键类型就是父表自己的键类型：

```rust
#[derive(DocumentEncode, Clone, PartialEq, Debug)]
#[ok_ref(PostKey)]          // 同一个键类型：key payload 逐字节相同
#[ok_ns(44)]                // 自己占一个 ns——这就是全部代价
#[ok_name("post_payloads")]
pub struct PostPayload { pub mime: String, pub body: Bytes }
```

读一列 `payloads.get(&key)`（一次点读，行根本不解码），写一列 `payloads.put(&key, &payload)`（一次行写，热行根本不重编），成对地写则父表与副表各 `save_with_prev_into` 进同一个 `MemBatch`、再一次 `commit_batch`（ADR-0003、ADR-0031），所以这一对是一次提交。建模侧的案例写在 [MODELING](../MODELING.zh-CN.md#字段太大放进副表)。

三条理由，按它们定案的顺序：

### 1. 复杂度提升很多，实质的功能提升不大

off-row 往行模型里加第五个存储位置，而行布局的每个消费方都得学会它：`FieldDesc` 多一个维度（payload 热段 / payload 冷段 / off-row）、`FieldSchema` 多一个桶、`split_names` 多一个必须挡在动态段之外的名字、`fetch` / `merge` / `replace` / `purge` / `delete` 各多一个分支、tag enum 需要 trait 关联类型加一张 const 表、四条 derive walk 要跳过这个字段、一个最终没人用的解码后钩子、一个写侧条目生成器，还有动态门面的 plan 面。每一处都是"此后永远要记得这个标注"的地方，每一处记错都是静默的——一个声明了却没编码的字段，或者一个落进了错误段的名字。

这份复杂度换来的、副表给不了的东西只有一样：整文档读一次 round trip 而不是多一次点读。而"整文档读要把大列一起读出来"恰恰是这个拆分本就不想付的那次读。

### 2. 接口语义上的冲突

ADR-0035 前一天刚落地的规则是：文档面就是一个名字键 map，一次写就是一次提交。off-row 在五处与它相撞：

- `R` 不再是文档。一份 `Document` 的声明字段不在它自己身上，就是声明与自己的类型不一致。
- `fetch` 要么漏掉一个声明列（一个静默丢字段的投影——正是 ADR-0035 要消除的那种谎），要么每次使用都付一次扫描。
- `replace` 不能再表示"这张 map 就是文档"，于是被文档承诺的等式 `replace(&空 map) == purge` 不成立：要么 off-row 的数据在整文档替换之后还活着，要么 `replace` 对一个它平时从不碰的面加一趟清理。
- `put(&R)` 不再表示"这份文档的状态"：off-row 的列在它之后存活——行为是对的，类型却不再表达它。
- `purge` 要读存储行，有段时还要读段；多一张 off-row 面就是每次 purge 多一次前缀扫描。

而那个字段级访问方法，是给一个名字键 map 已经选得动的东西再加第二个选择子：tag enum 带不了字段的类型，访问方法只能返回一种擦除后的货币（`DynamicValue`，或裸帧字节），于是编译期就检查完的声明类型退化成边界上的一次运行期检查。这个机制真要建的话，tag enum 仍然是正确的选择子——它给出对文档各列的穷尽性、并把 ordinal 钉在代码里——但它是在项目刚刚统一起来的那个面之上再加一张面。

### 3. 简单方便的替代方案：独立 ns 同主键存储

一张键类型为父表键类型的副表：

| | off-row 标注 | 副表 |
|---|---|---|
| 键 | `[ns][0x0C][pkey][ordinal 2B]` | `[ns'][0x00][pkey]`——与父表主键同长 |
| 读一列 | 1 次点读 | 1 次点读 |
| 写一列 | 1 次键写 | 1 次行写 |
| 成对写、原子 | 1 次提交 | 1 次提交（ADR-0003 批） |
| 成对删、原子 | 1 次提交 | 今天 2 次——公开的 `delete_from(batch)` 还缺 |
| 可建索引 / reduce 分组 | 禁止（索引键要定宽） | 允许 |
| 一行多列 | 一字段一帧、一张面 | 一行，形状随意 |
| 自己的 `#[ok_layout]` 版本 | 没有 | 有 |
| 导出 | 要改 bridge（带上 0x0C 面） | 免费——export/import 是 per `(K, R)`（ADR-0034） |
| `R` 保持完整 | 否 | 是 |
| 新增机制面 | 行模型里九处 | 零 |

标注唯一赢的一行，是"整文档读并且要连大列一起读"：一次 round trip 而不是两次。副表里那一行是否存在，也比"键缺席"更适合当"有没有 payload"的标记：它就是一个状态，不是一次缺席。

## 为什么不

- **标注与副表并存。** 那就有两种说法表示"这个值住在别处"，此后必须永远互相保持一致——正是前一天让六个按槽切分的旧动词退役的那个毛病。
- **只标注 payload，不动访问面**（字段留在 `R` 里、读时用解码后钩子回填、`put` 时把所有列都写一遍）。这是"不改 API"的那一版，也正是提案自己否掉的那一版，理由成立：那时 `put(&R)` 只是把同样的字节写到另一个键下，标注一点东西都没买到。
- **off-row 面用一个计数族**（`[ns][0x6n][pkey]`）。提案内部已经否过：它买到的是一次没有消费方需要的跨行扫列，代价是每份文档 #fields 次点读。
- **把大列塞进动态段**（槽 1）。槽 1 和行一样每份文档整段重写，隔离不了任何东西；而且那是无 schema 区，不是声明过的、有类型的列该待的地方。

## 后果

- 没有代码、没有 schema 变更、没有迁移。`FieldDesc`、`FieldSchema`、四个文档动词、derive 的 walk、动态 plan 面全部原样。
- 建模规则作为案例写进 MODELING（中英）：同一个键类型、自己一个 ns、写的那一对走一个批；并记下删的那一对归调用方（这个模型里没有级联——junction 是同一个形状）。
- 两处声明代替了原来的一处。配对由编译器钉住：副表复用父表的键类型，所以 key payload 构造上逐字节相同，只有 ns 与表名不同。
- 这个决定只留一项接口面工作：公开可进批的删除（`Collection::purge_into(&mut MemBatch, &K)`，包住已经私有的 `delete_into`）。它记在 PLAN 里，不在这篇里。
- 重新打开要靠证据，不靠口味：payload 进入多 MB 量级、整文档读必须一次 round trip、并且测出副表多出来的那次点读就是瓶颈。今天没有任何消费方接近这个形状。
