# ADR-0029: 路径索引——在无 schema 区上声明的路径

**状态**：已接受（2026-10-14）——实现随本决策落地
**日期**：2026-10-14
**英文版**：[0029-path-index.md](0029-path-index.md)
**依赖**：ADR-0012（字段名词汇表）、ADR-0016（4 字节头与 slot 段）、ADR-0020（范围扫描）、ADR-0022（动态访问方法）、ADR-0025（两个 schema 载体）

## 背景

动态段是"无 schema 区"：嵌套对象与数组以 nTLV 帧存放在那里，字段名经每表的字段名词汇表入典（ADR-0012）。而针对这一区的访问方法在实践中只覆盖 **schema 声明过的字段**——`AccessMethod::plain` 命名的字段由 `find_field` 在 schema（key/hot/cold）里解析，于是"嵌套对象里的某个位置"或"某个数组元素"没有声明式的表达。宿主当然可以写 `Func` 索引（可调用对象收到解码后的文档、返回编码字节），但那等于把字节布局知识和值类型下推到每一种宿主语言、每一条索引各写一次。

已经存在、本文档不算新东西的部分：

- 字段名词汇表给每个动态字段一个**定宽句柄**（u16，紧凑车道：`< 0xFF` 一字节，`0xFF` 转义接 u16 BE）；嵌套对象的字段 id 走同一本词汇表；
- `DynamicCollection::declare_index` 本就支持运行时声明访问方法，slot 由调用方分配；
- 索引条目本就共用一种布局——`[ns 2B][slot 2B][索引段][pkey]`，值 = includes 段；
- 多条扇出（fan-out）本就是已有形态（`Func` 返回 `Vec<Vec<u8>>`）。

## 决策

**路径是一等的声明值，有自己的组件词汇；路径索引声明一条路径，外加它条目排序所依据的值类型。**

1. **`Path` = 组件序列**，组件三种：
   - `Field(name)`——对象键，经字段名词汇表入典（**稳定身份**）；
   - `Index(u32)`——数组位次（**数据**：不入典，且不跨变更稳定——一次前插会移动其后所有位次）；
   - `Key(bytes)`——按字面携带的对象键，不入典。

   `Field`/`Key` 与 `Index` 是两个命名空间、两种 walker 操作（map 取值 vs 数组下标），不是同一个东西的两种写法。把它们合成一个整数，等于把某个 id 空间藏在隐式约定后面——正是 ADR-0001 的 ns 方向位被否掉的那种失败。

2. **规范字节形态自定界，且不前置组件计数**：

   ```text
   Field → [0x01][handle]         handle：u16，紧凑车道
   Index → [0x02][u32 BE]
   Key   → [0x03][len][bytes]     len：紧凑车道
   ```

   不前置计数的理由：
   - 一条路径是它一切扩展的字节前缀，于是"扫这条路径下的全部"仍是一次前缀扫描；
   - **计数会让"深度"变成排序主键**，同一子树的条目不再相邻。这是承重理由而非微优化：`[2][a][b]` 与 `[1][a]` 相比，所有 1 组件路径都排在所有 2 组件路径之前；
   - 数组通配不需要第三种组件——它**就是"没有 `Index`"**，而 `[a]` 仍是 `[a][0][b]` 的字节前缀；
   - 深度可由遍历得出；计数只买 O(1) 深度。

3. **一条声明路径占一个 slot，路径本身不进条目键**（slot 就是路径的身份）。条目键仍是 `[ns][slot][值][pkey]`，于是值的宽度由声明决定、条目保持静态可切——不引入"先走路径、再切值"的第三种键制式（这一层只有两种：静态偏移，以及末尾变长尾巴）。

4. **值类型由声明给出，绝不推断**。条目段是字节有序的；主文档的类型来自 `FieldSchema`，而路径没有 schema 字段可查，所以类型随声明。只接受有既定编码的类型（U8/U16/U32/U64/FixedBytes/Str）——类 wrapper 的类型在**声明时**就被拒，而不是每次写入才失败。

5. **数组在写时扇出**：每个解析出的值一条条目。变体与声明类型不符的值不产条目、也不报错（异构数组是正常数据——"属性缺失即空结果"同一条规则），路径缺失同理。

6. **路径索引挂在动态段的写路径上**（整文档写 `merge` / `replace` / `purge`，ADR-0035），绝不挂在主文档路径上。主文档只装 schema 声明的字段，那里深度为 1 的路径恰恰就是 `Plain` 已经索引的东西；嵌套内容只存在于无 schema 区。**一个条目集合只有一个维护者**：主路径的 `index_entries` 有意跳过 `Path` 声明。

## 后果

- 声明面就是一个构造器：`AccessMethod::path(slot, path, value_ty)`。
- 覆写时从存储的动态映射重算旧条目集合来清扫（条目按解析值定键），因此值变更不会留下悬挂条目——与主路径既有规则相同。
- 一条路径索引的字节开销与任何索引相同（路径不进键）；写放大 = 每条声明路径 × 每个解析值一条条目。
- `Path::encode`/`decode` 覆盖的是"路径作为数据"时的形态（声明载体、导出的 schema）。它们**天然以表为作用域**：句柄来自该表的词汇表，所以一条路径只能对着写它时的那张表解码。
- 查询面不变：最左前缀扫描把路径索引当 func 索引看（段宽是调用方的事，因此任意前缀——包括空——都合法），值的区间由 ADR-0020 的范围扫描覆盖。
- 有意排除：通用的"所有路径共用一个 slot"的嵌套值索引。它会把变长路径字节塞进条目键，并迫使键层进入 walk-then-slice 制式；声明即注册，所以"一路径一 slot"就是形态。

## Update（2026-10-14，落地）

记录下来是因为草案与代码不同，免得下一个会话把差异读成 bug 而不是精化：

- 草案把组件写成 `Field(u32)`；词汇表的句柄是 **u16**，编码直接复用词汇表自己的紧凑车道（`< 0xFF` 一字节，`0xFF` + u16 BE），没有另发明宽度。句柄定宽之后，唯一的变长组件只剩 `Key`。
- 草案把挂载点留作开放项（一个接口问题：计划面的整文档写签名可能要多一个 `old fields` 参数）。落地的做法是挂在动态段写路径上，并且只在声明了路径索引时才在那里读旧映射——计划面与全部绑定调用点不受影响。
- 路径条目携带**空的值段**：v1 不支持 `Path` 形态的 `includes`（若要做，需要同样做一次"单一维护者"分析）。
- 仍未实现、也没有被悄悄丢掉：对**已存在数据**后声明路径索引的回填（形态是 ADR-0020 的范围扫描 + 一个 batch），path→slot 的持久注册表——slot 与其它访问方法一致，仍由调用方分配——以及宿主语言的声明面：`okm-python` 的 `add_func_index` / `add_partial_index` 还没有 `add_path_index` 对应物，因此路径声明目前只在 Rust 侧（纯声明的访问方法不需要 callable 桥，所以那条 binding 是小的增量改动，不是设计问题）。
