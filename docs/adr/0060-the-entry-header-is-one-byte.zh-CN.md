# 0060：表项的头部压成一字节，编解码器独立成 crate

> **Languages:** [English](0060-the-entry-header-is-one-byte.md)（主）· [中文](0060-the-entry-header-is-one-byte.zh-CN.md)

**状态：** 已接受（2026-11-11）——头部当日落地于 `okm-core/src/model/obj_segment.rs`，两个方向都是，并有十六进制锁；裁决 5 的 crate 也随它落地——`okm-value` 持有词表（`Id`、`Names`、`Vocabulary`）、值词汇表和段编解码器，`okm-core` 留着 key 与那道门（同日那条 PLAN 段）。
**日期：** 2026-11-11
**依赖：** ADR-0012（值词汇表）、ADR-0042（布局版本是戳）、ADR-0043（不留别名）、ADR-0056 §5/§6（replay 即迁移）、ADR-0057（块表）、ADR-0059（按轴切 crate）

## 背景

布局 v2 给动态段配了一张块表，但每个叶子的表项仍是三个字段：`id`、`type u8`、`len varint`。这就是格式对每个字段收的全部开销，也是 v2 丢分的地方：扁平段是每字段 3 字节再加 2 字节头和一个 count，而内联形态本来就是每字段 3 字节——块表换来的局部性，恰恰是在字节上没省下任何东西。实测：6 字段 × 8 B 的段里表占 30.4%，100 字段 × 16 B 占 15.9%。

两条事实让更小的头成为可能。

- **`len` 就是数字的宽度。** 动态段刻意不带宽度：整数的字节是它的最小大端形态，所以 `UInt(7)` 一个字节、`UInt(300)` 两个字节。读者不知道长度就不知道值在哪结束，而对数字来说那个长度**就是**宽度。
- **三种类型的长度不会变。** `Bool` 一字节、`Null` 零字节、`F64` 八字节。它们的 `len` 一个信息都不携带。

所以长度和类型在争同一批八个比特，而只要值体够短，一个字节能同时装下两者。

## 裁决

**1. 叶子的表项头是一字节：`[composite:1][len:3][type:4]`。**

```text
entry  = id varint | head u8 | body
head   = bit 7      复合：这一项拥有下一个块
       | bits 6..4  len：0..6 内联，7 = 逃逸（后面跟一个 `put_len` varint）
       | bits 3..0  ObjValueType（0 UInt、1 F64、2 Str、3 Bytes、4 Bool、5 Null、
                                6 Array、7 Obj、8 Int）——编号不动
```

- **短值体不再单独写长度。** `len ≤ 6` 就在头里；`len ≥ 7` 写逃逸码 7 再跟一个 `put_len` varint，而那正是 v2 的长度字段本来就付出的字节数。没有任何情况变大。
- **三种定宽类型完全不写长度。** 写者把 len 位写 0，读者忽略它；它们的长度来自类型，和今天由声明给出一样。
- **复合表项不变。** 它们没有值体、没有长度，所以头字节就是 v2 的 type 字节置上 bit 7（`0x86`、`0x87`）。
- **类型 nibble 保留原编号。** type 字节本来就是 append-only（ADR-0012）：0–8 号仍是原意，已存的含义一个都不挪。四位留下七个空槽——足够以后放 `u128`/`i128` 而不用再换布局，而这正是"把宽度写进类型标签"唯一能买到的东西。

**2. 买到什么，用 ADR-0057 的同一批形状实测。**

| 形状 | v2 | v3 | 为什么 |
|---|---|---|---|
| 值体 ≤ 6 字节、id 一字节 | 每项 3 字节 | 2 字节 | 长度装得进头里 |
| 任意值体，`Bool` / `Null` / `F64` | 每项 3 字节 | 2 字节 | 类型**就是**长度 |
| 值体 ≥ 7 字节 | 每项 3 字节 | 3 字节 | 逃逸花的正好是长度字段原来那笔 |
| 1 000 个 `Null` 字段 | 4 496 B | 3 496 B | 每字段一字节 |
| 20 000 个 `Null` 字段 | 99 495 B，拒收 | 79 495 B，拒收 | 两者都超了 16 位的表 |

所以收益精确地是：值体六字节以内的字段省一字节，定宽类型的字段省一字节，更大的值体一字节不省。这让本次改动相对 v2 是帕累托改进——从不更差——但它**没有**补上 v2 相对 0057 之前内联形态的差距：那个形态每字段 3 字节且没有头，所以 `3 + 3n` 仍然输给 `3n`。扁平段真正赚到的地方是值小的时候：`3 + 2n` 在字段数超过三时胜过 `3n`。

**3. 让 v2 安全的那些性质一条没动。** bit 7 仍是结构位，所以更新版本写进去的陌生类型仍可在不理解它的前提下跳过；长度仍然存在线上而不是靠推导，所以被截断的值仍能被抓出来；要自洽的算术是同一组（`toc_len` 落在文件内、叶子长度之和落在值区、`blocks = 复合数 + 1`、表 ≤ 65 535 字节）。

**4. 这是布局 v3，切换方式是清库，不是升戳。** 不升 `#[ok_layout]`，也不给段布局自己的戳：声明的载荷形状没动，而一个没有读者会去查的号只是仪式。存着 v2 段的库不迁移、也不被识别——它被删掉。有一条后果必须写明，因为字节本身管不住它：changelog 目录天生跨代存活，每段用它自己的 `layout_version` 去找声明（ADR-0056 §5/§6），而段布局不随那个号走——所以跨过这次改动的日志，会把 v2 的段字节喂给 v3 的解码器。清库要连日志目录一起清；非留不可的日志，由写出它的那个构建导出。

**5. 编解码器搬出 `okm-core`，值词汇表跟着走。** 段编解码器（`encode` / `decode`）被不止一个 crate 使用——`okm-core` 自己（`document.rs`、`model/graph.rs`）与 `okm-dynamic`（`graph.rs`、`plan_fields.rs`）——而它的货币类型 `DynamicValue` 还用得更外面（`okm-dynamic` 把它 re-export 成 `Value`，`okm-lake` 与绑定层都建在它上面）。本 ADR 采用的规则就一句：**一个 crate 用的编解码器是那个 crate 里的模块；两个或更多 crate 用的，是它自己的 crate。** 这也是 ADR-0059 的轴判据——切分单位要等于变化的单位，而值类型与布局版本按自己的节奏变，不随存储走。

这个 crate 不能只是编解码器：它的接口类型是 `DynamicValue`，一个回头向 `okm-core` 要自己入参类型的 crate 就是循环依赖。所以新 crate 是"无 schema 的值 + 它的词表视图 + 两者的编解码器"——`okm-value`：`DynamicValue` / `DynamicField` / `ValueMap` / `CodecError`、`encode` / `decode`，以及裁决 6 那道词表缝。`okm-core` 依赖它；旧路径下不留任何 re-export（ADR-0043 的姿态：改名不留别名）。

**6. 编解码器是有状态的，而词表跟持有存储的句柄一起死。** 段里装的是 id，所以字段名词汇表的两个方向都要穿过 codec 的边界。上一版把这件事叫"编码器"是错的：它持有一份词表，所以它**就是**词表，而词表是有状态的。`okm_value::Vocabulary` 持有两个方向，除此之外对存储一无所知；编码和解码是它的方法。

- **没有注册表，没有存储身份，没有失效逻辑。** 活得比库还久的缓存本身就是 bug——清过的库 id 从 1 重来，旧缓存会拿"没有任何行携带的 id"去回答——所以正确的做法是让这件事不可能发生，而不是围着它做键：词表就是持有存储那个句柄（`Collection`）上的一个字段，与它同生同灭。同一个存储上的两个句柄各存一份，靠"未命中就去探"保持正确（下一条）；不需要 scope 令牌，也不需要 engine 身份。
- **存储门是四个方法的 trait，传的是数据，绝不是 key 布局。** `scan`（存储已知的全部，供热路径用）、`name_id` 与 `id_name`（两次未命中）、`allocate`（花掉游标，把 name → id、id → name 和递增后的游标写进调用方的 batch）。`okm-core` 在 namespace 与 slot 所在的地方实现它一次；`okm-value` 永远不知道这两样是什么，它的测试用一个内存门，不需要 engine。
- **默认懒；`init` 是热路径。** 未命中就往两个方向各探一次：探到就认领，探不到才分配（名字 → id）或回答"没有这个 id"（id → 名字，那是答案不是错误）。因为未命中有探针垫底，跳过装载只是多花探针，绝不可能铸出重复 id。明确知道自己马上要碰一大批名字的调用方先热一次，因为一次前缀扫描胜过 N 次探针；只碰三个字段的句柄不该为一张千条词表付钱。
- **okm 留下的是：一个字段、一个 trait 实现、一次提交成功后的调用。** 分配在它那个 batch 提交成功之前不算数：为未提交的 label 发出的 id 记作未落地，被拒的写什么都不留；`landed()` 在提交成功后调（原 `promote`）。其余规矩——pending 窗口、mirror 纪律、该探哪个方向——全在 crate 里。
- **这个 crate 起步的形态是量出来的，而且不是前缀树。** `id -> 名字` 根本不需要结构：id 从 1 起且稠密，所以就是一个按 id 索引的 `Vec`——一次边界检查，没有 hash，而这正是每次解码都要走的方向。`name -> id` 是一张 hash map，用快速带 key 的 hasher，名字借用同一个 `Vec` 里的那一份（每个名字只存一次，命中不分配）。在 100 与 1 000 个名字上实测每次查找：快速 hasher 5–12 ns、SipHash 10–19 ns、逐字节前缀树 20–63 ns、排序 `Vec` 加二分 54–69 ns。前缀树只在问"某个前缀范围"时才划算，那是 path 索引的地盘（ADR-0029）。
- **结构体门不许装载词表**（ADR-0035）：`get` / `put` 永远不载它，所以词表在第一次走段门时建出来，之后边用边填。从不碰动态段的手柄永远不付这笔钱。

**7. 这个 crate 不是什么。** `okm-value` 是代码的落点，不是规范，也不是交换格式。段的字节仍然是 `(值, 词表)` 的函数——字段 id 来自所属表的词表、按首次出现分配——所以它在库与库之间不 canonical，也不以 canonical 自居。要做独立格式，要么名字内联（丢掉经济性），要么共享可变词表（退化成有状态协议）；那个问题在别处已经有结论，这个 crate 不重开它。

## 否决

**把宽度写进类型（`u8`/`u16`/`u32`/`u64` 各占一个类型码）。** 它确实能省下同一字节，但只对"量级恰好填满 2 的幂宽度"的那些值有效——而且它花掉的是长度需要的比特：五位类型只剩两位长度，于是三字节以上的任何值体（每个字符串、每个大整数）都要吃一次逃逸，成本从数字挪到了字符串。它比本裁决多出来的唯一能力——让声明的宽度上线——必须靠补零实现，于是 `u64` 存 7 要花 8 个值体字节，今天是 3。它过不了本 ADR 赖以成立的帕累托判据。

**只给三种定宽类型省长度、其余仍两字节。** `Bool`/`Null`/`F64` 各省一字节，数字一点没省，代价却是同一个格式代。花同样的价，只拿到三分之一的收益。

**把每个数字补零到声明宽度。** 这恰好亏在元数据形状文档里占多数的那些值上（`u64` 存 7 变成 8 个值体字节）。ADR-0057 的无宽度选择不变。

**把编解码器放进 `okm-wire`。** 那个 crate 拥有帧协议——op tag、key、value 一律当不透明字节——完全没有值语义。值编解码器没有传输层关切，而且它在存储路径上；两条轴不同。

**留在 `okm-core`，因为它本来就在一个文件里。** 文件不是边界，变化节奏才是。留在 core 让"只改一处"停留在习惯层面，独立成 crate 才让它成为结构性的事实。

**偏移、定宽条目、块目录。** 与 ADR-0057 一致，仍然否决：没有部分读——`VirtualStorage::get` 返回整个值——所以偏移买到的是比它自己占的字节更便宜的算术。

## 后果

- 已有的库连同它的 changelog 目录一起删除，不走 replay（见裁决 4）。这条放在第一位，因为它是唯一不可逆的一条：字节里没有任何东西能区分 v2 段与 v3 段，所以两个构建不能共用一个库。
- `okm_core::model::obj_dynamic` 与 `okm_core::obj_segment` 的路径变成 `okm_value::…`：对 `okm-dynamic`、`okm-lake`、绑定层和 core 自己的调用点是破坏性的。`ValueMap` / `NameResolver` / `CodecError` 跟着 `DynamicValue` 一起搬，所以接收它们的 trait 实现也一起搬。
- "叶子条目与旧内联帧头逐字节相同"（ADR-0057 §6）不再成立；机制页、那串手算的十六进制例子以及 MODELING 的语法行都要跟着改。
- 解码只多一条规则：bit 7 置位表示没有长度；否则 len 码为 7 表示后面跟一个 `put_len` varint；再否则那三位的值就是长度。逃逸那一个分支就是全部新增代码路径。
- 早先那个"定宽类型不带长度、宽度放类型里"的头部设想，作为否决记录留在这里，免得下一次评审重新推导一遍。
