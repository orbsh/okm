# ADR-0081 — 声明发的是地址，不是一类型一张表

**Status：** 2026-11-24 裁决（无代码）。记录的是一棵树里已经成立的形态：一个 store 一张物理表，表的身份在键里。

## 1. 问题

redb 的写法是一个静态的、带类型的句柄——`const T: TableDefinition<&[u8], &[u8]> = TableDefinition::new("name")`——而它的 B-tree 是一张表一棵。建在它上面的 store 自然会问：`okm-derive` 要不要给每个行类型发一个？声明是唯一知道「这里有一张表」的地方，那它也可以是给表命名的那个地方。

不，因为在 OKM 里表是一个地址，不是一个对象。`#[ok_ns(N)]` 编译成 `NS` / `NS_PREFIX`（ADR-0002），一个 ns 就是一张表（由按 ns 命名的静态量在编译期保证，ADR-0079），而任何动词构造的每一把键都从这个头开始（ADR-0011）。redb 称之为表名的那件东西，正是 ADR-0034 称为「只在 store 之外才有意义」的名字。

## 2. 量到的：按类型分表是一场平手，所以这不是性能决定

一个用完就扔的探针（redb 4.2，20 万条目、96 字节值、200 个命名空间 × 1000 行，每臂一个写事务）对比了一张键里带 `[ns 2B][id 8B]` 的表，与 200 张键里带 `[id 8B]` 的表：

| | 单表 | 一 ns 一表 |
|---|---|---|
| 文件大小 | 33 689 600 B | 33 689 600 B |
| 打开 + 列表 | 0.20 ms | 0.18–0.19 ms |
| 扫一个 ns（1000 行） | 48.0–48.6 µs | 42.3–43.4 µs |
| 点读 | 0.45–0.48 µs | 0.47–0.53 µs |
| 批量构建 | 104–113 ms | 77–79 ms |

那两字节前缀在页粒度上根本没落到文件里，而 200 张表的打开代价和一张一样。重复跑得住的差别只剩单个命名空间的扫描：1000 行 48.0 对 43.4 µs——而把这一千行取回来的那次查询，ADR-0080 量到 943.8 µs。扫描侧 5 µs 的差，在查询真正付账的那扇门前是舍入误差。

所以读路径没有为单表付任何代价，而这个问句既不能靠基准测出来，也不能靠基准重开。

## 3. 决定它的是边界

1. **一个身份，不是两个。** ns 就是这张表在 store 里的名字。`TableDefinition` 会让同一张表多一个名字——一个字符串——而声明搬动时要靠手改的正是那个字符串；烙在盘上每一把键里的是数字。
2. **derive 里没有引擎。** `okm-derive` 没有运行期依赖，也不依赖 `okm-core`——它只把 `::okm_core::…` 当 token 发出去。redb 是 `okm-core` 的可选特性，ADR-0073 靠特性维持引擎矩阵；生成代码里出现 `::redb::TableDefinition`，等于让每个消费者都链接 redb，只开 fjall 的构建会直接编不过。
3. **引擎边界说的是字节。** `VirtualStorage` 是 `&[u8]` 上的 `put`/`get`/`del`/`scan_range`。fjall 从构造函数拿 keyspace 名，redb 适配器持有那唯一一张表，slatedb 根本没有表，远端形态搬的是字节恒等的帧（ADR-0010）。把引擎句柄放进声明，等于把这个 trait 变成按引擎分叉的词汇——正是 ADR-0080 拒绝的那个方向。
4. **多张表共用一台引擎是字节的性质。** 测试矩阵与多租户托管能在同一个 store 上跑互不相同的逻辑表，是因为它们的键字节互斥（ADR-0011 §3）。按类型分表把这条换成了表名登记簿，而执行一帧的接收方就得知道一把键属于哪张表——那个 join 是 ADR-0011 定过价、并拒绝掉的。
5. **地址集合在编译期并不封闭。** `with_ns`/`rebased` 把表植根到另一个命名空间（ADR-0062），布局代际是头部里的一位（ADR-0075），`DynamicCollection` 打开的是 store 自己描述的那个命名空间（ADR-0025）。每个声明一个静态句柄覆盖不了这些，所以按字节前缀走的那条路无论如何都在——而在它旁边再放一条，就是两者开始不一致的方式。

## 4. 裁决

`okm-derive` 只发地址：`NS`、`NS_PREFIX`、`PARTITION_ID`/`PARTITION_PREFIX`、`PLAN`，外加活 store 之外的词汇所用的 `LAYOUT_VERSION` 与 `TABLE_NAME`（ADR-0042、ADR-0034）。生成代码里不出现任何引擎类型。

物理空间的边界若真实存在，归 store 句柄或归键：`FjallStore::open(path, name)` 从装配点拿它的 keyspace，redb 适配器用一张名为 `okm` 的表，临时引擎一张都不要，而 `#[ok_partition(N)]` 往地址里写一个结构性的转义段。这些都不是在声明上用属性拼出另一个引擎的词汇。

## 5. 被否的替代

- **按行类型发 `TableDefinition`。** 量不到任何收益（§2）；代价是特性矩阵（§3.2）、表的第二个身份（§3.1）、运行期命名空间（§3.5）与恒等帧（§3.4）。
- **每个表一个实现 `redb::Key` 的类型化键。** 把键编解码的语义搬进引擎 trait 的实现里。键的构造今天只有一个点（ADR-0011 的第一条后果）；按声明再发一份 `as_bytes`/`from_bytes`，就是把这个点变成两处。
- **拿 `TABLE_NAME` 当表名。** 把 store 之外的名字变成 store 之内的地址——正是 ADR-0034 拒绝把结构体自己的名字拼成表名时拒掉的第二套词汇。
- **现在就在 `VirtualStorage` 上加 `space` 参数。** 没有后端需要：redb 的单表、fjall 构造时给的名字、slatedb 没有表，都合字节契约。

**重开条件：**出现一台引擎，其中表是一等能力且没有字节前缀的等价物——整表删除而不扫、每表一把加密密钥、共享树表达不了的按表压缩——或者出现一个必须把某张表交给它自己文件的部署形态。那时边界长出一个引擎无关的参数，各后端各自映射，而声明仍然只发地址。

## 6. 论证住在哪

`okm-core/src/engine/redb_backend.rs` 与 `fjall_backend.rs` 的模块注释在后端作者会读到的地方说了同一件事。它们是这条裁决的就地形态，不是它的第二份来源。
