- [0046 — 追加日志：一小时一个桶，时间存差值，词表要自己挣出位置](0046-append-only-log.md)（已实现为 `okm-series`：信封、区块压缩、索引、词表、封存、按时间读、保留、一个分区字段都已落地；复制对偏移与词表的影响、多分片共享词表两问按设计留空——需求压力来自**保留**：LSM 里每条被丢弃的消息都留一个 tombstone，压缩预算花在一张只会变小的表上（aura 的 `MqData` 正是：`delete_before` 逐行 `purge`，每行一次提交、一次 Count reduce 的 RMW）。日志的目录即桶、桶即保留单位：`<log>/<bucket>/part-<n>.log`，封存靠改名，回收是 `remove_dir_all`，一个 tombstone 都不写；时间存**差值**——part 头记 `base_ts`，头部之后每条只存与前一条的 varint 差（繁忙流 1–2 字节、任何精度），时间不许倒退（写侧拒绝，因为字节顺序**就是**时间顺序），**没有逐条校验和**——既然没有 fsync 就不确认、part 只在末尾写，崩溃只能截断尾，于是撕裂的就是 `len` 越过文件末尾的那条（校验和抓的是存储栈说谎，那属于字节所有者的活；part footer 带一次整段摘要供复制/导出校验）；持久性反过来——fsync 之后才返回偏移，而不是 ADR-0045 的「先提交后追加、至多一次」；载荷是 nTLV 而不是不透明字节，字符串的**形态由条目编号承载**：`n=0` 内联、`n≥1` 用第 `n-1` 个词表，宽度 `u16 << k` 写在块头里，所以升格是改一个编号；词表**属于 part 而不属于日志**（part 是保留/导出/复制的单位，必须自包含；日志级词表要引用计数或 GC），升格按**按自身宽度的分档**，`[[4,10],[8,5],[16,3],[0,2]]`（编码宽度的倍数→升格次数，`0` 表示无上界）：`L ≤ W` 永不（比自己编码还短的字符串只会越存越大，1 字节的 `GET` 对上 u16 永远是亏的，这一条不可调）、`W..4W` 10 次、`4W..8W` 5 次、`8W..16W` 3 次、`16W` 以上 2 次——长端那档正是「长错误消息第二次出现就进词表」不是特例的原因；表是**配置不是格式**，改它只影响将来的 part；因为计数按 part 划界、每小时从零开始，短端才需要保守（全局常数 10 会让「每小时出现九次」永远进不了词表）；键唯一的流什么都不升、全部内联，无限基数不是失效模式而是默认路径；计数不持久化；ADR-0045 的段**不**搬用这个基底——共享的只是约定（目录、改名封存、截断撕裂尾），契约三点相反：这里每条记录要单调时间（变更日志没有时钟，塞进去等于让 NTP 一跳可能写失败捕获）、ack 前 fsync（那边是提交后追加、洞靠重扫补，搬过去等于每次写加一道延迟税）、按时间保留（那边是每个消费者一条水位线，段只有湖拿走之后才能删）；加宽链留在 part 内（首块固定偏移、从最新块沿 `prev_offset` **往回**走，最新块由 `.dict.tail` 改名指名——于是 part 内**没有任何原地修改**，「崩溃只能截断尾」才成立）；体按 **64 KiB 区块**压缩（zstd/lz4，冲刷时压而不是封存时压——封存时压要整段重写，2 倍写放大换几个百分点），索引是 `part-<n>.idx` 每区块一行、写区块时追加（不塞进 `log.meta`：那是每次打开都读、只写一次的身份；也不按桶：跨 part 的索引没法跟其中一个一起丢），统计只到**物理**层（记录数/字节/时间范围/区块数/整段摘要）——没有字段级统计（那是湖里 Iceberg 的事、抽干器写 Parquet 时算的），按字段分区是**路径**而不是索引（`<bucket>/<值>/part-<n>`，每分区一个写者与词表，保留仍按桶）；这个 crate 不是队列也不是时序库——没有 ack/重投/游标，没有聚合，它是「追加 + 读回」那一半，okm core 一点不动）— [中文](0046-append-only-log.zh-CN.md)
