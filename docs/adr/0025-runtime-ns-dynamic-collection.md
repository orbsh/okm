# ADR-0025: Runtime-ns dynamic collections — keyed documents assembled at run time

> **Languages:** [English](0025-runtime-ns-dynamic-collection.md) (primary) · [中文](0025-runtime-ns-dynamic-collection.zh-CN.md)

**Status:** Accepted (2026-09-24); implementation follows

## Context

`Collection<S, K, R>` binds its namespace at compile time: `R::NS_PREFIX` is
an associated constant generated by the derive, and `K: KeyEncode` is a
compile-time DDL struct (ADR-0002: the ns dictionary is code; the key
derive panics on any variable-width key field). Both bindings are correct
for declared tables — the schema is known when the program is written.

Aura's ADR-0026 (type-scoped actor storage) needs a collection whose ns is
a RUN-TIME value: every registered actor type allocates one real ns from a
registry (`ACTOR_NS_BASE + id`), and the host cannot know the numbers
until types are uploaded. The application declares its collections in a
schema carried in `interface_schema`; the storage layer must materialize
them against the type's allocated ns without a compile-time table type
per ns (impossible — ns is data) and without collapsing back to a
single-table text-prefix scheme (that would reintroduce the shared-keyspace
aliasing the type-ns ruling exists to remove).

The second requirement is the key. Actor-declared collections key their
documents by application fields (e.g. `{user: "alice", seq: 3}`), so the
key, like the ns, is run-time data. The engine contract still needs
byte-ordered keys: `scan_range` is THE ordered-read primitive
(VirtualStorage), index and prefix semantics ride byte order, and every
fixed-width `KeyEncode` field is big-endian precisely so that encoded order
equals value order.

## Decision

### 1. `DynamicCollection<S>` — a runtime-ns assembly point

A new collection type in `okm-core` (`model/dynamic_collection.rs`):

```rust
pub struct DynamicCollection<S> { /* ns: [u8; 2], store: S, dict: DictCache */ }
impl<S: VirtualStorage> DynamicCollection<S> {
    pub fn new(store: S, ns: u16) -> Self;
    pub fn put(&mut self, key: &[(String, DynamicValue)], doc: &BTreeMap<String, DynamicValue>);
    pub fn get(&mut self, key: &[(String, DynamicValue)]) -> Option<BTreeMap<String, DynamicValue>>;
    pub fn delete(&mut self, key: &[(String, DynamicValue)]) -> bool;
    pub fn scan_prefix(&mut self, prefix: &[(String, DynamicValue)], limit: Option<u64>) -> Vec<Doc>;
    pub fn scan_range(&mut self, begin/end over the same key frame, limit) -> Vec<Doc>;
}
```

The key is an ordered list of named `DynamicValue` fields (NOT a map —
order defines the encoding, the names resolve through the field-name
dictionary exactly as the dynamic segment does, ADR-0012). The key frame
uses its OWN order-preserving wire; the document VALUE reuses the
existing nTLV dynamic-segment frames and dictionary unchanged.

### 2. The dynamic key wire is order-preserving

Byte order must equal value order per field, or scan/range semantics lie.
The nTLV value frames cannot serve (the `len varint` prefix breaks
lexicographic order). The key frame encodes each field as:

- `UInt(u64)` / `Bool` — fixed-width big-endian (byte order == value order).
- `Int(i64)` — big-endian two's complement XOR sign bit (standard
  order-preserving transform: flip the top bit, compare as unsigned).
- `F64` — IEEE BE with the sign-magnitude → magnitude-sign remap (negatives
  bitwise-inverted), the standard total-order float key.
- `Str` / `Bytes` — **terminator encoding**: raw bytes with `0x00` escaped
  as `0x00 0xFF`, terminated by `0x00` (standard lexicographic byte
  order; prefix scans over a text field behave correctly).
- `Null` — empty field (sorts first among same-type fields); `Array` /
  `Obj` are REJECTED as key fields (their order semantics are the
  caller's problem — flatten first).

One field-name frame precedes the values? No: names resolve through the
dictionary to ids, and each key field carries its `[id u16 BE]` followed
by its order-preserving body. The id prefix keeps self-describing
addressing (ADR-0011) while remaining order-stable (dictionary ids are
stable per collection).

### 3. Layout: same header discipline as declared tables

Keys are `[ns 2B][slot][key frame]` with the SAME slot constants
(primary `0x00 0x00`, dynamic segment `0x00 0x01`, dictionary
`0x00 0x02/0x00 0x03`) — the runtime ns lives exactly where the compile-time
`NS_PREFIX` would sit, so remote frames, nest prefixes, and the host-byte
layouts stay uniform (ADR-0011 full-keys, ADR-0010 wire). The
field-name dictionary lives inside the collection's own ns segment, same
as declared tables.

There is no partition-segment interaction: runtime-ns collections are
unpartitioned (`PARTITION_PREFIX` is empty); a workload-isolation need on
actor data is not yet demonstrated.

### 4. Scope guard: what DynamicCollection does NOT do

No derive, no declared payload fields, no typed decode, no `#[ok_index]`
or `#[ok_reduce]` declarations (the schema IS the declaration; secondary
indexing is the caller's own auxiliary collection), no subscribe events.
It is the escape hatch for host-assembled schemas — declared tables stay
the default, and a runtime-ns collection is the tool when ns itself is
data.

## Honest semantic cost

- **The dictionary adds a cross-machine vocabulary dependency**: ids are
  stable only within one engine's dictionary; exporting raw key bytes
  between nodes requires the dictionary to come along (it does — it lives
  in the same ns segment — but consumers must know that).
- **Key field types are narrower than the value frames**: no Array/Obj
  keys, `Int`/`F64` need order-preserving transforms (two encodings of
  the same abstract value now exist: the value TLV and the key wire).
  Accepted: key order is the property that makes scans honest; the
  transforms are standard and testable.
- **No compile-time verification** of key shape: two writers using
  different field orders in the same collection silently fork the key
  space. The schema declaration (the caller's contract) is the guard.

## Consequences

- Aura's ADR-0026 executor materializes each actor-declared collection as
  a `DynamicCollection` at the type's registry-allocated ns — one real
  ns per type, no text-prefix aliasing.
- `Collection` (compile-time) remains the primary surface; nothing about
  declared tables changes.
- The dynamic key wire is new wire surface: the hex layout-stability
  test suite gains cases for the order-preserving transforms (Int sign
  bit, F64 remap, Str terminator escapes).
