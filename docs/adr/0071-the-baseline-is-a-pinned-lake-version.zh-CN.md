# 0071 — 基线是一个钉住的湖版本，尾巴仍是段

状态：2026-11-20 裁决，已落地——指针、它的校验、湖侧的压实与恢复；capture 默认打开与压实阈值是 PLAN 里的后续项，因为这两项要等基线钉在湖里才划算。2026-11-21 追记：§7–§8 以**声明半边**落地——`Document::CAPTURED` 默认打开、`#[ok_uncaptured]` 让一张表退出、选择写进 store 自己的 meta 行并在 attach 时比对；这两条点名的**装配半边**（`Collection::captured` 会登记、`Collection::new` 不会）由 ADR-0074 撤回：只有一个构造函数 `Collection::open`，不存在可能静默的装配开关。§2（尾巴以封好的段过河）是唯一仍未落地的项。

## 背景

开了 capture 的表，磁盘上留着自己 payload 的第二份拷贝。压实之后日志目录里有一份**基线**：把真相半边整个扫一遍再写成段，1M 行订单这批数据上实测 125.4 B/行；此外还有至多 1 GiB 未被覆盖的增量（`CompactPolicy` 默认 1 GiB 或 24 h，keep 0）。库本身在 5M 行、带一个二级索引时是 128.5 B/行。在应用机器上这就是表字节的两份拷贝，而第二份存在的唯一理由是「让读者有个起点」。

湖里已经是同一份真相半边。它由 drainer 从同一批段投影出来（ADR-0058、ADR-0061、ADR-0065），也就是应用扫一遍库去重新推导本可以从对象存储读到的东西。ADR-0042 §7 早就把搬迁的冷侧写成 lakehouse 导出；这条裁决让**基线**成为那一侧。

交接不依赖基线放在哪。它依赖的是与段同一介质上的一个位置：owner 文件、最后一个封好段的名字、三写一断言（ADR-0056 §6）。这一层不动。

有一样实测到的缺陷必须一起修。湖的 parquet 写入端没有设 `WriterProperties`，所以它的数据文件是不压缩的：1M 行这批数据 120.2 B/行，而同一批行用 zstd(1) 是 33.0 B/行、lance 默认 v2 编码是 39.5 B/行。在打开压缩之前把基线搬进湖，等于把 120 B/行搬到 120 B/行。

## 决定

1. **基线可以是一个湖版本。** 当湖的导出存在且已经追平时，压实不再写全状态段，而是在日志目录里记下 `(湖表, 版本, 最后覆盖的段)`。回放因此是「恢复 lake@V，再应用 S 之后的段」。应用侧不再持有表的第二份拷贝，持有的是一个指针加一段有界的尾巴。
2. **段继续承担尾巴与围栏。** owner 文件、位置、三写一断言都不变。尾巴以**封好的段原样**过河，而不是重编码成一个窗口，所以切换的关键路径上不做格式转换，也不等 drainer。
3. **扫库写基线保留为退路。** 没有湖、湖落后、指针校验不过，就按今天的方式扫库写基线。指针永远不是唯一的起点。
4. **指针要校验，不可信。** 读者重新列一次湖，确认版本存在、其 manifest 覆盖 S；任何不一致就拒绝使用该指针。ADR-0065 拒绝 `_last_checkpoint` 是同一条理由：指针是第二个可能与列目录结果打架的表面。它读的是 **V 那一刻**的列表，不是当前列表：湖之后又落了窗口，不能拿来替它已经不再描述的那个版本作答，所以日志按指针点名的版本读取。
5. **湖的数据文件用 zstd 写。** 基线搬迁只有在落点比原点小的时候才有意义。
6. **窗口跟着可恢复项是谁而定。** `CompactPolicy::default()` 保持 1 GiB：基线是自己扫出来的表，那次扫描就是应用机上唯一可恢复的区域。bulk 钉在湖里的表取 `CompactPolicy::pinned()`——256 MiB，窗口变小只换取一条稍长的回放尾巴。两个设置是同一个决定，所以谁也不取代谁。
7. **capture 默认打开，`Off` 是对部署的陈述。** `Location::Off` 保留，但含义收窄成「这份部署没有一个能放日志的本地持久目录」——`EphemeralStore`（ADR-0072：数据随进程消失的内存引擎）、只读副本、容器的临时盘。它不是「记录太贵」：基线钉在湖里之后，稳态成本是一个有界窗口，所以关掉它的理由必须是物理的。
8. **两级，两级都要明说。** store 决定**放在哪**（`ChangelogConfig::location`），表决定**要不要**（`Document::CAPTURED`，默认打开，`#[ok_uncaptured]` 退出）。默认打开把表这一级从「opt-in」翻成「opt-out」，于是排除必须读起来就像在排除——这也是它必须是声明属性而不是构造函数调用的原因：属性在定义表的地方就看得见，构造函数只在恰好调用它的那个装配点看得见。ADR-0074 直接把第二个位置撤掉了（`Collection::open` 是唯一入口，它读到选择后与 store 的行**比对**，而不是由某个动词覆写），于是「表决定要不要」现在只有一个地方可以写。
9. **湖的位置与日志的位置无关，而且可以不配。** 湖可以在另一个目录、在对象存储、或者不存在。不存在时压实退回扫库基线。因为写者要校验指针（第 4 条），应用读不到的湖就是一个指针永远不会被认领的湖——那是退路在正常工作，不是失败。

## 由此而来

- **应用盘**：日志目录变成「≤ 1 GiB 的增量 + 一个小指针」。那个与表大小成正比的常驻项消失，整机口径从约 2× 表变成约 1× 表加一个有界窗口。
- **跨主机切换**：bulk 从对象存储来，尾巴是一个 blob。共享 POSIX 挂载不再是 bulk 的前提；它仍然是围栏的前提，或者由对象存储上的租约取代——那是另一个决定，这里不裁决。
- **恢复**：lake@V 加段，走现有的导出/导入路径。词表 id 重新 intern（ADR-0032）、索引重建，与今天的导出完全相同。
- **备份**：对已导出的表，湖成为归档的记录本身，于是它的保留策略（`vacuum` 的 `keep_versions`）**就是**备份保留策略，必须按这个说法写清。没人导出的表除了自己之外仍然没有归档。
- **这里不决定**：把围栏本身放到对象存储上。条件写的租约会把 ADR-0056 §6 否掉的 per-provider 论证重新引进来。

## 被否

- **用湖版本当交接位置。** 围栏会失去同介质证据，位置由第三个进程（drainer）推进，秒级断言变成等别人的进度。
- **切换时把尾巴重编码成湖的一个窗口。** 那是在必须很短的那段窗口里塞进一次格式转换和一个 drain 依赖。
- **用 lance 当湖格式。** 实测 39.5 B/行（parquet+zstd 是 33.0）；它钉 arrow 58 而 okm 是 60（一个二进制里两个 arrow）、构建要 `protoc`、还把 datafusion 拉进来。它真正的长处——随机访问、索引、向量检索——属于 okm 没有的服务层；如果哪天有了，那是叠加导出，不是替换。
- **DuckLake。** catalog 是一个 SQL 数据库，于是写者为了替换一次 JSON 追加，换来一个引擎，以及「catalog 行与 parquet 文件跨两种介质原子提交」的问题。
- **Iceberg。** 解析当前 metadata 指针需要 catalog，而 `iceberg-rust` 写侧仍是 0.x。它仍然是「被翻译到」的那个格式（XTable / UniForm），如果将来真有只认 Iceberg 的读者。
