# ADR-0050：junction 是一张表——自己的 ns、主键面、反向索引面

## Status

Accepted (2026-11-04)。取代 ADR-0015 的双 ns 寄生与 ADR-0016 里给 junction 的槽段（0x5nnn）。实现作为一次改动落地：derive、`Junction`、存储布局、导出的排除清单、以及建模指南。

## Context

今天的 junction 是寄生的：`link(a, b)` 在 A 的 ns 里写一条、在 B 的 ns 里写一条，都在保留的 0x5 段槽位上，两条的值都是空。ADR-0015 在做出这个选择的同时就把代价写下来了——条目装不下关系属性：「join time、role、permission」，而这是 SQL junction 表的经典需求。

代价不只是缺一个载荷。一个没有自己 ns 的 junction：

- 无法作为一个表被枚举或导出：它只是散落在两个别的集合里的槽位，所以 ADR-0045 的变更流把 junction 整段排除。
- 无法只凭一个端点删除：两条键是两个命名空间里的两个不同地址。
- 迫使每一个需要关系数据的应用去发明绕路。本 ADR 针对的正是那一种：两张文档表、每个方向一张——两张都自称真相，靠手写的双写维持一致。

## Decision

**1. 一个关系类型 = 一个命名空间**，和文档集合一样声明。junction 拥有自己的 ns、主键面和反向面。`0x5nnn`、`JUNCTION_ID`、`dir_slot` 和双 ns 的键构造一起退役：一种能带数据的关系类型就是一张表，那就给它一张表的地址。

**2. 主键面（0x00）就是关系行**：`[A·身份][B·身份] -> 关系文档`。关系的数据只存在于这里。因此 junction 可以携带载荷，并且用文档已有的一整套机制（字段类型、默认值、编码位置）——值是文档，不是字节串。

**3. 反向面是索引，不是第二份真相**：固定面 0x06 上的 `[B·身份][A·身份]`（0x06 由图让出：一个 ns 要么是图、要么是 junction，不会同时是两者），值是主键行的指针。它是投影：可以走主键面重建，坏了是修复而不是数据丢失。固定面 0x06/0x07 按现有编号复用，不新增分配。

**4. 方向不对称就是 SQL 的二级索引，不是缺陷。** A 方向是直接按主键读；B 方向是一次索引扫描加每条命中一次主键回查。当某个热点查询需要属性又不愿多一跳时，可以在反向面上加覆盖列——局部改动，主键面仍是唯一真相。

**5. 级联是原语，不是策略。** `unlink_all(node)` 走每一个指向该 node ns 的 junction 类型的反向面，在一个批里删掉每条行的两个面，返回条数。`purge` 时是否自动级联仍归调用方：那要求 okm 在运行时知道「哪些关系类型指向这个集合」，而这个模型在编译期声明关系类型。

**6. 导出按两个面分别处理**：主键面是真正的表，进湖；反向面是派生的，留在湖外——和图的面留在湖外同一个理由（`Graph::reindex` 从行重建它们）。ADR-0045 的排除清单从「junction」改成「junction 的反向面」。

## Alternatives rejected

- **两张文档表、每个方向一张（k10r 的镜像方案）。** 两张都装着事实，一致性依赖每个写者成对地写两次；而且谁也不能从谁重建。索引面两个问题都没有。
- **把载荷同时写进两条寄生条目。** 同一个事实存两遍且没有权威——或者只存一次，那两条条目不对等，每个反向读者都要知道自己站在哪一侧。
- **所有关系都用图边。** 对开放的端点类型、谓词、平行事实是正确的；对一个闭合的、两种类型的关系是错的——那里一张表是更小更快的陈述，而图的机械（谓词词表、edge id、ref 解码）是没有用户的成本。
- **让 junction 保持无值、另建一张表装属性。** 那就是镜像表，只是低了一层。

## What this does not change

junction 仍然只连接**两个**已声明的类型；身份仍然是端点对（没有 edge id：同一对之间、同一类型只有一条关系，平行事实是图边的活）；关系仍然作为显式事件被写入和删除，永远不作为文档字段。
