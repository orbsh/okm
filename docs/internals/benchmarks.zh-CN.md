# 基线基准

核心路径的基线数字（PLAN Phase 7「Benchmarks」），2026-09-12 记录于最初的 criterion 基线（`--save-baseline initial`）。用途：跨引擎/codec 变更的相对比较——**不是**绝对真理。共享跑分的机器方差 ±5%；在专用跑分机出现之前不设 CI 回归门。

重跑：`cargo bench -p okm-core --bench core_paths`（加 `-- --baseline initial`与本表对比）。引擎专属的 bench（fjall/slatedb/远程 round trip）在接线完成后作为独立的bench 文件落地。

## 环境

- dev profile（criterion 默认以 release 构建 bench——数字是 release 级），本机跑分
- MockStore 已移除；基线引擎 = TestStore 默认（slatedb 内存态）——代表内存局部性，
不代表磁盘引擎

## 被测声明

- `BenchKey { org_id: u32, user_id: u64, tag: [u8; 4] }`——16 字节键
- `BenchRow { level: u32, score: Reverse<u64>, visits: VarInt<u64>, name: String }`
——热段 6B + 两个冷 TLV 帧，一个字段索引（by_level）+ 一个 reduce（按 level 的 count+sum）

## key / payload 编码

| 路径 | 均值 |
|---|---|
| key encode（16B，3 字段） | 5.5 ns |
| key decode | 3.0 ns |
| encode_prefix_named（完整 3 字段） | 7.7 ns |
| encode_prefix_named（前 2 个） | 7.0 ns |

| 路径 | 均值 |
|---|---|
| put（行 + 索引条目 + reduce fold） | 1.31 µs |
| 点查 | 42 ns |
| 批提交（100 个操作） | 4.1 µs（约 41 ns/操作） |

## 同一批行的四个落点：OKM+fjall、裸 fjall、Redis、Parquet

`cargo run -p okm-core --release --example engine_paths --features test-engines,fjall`——一台机器、单线程、**1,000,000 行**，形状与本文其余各节相同（`BenchKey` + `BenchRow`：一个索引、一个 reduce）。

写是一次计时通过：第二遍就是覆盖写，而 LSM 里的覆盖是墓碑加 reduce 的 unfold，比插入慢好几倍——三轮取中间值量到的会是那件事，不是写。读与扫描是三轮的中间值。扫描探针是一个索引值后面挂表的百分之一（`level = i % 100`），即一万行。

**裸 fjall** 这一臂是这一节的关键：同一个索引值、同一批文档，分成两个 keyspace，用 fjall 自己的迭代器遍历，中间没有 okm——没有键结构、没有文档解码、没有 reduce、没有 `VirtualStorage` 那一跳。它回答的问题不是"okm 快不快"，而是"LSM 到底能不能做批量扫描"，以及 okm 的扫描贵在哪儿。

Redis 臂连的是 valkey 9.1.2，走 loopback，用的是写进 example 的 RESP 客户端——没有为这件事往 `okm-core` 加 crate；`REDIS_URL` 可以指向别处，连不上就自己跳过。

映射关系决定了这些列能不能比：OKM 的一次 **put** 是行、索引条目、reduce fold 一次调用完成；裸 fjall 的 put 是文档与索引条目两次写，没有 reduce。Redis 里是 `MULTI`/`EXEC` 中的 `SET` + `SADD` + 两次 `HINCRBY`。一次 **batch** 是一次 `Batch::commit` 对一次 `MULTI`+`EXEC`。一次 **scan** 是一个索引值后面一万行，带取回行与不取回行（`scan_covered` / 只 `SMEMBERS`、分数编在 member 里）。Parquet 没有任何点操作的对应物，那几格是空的。

| 臂 | put | get | batch（100 行） | scan（10,000 行） | covered | 磁盘/服务内 |
|---|---|---|---|---|---|---|
| okm + fjall（Buffer 模式） | 4.8 µs | 1.2 µs | 0.97 µs/行 | 10.1 ms（1.01 µs/行） | 5.0 ms（0.50 µs/行） | 208 MB |
| 裸 fjall（无 okm） | 1.7 µs | 782 ns | — | 4.4 ms（0.44 µs/行） | 1.2 ms（0.12 µs/行） | 208 MB |
| parquet（zstd 1） | 0.12 µs | — | — | 25.4 ms，全量一遍（25 ns/行） | — | 3.3 MB |
| redis / valkey（loopback） | 22 µs | 8.4 µs | 3.1 µs/行 | 4.4 ms（0.44 µs/行） | 1.2 ms（0.12 µs/行） | 171 MB |

怎么读：

- **点查是这个存储的全部意义，而在这个尺度上 fjall 比 Redis 快一个数量级**：裸 fjall 777 ns，走 okm 1.1 µs，Redis 8.3 µs。差的不是"内存对磁盘"（按 wiki 的存储器层级一节，这两者真实差距只有一个数量级上下，而且工作集在 page cache 里时根本不读盘），差的是一个往返——Redis 的每一次读都要过协议。
- **批量扫描不是核心场景，它本来该走 Parquet**：okm 能导出 Parquet（Iceberg 支持在后面），3.4 字节一行、全量一遍 25 ns/行。把"扫一百行、一万行"当成存储的考核项，是把分析负载塞进 OLTP 引擎。
- **而在 Redis 本该赢的那个场景——一个集合、一次往返取回全部成员——它也没有赢多少**。对比裸 fjall（把 okm 的模型层拿掉，只留 LSM 迭代器）：fanout 100 时裸 fjall 109 ns/行、Redis 192 ns/行；1,000 行时 102 对 121；10,000 行时 132 对 116；100,000 行时 196 对 136。也就是说 Redis 的优势要到一万行以上才出现，最好也只有 1.4 倍，而在一千行以下是裸 fjall 更快。
- **okm 自己的扫描比两者都慢**（fanout 100 时 490 ns/行，是裸 fjall 的 4.6 倍）：这部分是模型层的成本，不是引擎的。钱花在哪是量过的——一处多余的拷贝（每条条目把后缀再分配一份，只为去掉前缀）单独测值 26 ns/行（同样一万条：151 ns 对 125 ns），现在改成 drain 前缀、不再拷贝；其余是 `ScanIter` 每行交还一对 owned `(Vec, Vec)` 加上类型化解码。要把这两处去掉得动 `VirtualStorage` 的 trait，对一个真实归宿是 Parquet 的场景不值。把它算在"磁盘慢"头上，就是 wiki 里批判的那个错误归因。
- **写：裸 fjall 1.7 µs，Redis 22 µs，差的是 13 倍**。Redis 那 22 µs 里没有一件事是数据结构本身的开销，全是往返与协议解析。
- **持久化旋钮值 76 倍**：同一个 fjall、同一个 put，缓冲 4.8 µs，每次写都 fsync 是 0.37 ms。
- **占用**：fjall 的 LSM 文件在这个尺度上 208 MB（218 B/行，两次运行在 130–208 MB 之间，取决于 compaction 停在哪）；Redis 171 MB 是服务器的 `used_memory`；Parquet 3.3 MB。这些都不能和日志的 56 B/记录相比——带索引和 reduce 的 KV 存储是另一件事。

### 一个索引值、不回表：okm 扫描、裸 fjall、Redis 三方对照

| fanout | okm 扫描 | 裸 fjall | redis | 裸 fjall ÷ redis |
|---|---|---|---|---|
| 1 | 7.0 µs | 842 ns | 7.8 µs | 0.1x |
| 10 | 1.1 µs | 144 ns | 879 ns | 0.2x |
| 100 | 490 ns | 107 ns | 197 ns | 0.5x |
| 1,000 | 452 ns | 102 ns | 128 ns | 0.8x |
| 10,000 | 495 ns | 124 ns | 177 ns | 0.7x |
| 100,000 | 356 ns | 188 ns | 142 ns | 1.3x |

每行成本，不回表，同一次运行。

- **Redis 的"批量优势"只在拿它跟 okm 的模型层比时才成立**。跟裸 LSM 比，它在一千行以下更慢，最好也只是十万行时的 1.3 倍——这是它最擅长的形态（一个集合、一次 `SMEMBERS`、零解码），结果只值这么点。
- **裸 fjall 每行 100–190 ns，而且几乎是平的**；okm 那 356–495 ns 里约 4 倍是模型层（引擎迭代器每行给一对 owned、类型化解码、结果向量），不是引擎。
- **fanout 为 1 时三条路都不便宜**（6.7 µs / 952 ns / 8.0 µs）：开一个范围、解一条条目、造一个结果集是固定成本。要一行就该按主键取——那正是点查那一列，okm 1.1 µs、裸 fjall 777 ns、Redis 8.3 µs。
- **覆盖读一行不到半个点查**：okm 上 500 ns 对 1.2 µs，裸 fjall 更是只有一个零头；索引那一半从来不是贵的那一半，贵的是回表，而回表在批量场景里本来就该被避免或外包出去。
- **结论**：点查场景 Redis 输一个数量级，批量场景它只赢 1.1–1.4 倍，而那个场景的正确出口是 Parquet 而不是任何 KV。这就是 wiki 里那份批判的实测版本——Redis 的问题不是"内存库不好"，是它在两个方向都不占优，剩下只有多一跳网络的成本与一份要单独运维的进程。

## 动态 codec 的税（okm-dynamic 对 Rust derive，同一份声明）

| 路径 | dynamic | derive | 税 |
|---|---|---|---|
| key encode | 40.0 ns | 5.1 ns | 约 7.8× |
| payload encode | 84.2 ns | 107.7 ns | 约 0.8×（这里 dynamic 更快） |

key 上的解释器税真实存在，但绝对尺度极小（40 ns 对 5 ns——都远低于任何一次引擎操作）。payload 的反转（dynamic 比 derive 快）说明 derive 的 String TLV 路径分配得比走一遍 schema更多——值得以后查，不是阻塞项。dynamic 的 decode 基准随 PyO3 绑定工作一起落地。

## 变更日志的捕获税

`cargo run --release --example changelog_tax -p okm-core --features test-engines,fjall`（9 轮配对 × 5,000 次 put，每轮翻转顺序，取各轮比值的中间值——两个 fjall store 各自按自己的节奏做 compaction，所以不成对的中位数会漂）：

| 路径 | 均值 |
|---|---|
| put，无日志 | 1.32–1.55 µs |
| put，被捕获 | 1.37–1.71 µs |
| 捕获税 | **+84 到 +99 ns/次写，+6.9% 到 +8.5%**（一次离群：+54 ns，+5.4%） |

本机六次运行：+54/+5.4%、+84/+7.2%、+95/+8.5%、+99/+6.9%、+132/+4.7%，以及一次早期未配对的运行打印出负税（配对轮次修的正是这个）。读作 **约 +50 到 +135 ns/次写、5% 到 8%**，取约 90 ns。

这份税是帧的编码加一次 memcpy 进段缓冲：16 B 的键和约 45 B 的 payload 下，它远不到一次持久化put 的十分之一，也不碰 store 自己的成本。散布来自机器而不是代码——两条臂是两个各自按自己节奏compaction 的 fjall store，这就是数字取自逐轮翻转顺序的配对轮次的原因。

量度对象是 `fjall_tmp`，一个持久化 store——捕获税只有对着它才诚实。内存引擎在此之前根本不能用于这件事：`SlatedbSync` 在每次 `put` 上 await `WriteHandle::await_durable`，而持久化要等下一次WAL flush，slatedb 的默认间隔是 **100 ms**——实测每次 put 101 ms，平的一条线，与 store 规模无关（300 次 put = 30.3 s），这就是 `cargo bench … write-changelog` 看起来像挂死的原因。内存引擎现在跳过这个等待（对象存储随进程一起消失：没有东西需要恢复），同一段循环跑 5 ms（**约 17 µs/put**，快 6,000 倍）。

## 参照：对照网络 KV 服务（Redis，公开数据）

公开的 redis-benchmark 数据（官方文档，同可用区的 r7g/c6i 测量）：一次 GET/SET 是**约 100–300 µs p50**（loopback 或同可用区 TCP；单核约 145K ops/s，流水线约 1.5–1.8M ops/s）。各篇公开分析的拆解是一致的：哈希表查找约 50–100 ns，其余全部——RESP 解析/序列化、内核系统调用、网络往返——占这次操作的约 97%。值的大小线性放大网络那一侧（1 MB 的值约 12 ms）。

OKM 是**进程内库**——与「进程内缓存」那类数字同属一类（31 ns 哈希查找 + 指针），不属于网络服务那类。上面基线的单次操作成本恰好落在一个进程内 store 该在的位置：

| 操作 | Redis（网络，公开数据） | OKM（进程内，基线） |
|---|---|---|
| 点查 | 约 100–300 µs | 42 ns（put+get 路径）/ 带索引回表约 130 ns |
| 点写 | 约 150–300 µs | 1.3 µs（语义：主表 + 索引条目 + reduce fold） |
| 裸批提交 | 流水线约 0.6 µs/操作（16 深） | 约 41 ns/操作 |
| 扫一个前缀值的条目 | N 次往返（或 SCAN 迭代） | 约 120 ns/行，一次调用 |

诚实地读这张表：

- 三到四个数量级的差距是**网络**，不是服务器质量——Redis 自己的哈希查找是 50–100 ns，与 OKM 的
表操作同类。拿 Redis 的*总*延迟比 OKM 的*核心*延迟，比的是栈里不同的段。
- OKM **输给** Redis 的东西——没有结构性的，因为这个比较单位本身是错的。Redis 永远是「缓存服务 +
在其上提供 API 的应用」；Krystallizer 这类服务正是那个应用，所以诚实的单位是**OKM+服务 对 Redis+服务**。「多客户端/共享状态/TTL」这张清单在两种情况下都活在服务层：并发访问是服务的连接面（WS handler，无论用哪种存储并发度都一样），跨实例的共享状态是部署问题（OKM 或以共享引擎承载、或分片实例，ADR-0010 §5 的 bare/hosted 两种形态就是这套词汇），TTL/过期本来就是应用逻辑，Redis 也从来没替你实现过。应用改用 OKM 建模而不是 Redis 模式，得到的是：语义写（一次 put = 主表 + 索引 + reduce，而不是 N 次往返 + 客户端记账）、有 schema 的字节（每一跳不用序列化/反序列化）、以及有序结构（前缀扫描）而不用 ZSET 的各种变通。
- 部署拓扑：Redis 的是固定的（网络服务器、它自己的持久化、它自己的淘汰策略）；OKM 的是自由组合
——进程内引擎（本基线）、分片的 bare host（一个分片一个引擎，由编排器路由）、承载式多租户段（一个引擎，多个 `NestStorage`（配合 `#[ok_ns]`）执行器）、或一个形如 Redis 的网络服务（服务连接面后面的 RemoteStore——WS-CHANNEL 集成）——每种形态都只隔一个构造函数调用，字节格式在所有形态下都一样。
- 吞吐：Redis 单核约 145K ops/s（受 I/O 限制）；OKM 单线程约 700K 语义 put/s（每次 1.3 µs）。
诚实的说法是：作为进程内 Booth 存储（OKM 的设计点），网络服务的延迟下限是一笔可以直接删掉的成本——若确实需要网络面，把 host 包进服务的连接面，就能重建 Redis 的形状而不带 Redis 的模式。

codec 的成本落在运行间的噪声里；在两种压得动的形状上，压缩路径甚至比不压缩更快，因为写系统调用搬的字节少了 20–70 倍。
- **块大小比压缩级别更值钱。** 每块的工作（压缩、写、fsync、索引行）压过每条记录的工作：16 KiB
块每条记录 2.3 µs，256 KiB 块 0.56 µs。级别 3 在高度重复的数据上买回 9% 的字节，别处量不出来。
- **索引故意不逐块 fsync**——它是派生数据，adoption 会重建它。去掉第二次 sync 让写路径在 64 KiB
块下从 1,345 降到 882 ns/记录。
- **字典和 codec 不可互换。** 在闭环值上，interning 在 codec 看到之前就去掉了重复：在压缩之上
再少 4 倍的字节，且没有写时成本（872 对 683 ns/记录是反例）。每条一个唯一 id 时，它为 3% 的字节花掉约 15% 的写时间——那个形状就是 `Config::dict = None` 的用途。
- **读是 5–17 M 记录/s**，一次解一个块，调用之间不缓存任何东西；散布反映的是每个块解压要多少
工作，不是它装了多少条记录。
- 单线程，NVMe 上的 XFS（本机 `/tmp` 不是 tmpfs，所以逐块 fsync 是真的），无并发读者，每次运行
59 个块。

## 一百万条日志记录：okm-series 对 Parquet

`cargo run -p okm-series --release --example log_vs_parquet`——同样的百万条记录写两遍，一遍写进日志，一遍写进 Parquet 文件（arrow 60，ZSTD 级别 1，字典编码开，两边都是默认值）。记录是一个真实的日志行：level、service、host、一条 message（里面带 id 和延迟）、一个 32 位十六进制的 trace id、一个 latency、一个 status、一个 tenant。八个字段里有两个每条唯一，三个是5/8/16 个值的闭环集。

测试先打印基线——生成一条记录 195 ns，构造完 `Body` 302 ns——所以两边都不为测试自己的运算付账。

| 写入方 | 字节 | B/记录 | MB/s | 写 ns/记录 |
|---|---|---|---|---|
| okm-series，zstd 1，字典 | 56,087,068 | 56.1 | 28.4 | 1,881 |
| okm-series，zstd 1，无字典 | 60,123,961 | 60.1 | 33.7 | 1,703 |
| okm-series，不压缩（无 codec、无字典） | 165,774,882 | 165.8 | 66.6 | 2,374 |
| parquet，65,536 行/组 | 44,819,259 | 44.8 | 65.8 | 650 |
| parquet，4,096 行/组 | 48,393,042 | 48.4 | 68.3 | 676 |

| 读取方 | 全量扫描 | 单条 |
|---|---|---|
| okm-series | 2.64 M 记录/s | 52 µs（`read(offset, 1)`） |
| parquet，65,536 行/组 | 9.84 M 记录/s | 6,618 µs |
| parquet，4,096 行/组 | 8.39 M 记录/s | 887 µs |

怎么读：

- **Parquet 小 20%，写快约 3 倍。** 列式编码加按列的字典编码，在字节上就是比交错记录更好的答案；
而且写入方一次攒一个 row group，而不是每 64 KiB 压一次。
- **只有日志能按地址取一条记录。** 52 µs 对 887 µs 不是调优差距：Parquet 没有钩子能到第 *n* 行
而不解它所在 row group 的列，所以 4,096 行/组是它在这个用途上**最便宜**的形态，65,536 行/组要6.3 ms。日志按偏移 seek，解一个块，然后停。
- **全量扫描的数字不可当同类比。** Parquet 的扫描交回 Arrow 数组；日志把每条记录物化成带八个值、
五个自有字符串的 `Body`。只要一列的调用方应该去读 Parquet。
- **一次点读就是一次解压，外面套一次 open。** 示例把各段分别量了，加起来就是上面那个数：

| 每调用一段 | µs |
|---|---|
| `read_from(one offset)` —— 解压并扫描一个 64 KiB 块 | 43.2 |
| 扫目录、每个 part 读一次头、排序（`parts_by_offset`） | ~8 |
| `PartReader::open` —— 头、footer、字典、70 KB 索引 | 11.3，**现在每个 part 只付一次** |
| `File::open` | 0.6 |

  所以块大小才是旋钮：64 KiB 块意味着一次点读要解压 64 KiB，256 KiB 块会压低写成本、放大这一点读。
  索引**不再**被解析两次——排序 parts 以前要打开每个 part 读它的索引，那在 68 µs 里占 5 µs（头里就有
  同一个答案，0.6 µs 拿下）；之所以占比这么小，是因为索引早就改成读一次再切片，不再逐行读。`Log` 现在
  按 part 缓存解析好的 reader，键是文件长度——这成立是因为 part 只追加、只会变长（封存时改名，路径就是新
  键，所以封存后的 part 自然是一次新查找）。同一个调用因此从 62 µs 降到 **51.5 µs**，`parts()` 从 18.4
  降到 8.0；剩下的是解压，那是格式问题。

- **字典在这个形状下几乎不赚钱，而在下面那处修复之后也不再赔钱。** 7% 的字节换 8% 的写时间：
八个字段里有两个每条唯一，分档把它们留在内联，字典只去掉了 29 个不同字符串。真正吃字典红利的是闭环集形状，上一节的表说明了这点。

### 这个测试抓到的两个缺陷

两个在 50,000 条量级都看不见，都在产出上面数字的那一轮里修掉了。

1. **part 索引是一行一次 `read` 系统调用读的。** 无缓冲的 `File` 每次调用约 200 ns，与大小无关；
一百万条记录的 part 有 2,214 个块，于是每次点读在碰到记录之前先付 429 µs 的系统调用。整份索引读一次再切片，把 `read(offset, 1)` 从 472 µs 降到 67 µs（`parts()` 从 429 µs 降到 23 µs）。排序 parts 现在根本不打开 part——头里就带着第一个偏移——2026-10-31 那次运行里同一个调用是 62 µs，同一天加上 reader 缓存后是 51.5 µs。
2. **词表的频率表以自有 `String` 为键。** 每个还没被 intern 的字符串都为计数分配了一份拷贝，于是
「每条唯一」的字段——比如 trace id——把表塞满永远到不了分档所要求的第二次出现的字符串。在这个形状下，那是两百万个活着的 `String` 和每条 1,077 ns（把表改成以字符串的 64 位散列为键、并给表加上 2^20 个跟踪字符串的上限之后，2,859 → 1,862 ns）。散列碰撞只可能让一个实际只出现一次的字符串被提升；它无法解析成错的文本，因为块和 `promoted` 表都以字符串本身为键。
