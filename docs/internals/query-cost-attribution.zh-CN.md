# 一次查询的时间去了哪里：实测

> **Languages:** [English](query-cost-attribution.md) (primary) · [中文](query-cost-attribution.zh-CN.md)

这份文档回答一个问题：外部提案（`docs/ideas/schema-aware-index.md`）声称，把引擎的索引层换成 schema 感知的块索引或自研 ART，能得到 3–100 倍。这样的说法只有在“引擎的搜索占端到端查询时间的很大份额”时才成立。它不是。本文把这段拆分测出来，好让那个提案按算术被判断，而不是按它背后论文的名声。

## 环境与语料

AMD Ryzen AI 7 H 350，NixOS 26.11，内核 6.18.60，XFS on NVMe，页缓存热。存储是真实的 fjall，memtable 已轮转并封存（外加一次 compaction barrier），所以下面每一次读都走 SSTable 与块索引，而不是走 memtable——这正是“重写索引层才会有意义”的那个配置。

20 万行、三份索引（`by_org`、`by_org_status`、`by_org_covered`），每份的键都是 12 字节定宽（4 字节 org，8 字节行）。一个租户占 18 万行（90%）；另外二十个千行租户填满剩下的。被扫的探针取自其中一个千行租户：恰好 1000 条索引条目，与第二份索引 join 之后剩 121 条。SST 占用 15.1 MiB，外加 1.4 MiB 的索引块。

测量装置：`okm-core/benches/query_cost.rs`，criterion，`cargo bench -p okm-core --features fjall --bench query_cost`。均值，置信区间不超过 0.5%。

## 实测

| 情形 | 时间 |
|---|---|
| `store.get`（引擎裸点读） | 590.4 ns |
| `Collection::get_row`（同一次读，上面套文档层） | 622.8 ns |
| 仅键编码 | 17.1 ns |
| 仅载荷解码 | 11.2 ns |
| 仅引擎范围读，1000 条（不读行） | 157.7 ns/条 → 157.7 µs |
| scan 门拆分，`parts::<()>` | 177.8 µs |
| `parts::<(parts::Key,)>` | 185.0 µs |
| `parts::<(parts::Row,)>` 排空 | 925.7 µs |
| 默认 `(Fields, Key, Row)` 排空 | 943.8 µs |
| 同上，`.collect()` | 963.8 µs |
| 覆盖索引（`includes(amount)`） | 193.6 µs |
| 两段 join：只交键流 | 218.5 µs |
| 两段 join：同上，再对每条幸存者取一次 | 317.8 µs |
| 空探针：租户根本不存在 | 2.764 µs |
| 空探针：租户存在，但没有后缀匹配 | 2.785 µs |
| 用 `next()` 走 10 / 100 / 1000 条 | 4.29 / 20.9 / 183.6 µs |
| 用 `ScanIter::seek` 跳到第 10 / 100 / 1000 条 | 5.14 / 5.21 / 5.29 µs |

## 一次千条查询的归因（943.8 µs）

| 阶段 | 每条 | 占比 |
|---|---|---|
| 索引条目读（引擎扫描，含块索引） | 157.7 ns | 16.7% |
| scan 门拆分 + `Fields`/`Key` 解码 | 27.3 ns | 2.9% |
| 取数阶段：主表点读 + 解码 | 758.7 ns | 80.4% |
| ——其中引擎的点读本身（`store.get`） | 590.4 ns | 62.6% |
| 物化进 `Vec` | 20.0 ns | 2.1% |

这张表推出两句话，而它们决定了那个提案的成败。

第一，索引重写能触碰的那部分——搜索本身，一次块索引下降——就是空探针的代价：**每次查询 2.76 µs，占 943.8 µs 的 0.3%**。16.7% 里剩下的部分，是读查询正当需要的这一千条并拆分它们；没有任何树的形状能把这些字节变掉。

第二，点读根本不是索引问题：`get_row` 是 622.8 ns，其中文档层只贡献 32 ns。一个完美的索引改善不了一次“代价在取行”的查找。

## 这份数据支持什么、否证什么、测不了什么

**否证。** 那个 3–100 倍。在这个负载上，索引层重写的天花板是 16.7%，即端到端 **1.20 倍**；而现实的数字接近 1.0 倍，因为搜索那一项只占 0.3%。提案自己的招牌例子——用一个前缀 Bloom 回答不存在的租户——在现有引擎上已经是 2.76 µs，比扫那个租户的数据便宜约 110 倍；把它整个去掉，省下一次查询的 0.3%。

**支持。** 前缀过滤确实省掉了真实工作量，只是范围很窄：它跳过了一次下降。而覆盖索引——193.6 µs 对 943.8 µs，**4.87 倍**——指出了真正的杠杆在哪里：不读那一行。这个杠杆已经存在，不需要新引擎。

**测不了。** 冷缓存的 I/O：这里每个数字都是热页缓存，所以任何关于磁盘寻道的说法都超出这套装置的能力。至于等长打包块能否在同一批字节上胜过 fjall 的压缩块，不写出那个引擎就同样无法测——而那才是提案的真实成本，不是一次测量。

## 与超图讨论的关系

不是直接适用，但同一条教训可以搬过去：在一千条规模上，join 的键流花 218.5 µs，对 121 条幸存者的取数循环再加 99 µs，所以算法性的投入该花在算子层——正如 gallop 那个结果所示（倾斜输入上 42 µs 对 1.49 ms，35 倍）。编码改动付的是字节与写放大的账，不是查询延迟的账，论证就该站在那个地面上。
