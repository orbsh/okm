# 并发与写者

OKM 的语义层是**单写者**的。这句话承担了很多含义，所以本文把它摊开：KV 层已经保证了什么、
哪些机制依赖"只有一个写者"、第二个写者会破坏什么、以及有哪四种形态可以承载更多。
目的是让"多写者"成为一个带账单的决定，而不是一个愿望。

类型层面的那一半是 ADR-0035 规则 10（`&self` 动词 + `!Sync` 集合）；本文是它背后的分析。

## 1. 两层，一条保证

**KV 层是并发安全的。** `VirtualStorage::put` / `del` / `get` / `scan_*` 全部取 `&self`，
每个后端都在这层之下做了内部可变性：fjall 的 partition、redb 的 `&Database`、slatedb 的
`Arc<Db>`、远程 store 的 `mpsc::Sender`、以及 `BatchStore` 的 `RefCell`。
`SharedVirtualStorage::shared_handle()` 是同一物理引擎的廉价克隆。线程安全的字节不是意外，
它是这一层的契约。

**语义层不是。** `Collection` / `Graph` / `Junction` 承载的是 merge 的读-改-写、reduce 折叠、
词表 id 分配、陈旧面清扫、epoch 排序。这些全都假设自己是唯一的写者，而且没有一个由引擎级锁保护。
"单写者"指的就是这一层，不是字节存储。

今天靠什么保证：

- 动词取 `&self`（ADR-0035 规则 10），所以"能写"不再等于"拿到可变借用"；
- `Collection` 是 `!Sync`——一次写唯一触碰的可变状态是 epoch 计数器，它是 `Cell`——
  第二个线程连它的引用都拿不到。

跨**进程**的互斥是另一根轴，而且引擎已经关掉了：fjall 打开目录时加文件锁（第二个进程打不开），
slatedb 用 manifest 里的 writer epoch 栅栏掉过期写者。两个进程无法共享一个目录；
本文讨论的只是进程内的线程。

## 2. 五个假设只有一个写者的机制

| 机制 | 有了第二个写者 | 失效形态 |
|---|---|---|
| `merge` / `replace` 的读-改-写 | 两个写者读到同一份存储行，各自据它计算 | **丢更新**；而且这次写还会把旧行从每个 reduce 组里回折，账本被重复调整 |
| reduce 的恰好一次 | unfold(prev)+fold(new) 这一对不再成对 | 累加器漂移——`Count`/`Sum` 少算一次写；`HighWater` 在旧写后落地时回退 |
| 词表分配（`VocabCache::id_for`） | `name_key` 探测未命中，两个写者都读到计数器的下一个值并且都占用它 | **两个名字共用一个 id**；id→name 解回最后落地的那个，另一个名字被静默改名 |
| 面（路径索引） | 陈旧面的清扫由**存储行**推导，两个写者读到同一份 | 落败方的新闻存活，指向一份已经没有这个值的文档——索引命中解不出东西 |
| epoch 排序 | epoch 每次提交 +1，并盖在订阅事件上；消费方按 epoch 折叠批边界 | +1 的顺序不再是提交顺序，折叠出来的边界是错的 |

这些全都是**语义**不变量。每次写底下的提交仍然是原子的：并发在这里产生的不是撕裂的文档，
而是一份看起来一致、实则错误的文档。

## 3. 四种能承载多个写者的形态

**A. `Arc<Mutex<Collection>>`** —— 最便宜，也是两个消费方各自在上一层已经做的。
`Mutex<T>: Sync` 只要求 `T: Send`，而 `Collection` 是 `Send`（`Cell<u64>` 是 `Send`），
所以它能编译，okm 一行都不用改。它把所有访问串行化（读也串），语义完全不变：
RMW、折叠、词表、epoch 都与今天一致。

**B. 在 `RwLock` 外再包一层** —— 换来读并发，但前提是包装层永不交出 `&Collection`。
动词取 `&self`，所以拿到**读**守卫就足以写；`RwLock` 保护的是借用，不是语义。
包装层必须自己拥有一套动词（`fn merge(&self, …) { self.rw.write().merge(…) }`），
字段保持私有。否则那把锁只是装饰。

**C. 一个写线程加命令 channel** —— actor 形态，也是最贴合这个库实际模型的。
`Collection` 是 `Send`，可以 move 进线程；命令从 channel 进来，RMW 天然原子，因为只有一个线程执行它。
代价：每个动词一次往返，而且命令面没法对 `K`/`R` 泛型——每张表要有自己的命令 enum，或者一套字节协议。

**D. 把 channel 当作 store** —— 已经实装了，而且是两份：`RemoteStore`（`engine/nest.rs`）
用 `mpsc` 实现 `VirtualStorage`，`wire_client` 是它的异步孪生。接收线程的
`ExecCore::apply(&self)` 锁住 `engine: Mutex`，把一帧里的写合成**一个** batch 提交，再回答帧内的查询。
它换来的是：N 个线程共用一个引擎属主，加上帧级提交原子性。
它**没有**换来 RMW 原子性：一个 `get` 和据它构造的 `put` 是两帧，别的写者可以插在中间。

## 4. 一帧到底买到了什么

- **一帧内的写 = 一次提交。** 全落或全不落。这是 ADR-0010 的跨装配点原子路径，远程形态也保留。
- **一帧内的读看不到本帧的写。** 帧内的 op 先累积在局部 batch 里，循环结束后才提交；
  查询前那句 `commit_batch(Batch::default())` 提交的是空 batch，也就是空操作，所以它注释里写的
  "reads see prior ops in the same frame" 不成立。今天没有**生产**调用方构造混合帧，因此没有东西坏掉——
  但混合帧要做到"读到自己刚写的"，得让查询走一个 `BatchStore` 视图。已记入 `PLAN.md`。
- **没有条件 op。** 一帧能表达"写这个"，不能表达"如果这行还是我读到的那样就写"——
  而那正是并发写者真正需要的原语。

## 5. 真要做多写者，欠的是四笔债

全部在语义层：

1. **行版本** —— 条目里要有某个东西让写者与自己读到的版本比较，好让丢更新被发现而不是被提交。
   （今天什么都没有：条目就是 payload。）
2. **能扛交错的 reduce** —— 要么折叠可证交换，要么累加器像行一样带版本校验。
   `Count`/`Sum` 是可逆的，但在一次 unfold/fold 配对之间并不无序。
3. **原子分配词表 id** —— 占用 id 必须是一个操作，不是"读计数器再写计数器"。
   否则即便两个写者各自只碰**不相交**的文档，字段字典仍然会损坏。
4. **面的记账** —— 没有一份"每文档产出的面清单"或一次扫描，陈旧面根本无法判定，
   并发覆写也就无从知道该清哪些。

还有时钟：进程内计数器无法给两个写者的提交排序。epoch 要来自引擎（由 store 发放序列号），
或者每个写者一条流、由消费方归并。

这四笔债没还清之前，"并发写者"是一个字节层的能力，带着语义层的洞。
这也是为什么在任何多写者设计里，抬起 `!Sync` 是**最后**一步，不是第一步。

## 6. 今天的边界在哪

- `!Sync` 对现有消费方零成本：aura 把 realm 放在 `Arc<tokio::sync::Mutex<Realm>>` 后面
  （`crates/realm/src/lib.rs`），krystallizer 的服务端持有 `Mutex<ChannelStore>` /
  `Mutex<GraphStore>`（`crates/mem-server/src/lib.rs`）。两边早就在 okm 之上串行化了。
- 想要更多线程的调用方，有 A / B / C 三种选择，不需要改 okm。
- `shared_handle()` 给的是线程安全的**字节**，不是线程安全的**语义**：
  两个线程各持一个指向同一个 store 的 `Collection`，正是类型看不见的那种情况——
  每个集合都是各自线程里独立的 `!Sync` 值，没有任何东西拦它。
  这是当前 API 最可能的误用，所以这条规则写在这里，而不是留给读者推断。
